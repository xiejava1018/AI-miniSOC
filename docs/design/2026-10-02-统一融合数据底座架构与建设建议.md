| 问题 | 结论 |

## 1. 背景与目标（Why）

### 1.1 现状痛点
当前三类核心安全数据物理散落在三个系统：

- **资产数据** → PostgreSQL（`soc_assets` 及关联表）
- **告警数据** → Wazuh 的 OpenSearch（`wazuh-alerts-4.x-*` 索引，由 Wazuh SIEM 192.168.0.30:55000 写入）
- **访问/行为日志** → Loki（192.168.0.30:3100，7 天窗口）

各源查询各自为政：`alert_query.py` 直查 OpenSearch、`loki_tools` 直查 Loki、`assets.py` 直查 PG。上层功能（资产管理 AI、告警研判、图谱、行为分析）需要"一个资产的全部上下文"时，必须自行拼装三个源，重复且易错。

### 1.2 目标
在不搬迁、不新增数据库引擎的前提下，建立**逻辑统一融合层**，使上层能：
1. 以统一实体（资产）为锚，跨三源解析与关联；
2. 拿到一个资产的**统一事件时间线**（告警 + 日志 + 变更 + 漏洞），支撑资产管理 AI 的 S11 变更影响、影响面分析、确认工作台等场景。

### 1.3 非目标（Non-goals，明确不做什么）
- ❌ 不把 OpenSearch / Loki 数据**全量搬迁**进 PostgreSQL。
- ❌ 不引入新的数据库引擎（Neo4j / Neptune / 数据湖 / 实时流处理平台）。
- ❌ 不做跨源实时物化视图 / CDC 同步管道。
- ❌ 不重造已有的图谱底座（`soc_graph` 已成熟，见 §3）。

## 2. 现状盘点（代码核实）

> 下表每一行均经源码核实，非凭记忆。

| 数据源 | 物理存储 | 落库方式 | 是否进融合层 | 代码依据 |
|---|---|---|---|---|
| 资产 | PostgreSQL | 主源 | 是（融合主锚） | `models/asset.py` → `soc_assets` |
| 漏洞 | PostgreSQL | Wazuh/OpenSearch 同步落库 | 是（进图） | `services/wazuh_scap_sync*.py`、`models/vulnerability.py` |
| 告警（原始） | OpenSearch | **实时查询，不落 PG** | 间接（经告警簇） | `services/alert_query.py:5` 明确"优先查 wazuh-alerts 索引" |
| 告警（簇研判） | PostgreSQL | 聚合后落库 + 关联资产 | 是 | `models/alert_group_analysis.py` → `soc_alert_group_analyses`（`linked_asset_id` 外键） |
| 日志（原始） | Loki | 实时查询，7 天窗口 | 否 | `mcp/tools/loki_tools.py` |
| 日志（特征） | PostgreSQL | 抽取行为画像落库 | 是 | `services/behavior_profile/loki_source.py:loki_raw` 拉原始行 → `soc_behavior_profiles` |
| 连接配置 | PostgreSQL | 多实例配置表 | 已统一 | `models/data_source.py` → `soc_data_sources` + `services/data_source_resolver.py` |
| 融合模型 | PostgreSQL | 图节点/边 | 已建 | `models/graph.py` → `soc_graph_nodes/edges` + `services/graph/builders.py`（6 Builder） |

### 2.1 已建融合层（绿框，已有）
- **统一连接管理**：`soc_data_sources`（多实例，DB 配置优先 + env 回落）+ `DataSourceResolver`（60s 缓存，支持 wazuh/opensearch/loki/tplink/scanner/ai）。
- **融合模型**：`soc_graph_nodes / soc_graph_edges` + 6 个 Builder：
  1. 资产-端口-漏洞 Builder（D1 确定性边，confidence=1.0）
  2. 身份 Builder（账号-人关联）
  3. 拓扑推断 Builder
  4. `AlertGroupBuilder`（告警簇 → 图节点/边）
  5. 人工关系 Builder
  6. NAT 映射 Builder（`maps_to` 边，5min 同步）
- **特征抽取**：`behavior_profile` 已从 Loki 抽取行为画像落 PG。

### 2.2 关键事实（纠正常见误解）
- **告警不是"完全没进 PG"**：原始告警文档在 OpenSearch，但**告警簇研判结果已落 `soc_alert_group_analyses` 并外键关联资产**——这是既有的"告警 → 资产"融合通道。
- **日志不是"完全没进 PG"**：原始日志留 Loki，但**行为画像（`soc_behavior_profiles`）已落 PG**——这是既有的"日志 → 特征"抽取通道。
- 因此"三源零融合"是错的；真实状态是**融合层已建一半，且三源都有各自合理的落库策略**。

## 4. 缺口详述与建设方案

### 4.1 缺口 A：统一实体解析锚
**问题**：三源标识符不统一——资产用 `asset_ip` / `wazuh_agent_id`，告警用 `agent.ip`，日志用 `srcip`。目前仅在图谱层部分对齐（`alert_query._find_asset` 按 `wazuh_agent_id` / `asset_ip` 关联），缺一个贯穿全局的"实体主键"约定。

**方案**：
- 以 `soc_assets.id` 为统一实体主键，建立 `EntityResolver` 服务：`(asset_ip | wazuh_agent_id | 日志 srcip) → asset_id`。
- 复用 `soc_assets` 现有字段，不新建大表；仅补充反向索引（如需高性能可加 `soc_entity_alias` 轻量表）。
- 覆盖日志 `srcip`、告警 `agent.ip` 的全量对齐，并把解析结果回流成 `soc_graph_edges`（补齐"东西向流量边""告警实时边"——即上一轮《数据底座评估》缺口 1）。

**接口草案**：
```
EntityResolver.resolve(ip_or_id: str) -> asset_id | None
EntityResolver.register_alias(asset_id, alias_type, alias_value)  # 启动/同步时填充
```

### 4.2 缺口 B：资产统一事件时间线 API（联邦查询 · 零搬迁）
**问题**：无"给我这个资产的所有事件（告警 + 日志 + 变更 + 漏洞）时间线"的统一查询。上层功能被迫各自拼装。

**方案**：新增 `TimelineService`，**运行时联邦拼接**三源，不落库（可加轻量缓存）：
- PG 适配：`soc_asset_change_log`（变更）、`soc_asset_vulnerabilities`（漏洞）、`soc_behavior_profiles`（行为）
- OpenSearch 适配：复用 `AlertQueryService.get_alerts_by_ip`
- Loki 适配：复用 `loki_raw` / `loki_tools`
- 归一化为统一事件模型后按 `@timestamp` 合并排序。

**接口草案**：
```
GET /api/v1/assets/{asset_id}/timeline
  ? start=ISO&end=ISO&types=alert,log,change,vuln&limit=200
→ {
    "asset_id": "...",
    "events": [
      {"ts": "...", "type": "alert", "source": "opensearch",
       "summary": "...", "level": 13, "ref": "fingerprint|agent_id"},
      {"ts": "...", "type": "log", "source": "loki",
       "summary": "访问 example.com", "ref": "log_id"},
      {"ts": "...", "type": "change", "source": "pg", ...},
      {"ts": "...", "type": "vuln", "source": "pg", ...}
    ],
    "merged_at": "..."
  }
```
前端可在"资产详情页"新增时间线 Tab（呼应 UI 融合设计里"详情页增强"而非新建页的纪律）。

## 5. 联邦查询实现设计（Federation / TimelineService）

> 本节把 §4.2 的接口草案落为可实现的技术设计，范围为 P0 时间线 API。原则不变：**零数据搬迁、零新引擎、复用现有三源客户端**。

### 5.1 统一事件模型（EventRecord）
三源事件归一化为统一结构，避免过度归一丢失信息：

```
EventRecord:
  event_id:    str            # 源内唯一 ID（fingerprint / log_id / change_id）
  ts:          datetime       # 事件时间（UTC），统一以此排序
  source:      enum           # pg | opensearch | loki
  event_type:  enum           # alert | log | change | vuln
  asset_anchor:str            # 关联资产所用的原始键（asset_ip / agent.ip / srcip）
  asset_id:    str | None     # EntityResolver 解析后的统一主键；P0 先用 asset_ip 粗对齐，解析不到为 None
  severity:    int | None     # 0-15（Wazuh level）；日志/变更可为 None
  summary:     str            # 人读摘要
  payload:     dict           # 源原始字段子集（保留细节，下游按需取用）
  raw_ref:     str            # 跨源回溯句柄（OS index+id / Loki stream+ts / PG table+id）
```

### 5.2 服务接口
```
class TimelineService:
    async def get_timeline(
        self,
        asset_id: str,
        start: datetime,
        end: datetime,
        types: list[EventType] | None = None,
        limit: int = 200,
        cursor: str | None = None,
    ) -> TimelineResult: ...

TimelineResult:
    asset_id:      str
    events:        list[EventRecord]   # 按 ts 降序，已截断至 limit
    next_cursor:   str | None         # 分页游标
    source_status: dict[source, SourceState]  # 各源 成功/降级/超时
    coverage_note: str                 # 诚实标注，如"Loki 仅覆盖近 7 天"
    merged_at:     datetime
```

### 5.3 三源适配器（复用现有**同步**客户端，统一用 run_in_executor 包裹）

> **实现约束（G1 关闭条件）**：源码核实——`LokiClient` 内部为同步 `httpx.Client`（`browsing_detection/loki_client.py:69`）、`AlertQueryService.get_alerts_by_ip` 为同步 `def`（`alert_query.py:147`）、SQLAlchemy 全程为同步 `Session`。因此 `TimelineService` 设计为 **async 服务**，但每个适配器的阻塞调用（HTTP 查询 / PG 查询）必须用 `loop.run_in_executor(self._executor, fn, *args)`（`asyncio.to_thread` 等价）卸载到线程池，**绝不可在 async 函数体内直接同步阻塞**。否则任一源慢查询会冻结整个事件循环、三源无法真正并发。各适配器内部自开 `SessionLocal()` 独立会话（参照 `graph.py:307` 的「独立 Session + 线程池」模式），避免共享同一 Session 跨线程。
- **PGAdapter**：以 `asset_id` 为锚查询——
  - `soc_behavior_profiles`（行为画像）：`WHERE asset_id = :aid OR (asset_id IS NULL AND ip = ANY(:asset_ips))`（**G3 关闭条件**：`asset_id` 可空（`behavior_profile.py:41`，未纳管设备），仅按 `asset_id` 过滤会静默丢日志；补充按 `ip ∈ 资产已知 IP 集` 回退，恰覆盖 UEBA 重点的未纳管设备）。
  - `soc_identity_events`（身份事件，**G4 关闭条件**：已是 PG 数据，含 `src_ip`/`dst_ip`/`ts`，`identity.py:20-39`，原设计漏纳入）：`WHERE dst_ip = ANY(:asset_ips) OR src_ip = ANY(:asset_ips) OR asset_id = :aid`。
  - `soc_alert_group_analyses`（告警簇研判，`linked_asset_id` 关联）：`WHERE linked_asset_id = :aid`。
  - 上述查询均经 `run_in_executor` 包裹后在协程内 `await`。
- **OSAdapter**：复用 `AlertQueryService`（实例化即同步建 `httpx.Client`，`alert_query.py:34`）；调用 `get_alerts_by_ip(ip)` 落在 `run_in_executor` 内。按 `wazuh_agent_id` / `agent.ip` 映射 `wazuh-alerts-4.x-*`。
- **LokiAdapter**：复用 `LokiClient.query_range`（已封装时间分片 + 截断信号）；调用同样经 `run_in_executor` 包裹。日志仅含 IP，故 **按"资产已知 IP 集"匹配 `srcip`**（G2：跨网段同 IP 复用存在，`asset_ip` 唯一约束实为 `(network_segment, asset_ip)`（`asset.py:16`）；时间线**始终以 `asset_id` 为锚、用 IP 集反查日志**，永不从裸 IP 反推资产）。stream 选择器固定为 `access_log`（G4 待与采集侧确认日志流名）。

### 5.4 并发编排与超时隔离（run_in_executor + gather + wait_for）
```
async def get_timeline(self, anchor, start, end, ...):
    loop = asyncio.get_running_loop()
    # 每个适配器阻塞调用都用 run_in_executor 卸载到线程池，避免阻塞事件循环（关闭 G1）
    pg_task  = self._guarded(loop, lambda: PGAdapter().fetch(anchor, start, end),         "pg",         3.0)
    os_task  = self._guarded(loop, lambda: OSAdapter().fetch(anchor, start, end),         "opensearch", 5.0)
    lok_task = self._guarded(loop, lambda: LokiAdapter().fetch(anchor, loki_start, end),  "loki",       8.0)
    results = await asyncio.gather(pg_task, os_task, lok_task, return_exceptions=True)
    # 单源超时/失败 → 该源 source_status=timeout/error，其余照常合并（诚实降级）
    events = merge_and_sort([r for r in results if isinstance(r, list)])
    return TimelineResult(..., source_status=build_status(results))
```
- `_guarded` 内部：`await asyncio.wait_for(loop.run_in_executor(self._executor, fn), timeout)`；超时抛 `SourceTimeout`、其余异常透传。
- `self._executor` 为模块级 `ThreadPoolExecutor(max_workers=8)`，三源并发由线程池实现，而非依赖 async 客户端。
- `return_exceptions=True` 保证单源异常不影响合并。

### 5.5 实体锚策略（P0 粗对齐 → P1 精确）
- **P0**：以入参 `asset_id` 为锚（**非**裸 IP）。适配器以 `asset_id` 直接查 PG（精确）；日志/告警因仅含 IP，用"资产已知 IP 集"（`asset_ip` + `public_ip`）反查匹配。解析不到 `asset_id` 的离散日志仍纳入时间线（标注"未关联资产"）。
- **G2 提示**：`soc_assets.asset_ip` 唯一约束为 `(network_segment, asset_ip)`（`asset.py:16`），全局 IP 可能复用。时间线 API **不以 IP 作为资产唯一锚**，而是锚定 `asset_id` 后用 IP 集反查——既规避跨网段碰撞，又满足"按资产看全部事件"。
- **P1**：接入 `EntityResolver`（§4.1），优先级 `wazuh_agent_id → asset_id` > `asset_ip` > `srcip` 反向索引，覆盖率提升至 ≥ 95%。

### 5.6 分页与限额
- `limit` 默认 200，上限 1000；`cursor` 为上一页末位事件的 `(ts, event_id)` 编码。
- 三源各自取 `limit` 条后在内存合并排序再截断，避免单源拉取过量导致 OOM。

### 5.7 诚实性约束（呼应 R2 / R3）
- **Loki 7 天窗口**：请求超窗时裁剪 `start` 至 `end-7d`，并在 `coverage_note` 标注"日志仅覆盖近 7 天"。
- **聚合计数**：OS 侧强制 `size=0` terms 聚合（复用既有 `get_level_buckets_by_ip` 范式），禁止客户端分桶，避免 level-13 被截断报 0。
- **缺失源**：`source_status` 显式标记，前端对"暂不可用"源展示占位而非静默遗漏。

### 5.8 验收标准（本设计）
1. **单测**：三源适配器可独立 mock，合并排序正确（含跨源 ts 交错、同 ts 稳定排序）。
2. **超时单测**：`PGAdapter` 注入 5s 延迟，整体在 8s（Loki 超时上限）内返回且 `source_status.pg = TIMEOUT`，其余源正常合并。
3. **集成**：对真实资产 `GET /assets/{id}/timeline` 返回三类事件，P95 < 2s。
4. **诚实性**：构造 Loki 超 7 天请求 → `coverage_note` 明确标注；构造 OS 故障 → 时间线不整体失败，降级返回。

> **代码落点（P0 已实现骨架）**：`src/backend/app/services/federation/`（`schemas.py` / `adapters.py` / `timeline_service.py`）+ `app/api/asset_timeline.py`（挂 `GET /api/v1/assets/{id}/timeline`，已在 `app/api/__init__.py` 注册）。

## 10. 落地可行性评估（Gap Analysis，2026-10-02 PM 复核）

> 本节基于源码逐条核实，回答"方案能不能落地、缺什么"。结论：**P0 可落地但需先关闭 4 个缺口；P1 当前不可作为编码任务落地（仍是设计 spike）；P2 条件触发无需现在决策。**

### 10.1 结论速览

| 阶段 | 能否落地 | 阻断级别 | 关闭条件 |
|---|---|---|---|
| **P0** 联邦时间线 API | ✅ 可落地（需先关 4 缺口） | 非架构级，规格补齐 + 适配器小改，约 1–2 工作日 | 关闭 G1–G4 |
| **P1** 实体解析锚 | ❌ 当前不可编码落地 | 设计缺口，需先 spike | 关闭 G5–G7（算法/覆盖率/迁移约束） |
| **P2** 规模扩展 | ⏸ 条件触发 | — | 规模破万级再评估 |

### 10.2 代码核实事实（非假设）

- 三源客户端**均存在可复用**：PG `AsyncSession`、`alert_query.AlertQueryService.get_alerts_by_ip`（alert_query.py:147，sync `def`）、`behavior_profile.loki_source` + `LokiClient.query_range`。
- **但 LokiClient 是同步实现**：`loki_client.py:69 self._client = httpx.Client(...)`；`get_alerts_by_ip` 同是 sync `def`。这是 P0 设计的关键约束（见 G1）。
- `soc_assets` 唯一约束是 `(network_segment, asset_ip)`（asset.py:16），**非 `asset_ip` 单列**。
- `soc_behavior_profiles.asset_id` **可空**（behavior_profile.py:40），未纳管设备为 NULL。
- `soc_identity_events` 已存在（identity.py:30），含 `src_ip/dst_ip` 与可空 `asset_id`——即"东西向登录"已是 PG 数据，但 §5.3 PG 适配器未纳入。

### 10.3 P0 缺口清单（须关闭才能编码）

| # | 缺口 | 严重度 | 关闭条件 |
|---|---|---|---|
| **G1** | **同步 I/O 未适配异步编排**：§5.4 的 `asyncio.gather` 直接调 sync `LokiClient`/`get_alerts_by_ip`，会阻塞事件循环，三源无法真并发，单源慢查询冻结整个后端 | **关键** | 三个适配器在 `async def` 内用 `await loop.run_in_executor(None, sync_call)` 包裹阻塞调用；§5.4 显式标注"现有客户端为 sync，禁止裸调" |
| **G2** | **asset_ip 匹配缺 network_segment**：P0 用 `asset_ip` 单键匹配会与跨网段复用 IP 碰撞 | 中 | 对齐键改为 `(network_segment, asset_ip)`；OS 侧需先按 agent 解析出 segment（默认 `default`） |
| **G3** | **行为画像 asset_id 可空被静默丢失**：PG 适配器"按 asset_id 过滤"会丢掉所有未纳管设备画像（恰是 UEBA 重点） | 中 | 对 `asset_id IS NULL` 画像改走 `ip` 回退匹配，或以"未纳管 IP"伪实体呈现 |
| **G4** | **identity 登录事件未进时间线 + Loki 流选择器未定**：PG 适配器漏 `soc_identity_events`（东西向流量源头）；Loki 适配器只说"按 srcip 查"未定 LogQL 流 | 中 | PG 适配器补 `soc_identity_events`；Loki 适配器显式写 `{app="browsing"}` 或实测流选择器 + 标签名 |

### 10.4 P1 缺口清单（须先设计 spike）

| # | 缺口 | 说明 |
|---|---|---|
| **G5** | `EntityResolver` 算法未定义 | "alias → asset_id" 优先级 `wazuh_agent_id > asset_ip(+segment) > srcip 反向索引 > hostname/mac 模糊` 需写清；模糊匹配阈值与冲突仲裁未定 |

### 10.5 纵向风险（仍成立）
