## 0. 总览与执行纪律

### 0.1 阶段目标
| 阶段 | 覆盖问题 | 目标 | 阻断级 |

### 0.2 执行纪律（强制）
1. **禁止对生产库跑任何 DDL/迁移**。所有验证在本地 PG 或测试库（`AI-miniSOC-testdb`）进行；涉及迁移、唯一约束、外键的工单，必须在**独立库**完成 `pg_dump` 备份后再操作。
2. **每个工单独立提交、独立可验证**，不跨工单打包。提交信息带 `[P4]` 前缀与工单号（如 `[P4] P1-T1 收敛 Alembic 迁移图`）。
3. **先想清楚再动手**：每个工单开工前，Agent 先用 Read/Grep 复核本文档标注的涉及文件，确认行号与现状，再改。
4. **评审复核机制**（沿用既有流程）：Agent 完成一个阶段后，由本会话主 Agent 做独立复核（对照"验收标准"逐项核对代码与库），复核通过才进入下一阶段。
5. **非目标不可触碰**（见第八节）：不新增检测源、不做报告生成、不重构采集器、不把路由器硬件故障当代码项、不引入 Celery 等重组件。

## Phase 1（地基 · 🔴 P0）

### P1-T1【问题 A】Alembic 迁移图收敛与重建（最高优先，单独立项）
**目标**：让 schema 回到版本控制下，消除重复 revision 与分叉，`alembic upgrade head` 可在新库幂等执行。

**前置依赖**：无（Phase 1 起点）。需 DB 访问（本地 PG 或 `AI-miniSOC-testdb`）。

**具体执行步骤**：
1. **备份当前 schema**：`pg_dump -s -O` 导出结构到 `scripts/migrations_backup_<date>.sql`，留存。
2. **修复重复 revision id**：将 `a1b2c3d4e5f6_add_vulnerability_management_tables.py` 的 `revision` 改为唯一值（如 `a1b2c3d4e5f7`），并据表依赖关系设定其 `down_revision`（建议接在正确线性位置上；因 vuln 表独立，可挂在 `c3d4e5f6g7h8` 之后作为新 head，或评估是否应与 data_classification 链合并）。
3. **合链为单 head**：清理分叉，确保 `alembic heads` 仅返回 1 个 revision。必要时用 `alembic merge` 合成 merge revision。
4. **把 alembic 加入依赖**：`requirements.txt` 增加 `alembic==<与 venv 兼容版本>`；在 venv 安装；确认 `alembic --version` 可用。
5. **以线上 schema 为基线 stamp（关键，不得裸 autogenerate）**：
   - 在**独立库**执行 `alembic stamp head`，将 `alembic_version` 标记为修复后的 head（不实际跑 upgrade，因结构已靠 create_all 存在）；
   - 跑 `alembic check`（或比对 `alembic upgrade head --sql` 与 `pg_dump -s`）；若模型与库漂移，产出**一份** corrective migration 对齐，禁止逐文件补。
6. **验证**：新库 `alembic upgrade head` 成功且幂等；`alembic current` 显示有效修订；`alembic heads` 单一。

**涉及文件**：`src/backend/alembic.ini`、`src/backend/alembic/versions/*.py`、`src/backend/requirements.txt`。

**验收标准**：
- [ ] `alembic heads` 输出**唯一**一个 revision；
- [ ] 全新空库 `alembic upgrade head` 成功率 100%，可重复执行无报错；
- [ ] `alembic current` 显示有效修订号；
- [ ] 保留 schema 备份文件，记录提交哈希。

**风险与回滚**：改迁移图若错接 down_revision 会导致 `alembic upgrade` 链断裂。回滚 = 还原 `alembic/versions/` 与 `requirements.txt`，复用 `pg_dump` 备份重建库。

### P1-T2【问题 A】收口运行时 DDL（迁移图修复后紧跟）
**目标**：生产启动路径不再有 `create_all` / 运行时 `ALTER`，表结构变更一律走 migration。

**前置依赖**：P1-T1 完成（迁移体系可用）。

**具体执行步骤**：
1. 逐个处理"已核实事实基线"列出的 6+ 处 `create_all` 与 `ALTER`：
   - `browsing_detection/scheduler.py:46`、`alert_digest_service.py:37`、`alert_group_triage_service.py:42`、`alert_group_snapshot_scheduler.py:32`、`alert_group_snapshot_service.py:45` 的 `create_all` → **删除**，改由启动流程 `alembic upgrade head` 保障表存在；
   - `alert_group_snapshot_service.py:58` 的 `ALTER TABLE soc_alert_groups ADD COLUMN IF NOT EXISTS` + `_schema_ensured` 开关 → 改为对应 migration（新建迁移补齐 `soc_alert_groups` 的 AI 列）；删除 `_schema_ensured` 全局标志；
   - `scripts/create_missing_tables.py`、`scripts/backfill_vulnerability_contract.py:147` 的 `ALTER` → 迁移化或标注为"历史一次性脚本，禁止生产调用"，加显式注释/退出码保护。
2. 增加 CI 漂移检查：在 CI 跑 `alembic upgrade head --sql` 并与模型比对，或加 `alembic check`（视 alembic 版本）。
3. 代码扫描确认：Grep `create_all|ALTER TABLE|ADD COLUMN IF NOT EXISTS`，除测试 `conftest.py`/`scripts/test_*.py` 外**无生产路径残留**。

**涉及文件**：上述 6+ 处源文件 + 新增迁移 + `scripts/`。

**验收标准**：
- [ ] 生产路径（非 test/conftest）零 `create_all`、零运行时 `ALTER`；
- [ ] 新增的 ALTER 类变更均有对应 migration 文件；
- [ ] CI 加入迁移漂移检查且不通过即阻断。

**风险与回滚**：删除 `create_all` 后若某表未被迁移覆盖，启动会报"表不存在"。回滚 = 恢复该处 `create_all` 并补迁移，不要裸回滚导致漂移。

### P1-T3【问题 B】Loki 查询分页 / 时间分片 / 聚合下推
**目标**：消除静默截断，行为检测基于全量或正确聚合样本。

**前置依赖**：无硬依赖；建议与 P1-T5（时间语义）协同设计窗口边界。

**具体执行步骤**：
1. 在 `app/services/browsing_detection/loki_client.py` 的 `query_range` 重构为**时间分片/边界翻页**：以本页末条时间戳为下一页 `start`，循环累计直至窗口耗尽（Loki `query_range` **无 `next` 游标**，只能用时间边界推进）。
2. 设**硬上限**（如 50 万行）防失控；超阈值记 `logger.warning` 并向上层返回"已截断 N 条 / 样本不完整"信号，绝不静默丢弃。
3. **聚合下推**：对计数/topk 类需求改用已有 `query()` 走 LogQL（`count_over_time` / `sum by` / `topk`），明细只在命中后按需拉取，降低体量。
4. 重试配退避与上限（与 P3-T1 一致），避免大查询重试放大负载。

**涉及文件**：`app/services/browsing_detection/loki_client.py`、`app/services/browsing_detection/scheduler.py`（调用方）。

**验收标准**：
- [ ] 注入 >1 万行日志的窗口，行为检测基于全量样本（或聚合结果正确）；
- [ ] 触发上限时有明确 warning 日志 + 结构化"截断 N 条"信号透出到调用方；
- [ ] 现有 `query()` 聚合路径可用且被新逻辑复用。

**风险与回滚**：时间分片过细会降低性能、过粗仍可能截断。回滚 = 保留原 `limit=10000` 单页逻辑，仅作为 fallback。

### P1-T4【问题 C】行为事件幂等落库
**目标**：同一 (ip,domain,window) 重复跑/重放不产生重复事件，KPI 稳定。

**前置依赖**：P1-T5（统一窗口语义，左闭右开）先定；P1-T1（迁移体系）用于加约束。

**具体执行步骤**：
1. 在 `models/browsing_event.py` 为 `soc_browsing_events` 增加唯一约束 `UniqueConstraint("ip","domain","window_start","window_end", name="uq_browsing_event_window")`。
2. 新建 migration 添加该唯一约束；迁移内先 `DELETE` 清存量重复（按 `(ip,domain,window_start,window_end)` 保留一条）。
3. 改 `event_service.py:53-65` 落库为 `INSERT ... ON CONFLICT (ip,domain,window_start,window_end) DO NOTHING`（或 `DO UPDATE` 仅刷 `score/rule_hits`），保留 `_is_suppressed` 作为二级抑制。
4. 回归：`create_findings` 同窗口重跑返回的 `created` 数应稳定（重跑后为 0 新增）。

**涉及文件**：`models/browsing_event.py`、`event_service.py`、新增 migration。

**验收标准**：
- [ ] 库内唯一约束生效（`\d soc_browsing_events` 可见）；
- [ ] 同窗口重复跑/重放事件重复率 = 0；
- [ ] KPI（事件数）在重跑前后一致；
- [ ] 存量重复已清理（SQL 抽样核对）。

**风险与回滚**：`ON CONFLICT` 与 `_is_suppressed` 语义若冲突会漏报。回滚 = 撤销唯一约束迁移 + 恢复 `db.add`，并补测试区分两者职责。

### P1-T5【问题 I】时间 / 时区统一
**目标**：跨窗口边界不重不漏，24h/7d 切换计数一致。

**前置依赖**：无；建议 P1-T3/T4 前完成以统一窗口定义。

**具体执行步骤**：
1. 明确**窗口语义：左闭右开 `[start, end)`**，在 `DetectionConfig` / scheduler 文档化。
2. 统一 **UTC 存储**：确认所有 `DateTime(timezone=True)` 落库为 UTC；展示层（前端）转本地时区。
3. 抽离时间工具 `app/core/time_utils.py`：纳秒↔秒、UTC↔本地、窗口切分函数，集中转换。
4. NTP 偏差：在启动日志打印本地/UTC 偏移，关键节点核对。
5. 补单测：跨边界窗口切分不重不漏；24h/7d 切换计数一致。

**涉及文件**：`app/core/time_utils.py`（新）、`scheduler.py`、`event_service.py`、前端时间展示处。

**验收标准**：
- [ ] 窗口一律左闭右开，跨边界不重不漏（单测覆盖）；
- [ ] 24h/7d 切换计数一致；
- [ ] 时区转换有集中工具且带测试。

**风险与回滚**：历史数据若已混入时区错乱，仅改新逻辑不影响旧数。回滚 = 撤销 time_utils 接入，保留旧逻辑。

### P2-T3【问题 F】数据新鲜度 / 采集健康监控
**目标**：采集中断主动感知，仪表板区分"正常窗口"vs"源挂了"。

**前置依赖**：建议复用 Phase 1 调度器埋点（见后台任务可观测性方案）。

**具体执行步骤**：
1. 建统一"数据源健康"记录：各采集器/源/同步任务记 `last_success_at` + 失败计数（可落在 `soc_task_executions` 或独立 `soc_source_health`）。
2. 仪表板态势条据 `last_success_at` 计算"数据截至"：>2× 采集周期未更新**标红**"采集中断"。
3. 对已知源（如 `192.168.0.2` TL-R479GP-AC 路由器）设中断告警（运维工单联动，非硬件修复）。

**涉及文件**：仪表板 summary 接口、前端 console 态势条、新增健康采集逻辑。

**验收标准**：
- [ ] 主动停某采集源，仪表板在 1 个周期内标红"采集中断"而非静默陈旧；
- [ ] 区分正常 7 天窗口与真中断。

**风险与回滚**：误报中断会扰民。回滚 = 关闭标红阈值或放宽周期倍数。

### P2-T4【问题 G】同步失败可追踪 / 重放
**目标**：失败记录入死信、可查原因、可重放，部分失败不阻断整批。

**前置依赖**：P2-T3 健康记录可复用。

**具体执行步骤**：
1. 批次级错误明细落表（或结构化日志）：批次 ID、失败记录主键、错误类型、时间。
2. 死信队列：失败记录进死信，支持按批次重放；成功部分可见、不丢。
3. 注入一批含坏数据的推送，验证可查、可重放、整批不丢。

**涉及文件**：同步任务服务层、`soc_sync_tasks` 扩展或新增死信表、相关 API。

**验收标准**：
- [ ] 注入坏数据，能查到失败记录与原因；
- [ ] 可重放成功记录，整批不丢；
- [ ] 部分失败不阻断整批。

**风险与回滚**：死信表膨胀。回滚 = 暂停死信写入，保留结构化日志兜底。

**前置依赖**：P2-T1（字段层）完成；P1-T1（迁移体系）。

**具体执行步骤**：

## Phase 3（健壮性与防护 · 🟡 P2）

### P3-T1【问题 J】客户端重试（tenacity）
**目标**：内部网络瞬时抖动自愈，无整批失败、无重试风暴。

**前置依赖**：无。

**具体执行步骤**：
1. `requirements.txt` 加 `tenacity` 并安装。
2. 为 `loki_client.py` / `opensearch_scap_sync.py` / `wazuh_client.py` 的 httpx 调用加 `retry(stop=stop_after_attempt(3), wait=wait_exponential, retry=retry_if_exception_type(可重试类))`；区分 5xx/超时（可重试）与 4xx（不重试）。
3. 大查询（见 P1-T3）加重试上限，防放大。

**涉及文件**：三个客户端、新增 migration 无关、新增依赖。

**验收标准**：
- [ ] 模拟源端瞬时 503，客户端自愈成功、无整批失败；
- [ ] 无重试风暴（指数退避生效）；
- [ ] 4xx 不触发重试。

**风险与回滚**：退避配置不当拖慢。回滚 = 移除装饰器恢复单次调用。

### P3-T2【问题 K】测试网补强

**涉及文件**：`tests/` 下各测试、`tests/integration/test_user_workflow.py`。

### P3-T3【问题 L】KEV ∩ 漏洞 = 0 数据探查

**风险与回滚**：探查不改生产数据，零风险；回流逻辑若开需独立评审。
