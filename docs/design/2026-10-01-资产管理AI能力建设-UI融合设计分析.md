## 0. 前稿问题与本稿方法论

**前稿（2026-10-01-资产管理AI能力建设-UI设计.md）的根本问题**：在未系统调研平台现状的情况下，把"业务系统 / 定级备案 / 数据健康 / 变更影响 / 对账闭环 / 资产图谱 / AI 资产纳管 / 任务中心 / 工作台"等约 **12 项已上线功能**当成"新建或待注册页面"平铺，等于**重复建设**。

**本稿方法论**：先盘点现状 → 每个拟建设能力锚定到现有菜单/页面 → 判定「升级已有 / 真正新增」→ 仅在确实无承接页时才新建，且新建页体量最小化。

> 平台事实：菜单由**后端 `soc_menus` 驱动**（`MenuProcessor` → `fetchGetMenuList` → `menuDataToRouter`），前端 `asyncRoutes.ts` 仅为前端模式的兜底。因此"页面是否存在"以 `views/` 磁盘文件 + `routesAlias` 别名 + 后端菜单种子三者共同判定。

### 2.1 重点澄清：资产图谱「增强」而非「新建」

现有 `asset/graph`（1152 行，代码核实）**已具备**：力导向 + 环形双布局、按业务系统/网段/重要度着色、搜索定位、点节点出详情卡（→跳资产详情）、点边看证据（置信度 % + evidence）；**边置信度三档**（≥90 实线已确认 / 60–89 实线规则归一 / <60 虚线推断）；右栏 KPI（节点 / 关系边 / **边覆盖率** / 无 agent 盲区）；以及 **「修复阻塞点 Top N」**——基于 `getVulnChokepoints` 的漏洞到关键资产**可达性计算**（已含攻击可达性雏形，但仅以列表呈现，图上不可视）。

因此本方案对图谱的「攻击路径高亮」**不是新建攻击路径引擎**，而是把已有的可达性计算结果在图上显式画成带逐跳置信度的链路（外网 → NAT → 防火墙 → 主机 → 核心库）。复用与新增边界如下：

| 维度 | 现状（已具备，保留复用） | 本方案新增（增强） |
|---|---|---|
| 布局 / 着色 / 搜索 / 详情卡 | ✅ 力导+环形、按业务/网段/重要度、点节点详情、点边证据 | — |
| 边置信度三档 | ✅ ≥90 / 60–89 / <60 三档视觉编码 | — |
| 边覆盖率 / 盲区 KPI | ✅ 已存在 | — |
| 可达性 / 攻击路径 | ⚠️ 仅有「修复阻塞点」列表（`reachableCriticalCount`），**图上不可视** | ✅ **攻击路径可视化**（逐跳高亮 + 每跳置信度） |
| 暴露面 | ❌ 图谱无暴露面表达 | ✅ 暴露面叠加层（公网 IP/端口 → 内网映射） |
| ATT&CK | ❌ 无技术映射 | ✅ ATT&CK 映射叠加层（优先并入图谱，非独立页） |
| 高置信聚焦 | ⚠️ 仅有「显示推断边」反选开关 | ✅ 「仅看 ≥0.9 已验证边」正向聚焦 |

> 结论：图谱是"关系图 + 可达性计算"已成熟的能力，本方案补齐"看得见、可解释、可叠加"的攻击路径视图，**复用现有引擎，不重复造轮子**。原型导航已将该页标为「已有·攻击路径增强」；原型图谱页副标题亦注明复用关系，供评审者一眼识别。📎 底层为底座 §3 `soc_graph` + 6 Builder，攻击路径 query `find_paths`/`vuln_chokepoints` 已存在（底座 §3 / 实施方案 §九）。

## 3. 真正需要新增的最小页面（5 个）

仅当确认**无已有页面可承接**时才新建，且体量从简：

| 新增页 | 为什么不并入已有页 | 最小形态 | 数据底座依据 |
|---|---|---|---|
| **确认工作台** | data-health 的"确认"是稽核**差异**确认，语义不同于"数据补齐**候选**确认"；独立页更易做批量确认流 | 候选列表（<0.7 置信）+ 批选确认/修正/忽略 + 写入置信度 | 写入 `soc_graph_edges` 置信度（底座 §3） |
| **数字员工工作空间** | S9 问答散落在 list、AI 洞察散落在 console，八工具无统一编排面；需聚合+证据链+采纳闭环 | 左侧工具导航 + 对话/结果区 + 证据链 + 转工单/定位图谱 | 消费既有 MCP / 图谱 query（底座 §3） |
| **本体视图** | 全平台无本体可视化（YAML 仅后端） | 本体树 + 资产↔本体对齐 + CI 校验状态 | 本体 YAML（底座未含，方案 AOG-1） |
| **暴露面分析** | 仅 `constants/criticality.ts` 有"暴露面等级(保留)"常量，无页面 | 资产/网段对外暴露面清单 + 风险标注（可后期并入 overview） | 📎 关系数据来自已建 `soc_maps_to`（底座 §2.2） |
| **ATT&CK 映射** | 无技术映射页 | 资产→ATT&CK 技术映射表 + 覆盖热力（可后期并入 graph 叠加层） | 📎 告警源为 OpenSearch（底座 §1.1 / §5 联邦查询） |

> 设计纪律：**暴露面 / ATT&CK 优先做"并入已有页的 Tab/叠加层"，仅在迭代受阻时才独立成页**，避免页爆炸。

## 4. 修订后落地清单（替代前稿 16 页平铺）

### 4.3 与 OH-UI 任务的对应（修订）
- 前稿 OH-UI.1~14 中，约 9 项实际是**升级任务**（OH-UI 重标为 `升级-X`），仅 5 项为**新建任务**（确认工作台/数字员工/本体/暴露面/ATT&CK）。
- 排序建议（成本优先）：先点亮已有孤儿页注册（若仍有未接菜单者）→ 升级 detail/business-system/compliance/data-health/graph → 再攻坚 5 个新增页。

## 5. 对原型（HTML）的修订建议
1. 导航不再平铺 16 页，改为**以现有菜单为骨架**，新增页只在现有分组下挂少量入口：
   - 资产管理分组：概览/列表/详情/图谱/业务系统/合规/数据健康/变更影响/稽核（**全部已有**，仅标注"待增强标记"）

   - 推理分析（新增组）：暴露面、**ATT&CK 映射**（攻击路径在图谱内增强）
   - 数字员工（新增组）：数字员工工作空间
   - AI 资产（并入系统管理→AI 模型管理下的"AI 资产视图"）

3. 业务系统原型改为"三维度自动建议 + 关联资产/责任人建议"的**增强示意**。
