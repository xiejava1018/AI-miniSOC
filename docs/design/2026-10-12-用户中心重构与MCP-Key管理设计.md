## 1. 背景与动机

### 1.1 问题一：MCP 接入缺乏身份凭证体系

AI-miniSOC 的 MCP Server（`:8100`，Streamable HTTP `/mcp` + SSE `/sse`，60 个 tool）当前状态：

- **传输层无鉴权**：任何能连到 8100 的客户端都可以 initialize、枚举全部 tool 清单
- **业务层凭证靠 Agent 动态配置**：`set_mcp_credentials(username, password)` 把**账号密码明文交给 Agent 侧持有**，密码暴露面大、无法单独撤销、审计只能落到"某账号"而分不清是人还是 Agent
- **无法按人授权**：腾讯 workbuddy 等通用成品 Agent 接入时，只能共用人工账号，权限边界模糊

### 1.2 问题二：个人中心名存实亡

`src/frontend/src/views/system/user-center/index.vue` 存在但：

- **无入口**：`soc_menus` 无对应菜单记录，是隐藏路由（`UserCenter = '/system/user-center'`）
- **内容是模板 demo**：假姓名、假邮箱、假标签（art-design-pro 占位），表单未接任何后端接口
- 用户无法自助维护个人资料、修改密码

### 1.3 目标

把两个问题合成一个交付：**以"用户自助 MCP Key 管理"为首个落地功能，重做个人中心为真正的独立用户自助页面**，同时补齐基本资料与修改密码能力。

## 2. 设计总览

```
                    ┌──────────────────────────────────────┐
                    │        用户中心（独立页面）            │
                    │  /system/user-center（隐藏路由）      │
                    │  入口：右上角头像下拉                  │
                    │  ┌────────┬────────┬────────┐        │
                    │  │基本资料 │安全设置 │MCP 接入 │        │
                    │  └────────┴────────┴────────┘        │
                    └───────┬──────────────────┬───────────┘
                            │ REST             │ 管理（申请/延期/注销）
                            ▼                  ▼
        ┌─ GET/PUT /api/v1/users/me ──  POST /api/v1/users/me/mcp-keys …
        │
        │  Key 使用（Agent 侧）
        ▼
┌───────────────────────────────────────────────────────────┐
│ MCP Server (:8100)                                        │
│  Authorization: Bearer sk-mcp-xxxx                        │
│    → 中间件: hash → 查 soc_mcp_keys（TTL 缓存）            │
│    → 校验 status/expires_at/user.status                   │
│    → 以绑定用户身份 mint JWT → TokenManager 注入           │
│    → 60 个 tool 按该用户角色（X1 权限矩阵）执行             │
└───────────────────────────────────────────────────────────┘
```

核心原则：**Key 是用户的第二种凭证，权限完全继承用户角色**（同 GitHub PAT / OpenAI API Key 模式）。

## 3. 数据模型

### 3.1 新表 `soc_mcp_keys`

> 不在 `soc_users` 加字段——需求（有效期/注销/重申请/多 Key 并存/审计留档）需要独立生命周期实体。

```sql
CREATE TABLE soc_mcp_keys (
    id            BIGSERIAL PRIMARY KEY,
    user_id       BIGINT NOT NULL REFERENCES soc_users(id) ON DELETE CASCADE,
    name          VARCHAR(50) NOT NULL,                    -- 用途标识："workbuddy"、"我的Claude"。**唯一性是应用层**（WHERE user_id=? AND name=? AND status='active'），DB 不加 UNIQUE 以允许"注销后同名重新申请"
    key_prefix    VARCHAR(16) NOT NULL,                    -- 明文前缀 sk-mcp-ab12（列表辨认用），实际存 11 字符（"sk-mcp-" 7 + 4 位）
    key_hash      VARCHAR(255) NOT NULL UNIQUE,            -- SHA-256 hex 定长 64 字符（VARCHAR(255) 留余量），永不存明文
    status        VARCHAR(20) NOT NULL DEFAULT 'active',   -- active / revoked（过期为运行时判定，不落库）
    expires_at    TIMESTAMPTZ NOT NULL,
    last_used_at  TIMESTAMPTZ,                             -- Key 最后被 MCP 中间件使用的时间
    revoked_at    TIMESTAMPTZ,
    revoke_reason VARCHAR(100),                            -- user_revoked / admin_revoked / superseded(同名旧 Key 被新 Key 替换)
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()       -- 任意列 UPDATE 时刷新（含 last_used_at 异步写回）
);

CREATE INDEX idx_soc_mcp_keys_user   ON soc_mcp_keys(user_id);
CREATE INDEX idx_soc_mcp_keys_hash   ON soc_mcp_keys(key_hash);
-- 应用层唯一性索引（active 状态内 name 唯一）：
-- CREATE UNIQUE INDEX uq_soc_mcp_keys_user_active_name ON soc_mcp_keys(user_id, name) WHERE status = 'active';
-- （可选 partial unique index；PostgreSQL 支持；如不实现则由 service 层 SELECT 校验）
```

设计决策：

| 决策 | 理由 |
|---|---|
| **过期不落库状态列**（expired 是运行时判定 `now() > expires_at`） | 避免"过期清理定时任务"；列表展示时实时计算"剩余天数"即可 |
| **注销/过期是终态，不复用记录** | 注销的 Key 即使 DB 记录还在也永远失效；重新申请 = 新记录；历史留档满足审计 |
| **`ON DELETE CASCADE`** | 删除用户自动清 Key，无孤儿凭证 |
| **`key_hash` 唯一索引** | 天然防重复；查询走索引 |
| **沿用 scanner_agents 的 `api_key_hash` 模式** | 项目内已有先例（`soc_scan_agents.api_key_hash`），保持一致 |

### 3.2 Key 格式与生成

```
sk-mcp- + 32 字节 secrets.token_urlsafe → 全长约 47 字符
示例: sk-mcp-Xk9f2mQ8vLp3nR7wYtN4bJ6hZcA1eD5u
```

- 前缀 `sk-mcp-`：便于日志/告警系统识别凭证类型（secret scanning 友好）
- `key_prefix` 存明文前 11 字符（`sk-mcp-` + 4 位），列表展示 `sk-mcp-ab12…`
- 生成时**明文只返回一次**（响应体），之后任何接口不可再取

### 3.3 配置中心项（复用 system_configs）

| 配置键 | 默认值 | 说明 |
|---|---|---|
| `mcp.auth.required` | `false` | MCP 传输层是否强制要求 Bearer Key。**生产 v1 后期手动置 `true`**；本地 dev 默认 false 免打扰。切换不用改代码 |
| `mcp.key.max_per_user` | 5 | 每用户 active Key 上限 |
| `mcp.key.max_validity_days` | 365 | 有效期上限（天） |
| `mcp.key.min_validity_days` | 1 | 有效期下限（天） |
| `mcp.key.cache_ttl_seconds` | 60 | Key 缓存 TTL。注销/用户禁用同时清缓存**主动失效**（TTL 兜底） |
| `mcp.key.failure_lock_threshold` | 10 | 连续校验失败锁定阈值。**按 IP 维度**，**与登录失败计数（按 username 维度）独立，不复用** |
| `mcp.key.failure_lock_minutes` | 15 | 锁定时长 |

一个 alembic 迁移：建表 + 索引 + 配置种子（JOIN `soc_system_configs` 结构插入默认项，**遵守 §4.3 红线：不硬编码 id、用 `bind.execute` 带参数**）。挂在当前单 head 下游。

## 4. 后端 API 设计

### 4.1 端点清单

#### 自助端点（`/api/v1/users/me/*`，登录即可用，任何角色）

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| GET | `/users/me` | 我的基本资料。与 `auth.py` 的 `GET /auth/me` **并存**：前端个人中心调 `/users/me`（向下兼容并返回完整字段 phone/email/department/role/last_login）；其他场景前端仍可调 `/auth/me`。两个端点内部**共用同一查询逻辑**，service 层抽到 `app/services/user_profile.py` | JWT |
| PUT | `/users/me` | 修改自己的可编辑字段（nick_name / phone / email / avatar / gender）；被拒绝字段（username/role_id/department_id/status/is_superuser）→ `code=422` + 错误 detail 指明哪几个字段被拒绝 | JWT |
| POST | `/users/me/change-password` | 修改自己密码（需旧密码验证） | JWT |
| GET | `/users/me/mcp-keys` | 我的 Key 列表（含状态/到期/最后使用） | JWT |
| POST | `/users/me/mcp-keys` | 申请新 Key `{name, validity_days}` → 返回一次性明文。**viewer / auditor 角色调此端点 → `code=403`**（见 §7） | JWT |
| POST | `/users/me/mcp-keys/{id}/extend` | 延期 `{new_validity_days}`（仅 active 可延期） | JWT |
| DELETE | `/users/me/mcp-keys/{id}` | 注销自己的 Key（同步清缓存，即时生效；生效语义见 §5.2） | JWT |

#### 管理端点（`/api/v1/users/{user_id}/mcp-keys`，admin only）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/users/{user_id}/mcp-keys` | 查看指定用户 Key 列表（**只读**，看不到明文） |
| POST | `/users/{user_id}/mcp-keys` | **admin 代发**（viewer/auditor 无自助权时由此代发；响应明文仅 admin 转交用户，不落库不落日志） |
| DELETE | `/users/{user_id}/mcp-keys/{id}` | 强制注销（`revoke_reason='admin_revoked'`） |

全部走 `@log_audit` 落审计 hash 链（动作：`mcp_key.create / extend / revoke / admin_revoke`，审计 detail 记 key_prefix 便于追溯）。

### 4.2 请求/响应示例

```jsonc
// POST /users/me/mcp-keys  { "name": "workbuddy", "validity_days": 90 }
// → HTTP 200 envelope {code:200, data:{...}}
{
  "id": 1,
  "name": "workbuddy",
  "key": "sk-mcp-Xk9f2mQ8vLp3nR7wYtN4bJ6hZcA1eD5u",   // ⚠️ 唯一一次出现
  "key_prefix": "sk-mcp-Xk9f",
  "expires_at": "2027-01-10T00:00:00Z",
  "created_at": "2026-10-12T00:00:00Z"
}

// GET /users/me/mcp-keys → data: [ ... ]  （无 key 字段）
{
  "id": 1, "name": "workbuddy", "key_prefix": "sk-mcp-Xk9f",
  "status": "active", "days_remaining": 89,
  "last_used_at": "2026-10-12T08:00:00Z",
  "expires_at": "2027-01-10T00:00:00Z"
}
```

### 4.3 校验规则

- `name`：1-50 字符，同用户下唯一（active 状态中）。**应用层校验**（DB 无 UNIQUE），允许"注销后同名重新申请"——注销状态行不参与唯一性判定
- `validity_days`：`min_validity_days ≤ v ≤ max_validity_days`（配置中心）
- active Key 数达 `max_per_user` → `code=409` `已达上限，请先注销不用的 Key`
- `PUT /users/me` **不可改** username / role_id / department_id / status / is_superuser（服务端白名单过滤）；被拒字段 → `code=422` + 错误 detail 指明哪几个字段
- `change-password`：
  - **旧密码错误** → `code=401`（鉴权失败，**不是**数据校验）；复用登录失败计数（按 username 维度，连续错 5 次锁 15 分钟，与登录共用锁机制）
  - **新密码强度不够**（如 `<6` 位 / 不满足复杂度正则）→ `code=422`（数据校验）
  - **审计**：成功 → `password.change.success`；失败 → `password.change.fail`（含 username + 源 IP，落 `soc_audit_logs` hash 链；用于检测改密码爆破）

## 5. MCP 侧 Key 校验链路

### 5.1 中间件流程（`app/mcp/server.py` 组合 Starlette app 外层）

```
请求: Authorization: Bearer sk-mcp-xxxx
  │
  ├─ 无 Authorization 头？
  │    → 兼容模式：放行，维持 set_mcp_credentials 现状（过渡期并存，见 §5.3）
  │
  ├─ 带 Bearer → SHA-256(key)
  │    → 查 soc_mcp_keys（内存缓存: key_hash → {user_id, expires_at, status}，TTL 60s）
  │    → 未命中 / status=revoked / now≥expires_at → 401 + {"error":"key_invalid|key_revoked|key_expired"}
  │    → 命中 → 再查 soc_users（同缓存条目内联 user.status）
  │         → user.status != active → 401 {"error":"user_disabled"}
  │
  ├─ 通过 → 服务端直接以该用户身份 mint JWT（免密签发，权限子集见 §5.2）
  │         → 注入 TokenManager（优先级高于 set_mcp_credentials 的会话凭证）
  │         → 异步更新 last_used_at（fire-and-forget，不阻塞请求）
  │
  └─ 失败计数：按来源 IP（**与登录失败计数独立**——登录按 username + 5 次阈值 + 15 分钟锁；MCP 按 IP + 10 次阈值 + 15 分钟锁，两套计数器不互通），超阈值 → 429 锁定（配置中心项）
```

**缓存失效范围约定**：

| 触发事件 | 失效范围 |
|---|---|
| 单 Key 注销（`DELETE /users/me/mcp-keys/{id}`） | 清该 `key_hash` 的缓存条目 |
| 单 Key 延期（`POST .../extend`） | 清该 `key_hash` 的缓存条目（expires_at 变了） |
| 用户被禁用（`soc_users.status != active`） | **清该 user_id 名下所有 Key 缓存条目**（避免遍历 Key 缓存按 `key_hash` 反查归属）。实现：维护 `user_id → [key_hash]` 辅助索引，或按 user_id DB 反查批量删 |
| admin 强制注销他人 Key | 同上（同步清被影响用户的所有 Key 缓存） |
| 用户改密码 / 被 admin 删除用户 | 失效 + 走 §5.2 的 JWT 黑名单联动 |

TTL `mcp.key.cache_ttl_seconds`（默认 60s）兜底——即便主动失效漏掉，60s 内全局一致。

### 5.2 免密签发的权限边界

服务端 mint JWT 时**不需要密码**（等价于 password grant 之后的 token），权限完全等于该用户正常登录：

- 角色/端点权限照常走 X1（tool 内部调后端 API 时带此 JWT）
- `get_current_user` 类 tool 返回绑定用户 → Agent 能感知"我是谁"
- 审计链记录 `operator=用户名`，MCP 来源通过审计 detail 的 `via=mcp_key(sk-mcp-Xk9f)` 区分人工操作

**⚠️ Key 撤销的生效语义（v1.2 修正）**：

- MCP mint 的 JWT **仅在服务端内部使用**（TokenManager 签发后注入 tool 调用，Agent 侧拿不到），因此不存在"Key 已注销但 JWT 还能用"的窗口——每个 MCP 请求都重新过 Key 校验中间件，注销时同步清缓存 → 下一请求立即 401
- **不新增"按 user_id 撤销全部 JWT"的黑名单联动**（现有黑名单是 per-jti 原语，单 Key 注销也不应踢掉用户人工登录会话）
- 全局事件（用户禁用/删除）的处置：清 user_id 名下全部 Key 缓存（MCP 侧断）+ 登录态由各端点现行的 user.status 校验兑杀（人工会话断），两层各自生效
- access_token 有效期 2 小时（`ACCESS_TOKEN_EXPIRE_MINUTES=120`），仅作为上述机制的背景参数，无需特殊处理

### 5.3 兼容与迁移策略

| 阶段 | 行为 |
|---|---|
| v1 上线 | 无 Bearer 头 → 维持现状（免鉴权连入 + `set_mcp_credentials`）；带 Bearer → Key 即身份 |
| 观察期后（配置中心开关 `mcp.auth.required=true`） | 无有效 Key 一律 401，`set_mcp_credentials` 废弃 |
| 生产默认 | **`required=true`**（部署时配置中心置位）；本地 dev 默认 false 免打扰 |

> 该开关让"本地开发裸连"与"生产强制 Key"两个诉求共存，且切换不用改代码。

### 5.4 性能

- 缓存命中 → 0 次 DB 查询；未命中 → 1 次（`key_hash` 唯一索引点查）
- 远端 dev 库 RTT ~90ms：TTL 60s 缓存后可忽略；Key 注销/用户禁用后**最迟 60s 内全局失效**（主动失效：注销/禁用写操作同时清缓存）

### 6.1 入口（不进菜单树）

### 6.4 Tab2 安全设置

1. **修改密码**：旧密码 + 新密码 + 确认新密码；校验规则对齐后端（≥6 位）；成功后**强制登出跳登录页**（旧 JWT 已随密码变更失效策略——与现有 logout 黑名单机制联动）
2. **登录安全信息**（只读展示）：最后登录时间 / 当前会话 token 到期时间（来自 store），帮助用户感知会话状态
3. 会话管理（在线设备列表/远程下线）：**本期不做**，留扩展位（见 §10 非目标）


交互细节：

| 交互 | 设计 |
|---|---|
| **申请新 Key** | 弹窗：名称 + 有效期（下拉 7/30/90/365/自定义天数控 max_validity_days）→ 提交 → 结果弹窗展示**一次性明文** + 复制按钮 + 大字提醒"关闭后无法再次查看" |
| **接入示例** | 弹窗展示各 Agent 配置片段（自动填入用户自己的 Key 前缀提示 + 服务地址）：workbuddy JSON（`~/.workbuddy/mcp.json` 格式）/ Claude Code 命令 / Cursor JSON，Tab 切换 + 一键复制 |
| **延期** | 弹窗输入新有效期（≤上限），仅 active 可延期；过期 Key 显示"重新申请"（同名新建） |
| **注销** | 二次确认（输入 Key 名称或前缀确认，防误触）；注销即刻生效（清缓存） |
| **状态标识** | 🟢 active（含剩余天数，≤7 天变黄提前预警）/ ⚪ 已过期 / 🔴 已注销 |

组件规范：列表用 `ArtTable`/卡片列表（3 条以内用卡片更合适），弹窗复用 `ArtSearchBar` 风格的表单校验；对齐 `views/system/role/index.vue` 基准。

## 7. 权限矩阵（对齐 X1）

| 操作 | 本人 | admin | operator | viewer/auditor |
|---|---|---|---|---|
| 查看 / 编辑自己的基本资料 | ✅ | — | ✅（自己的） | ✅（自己的） |
| 修改自己的密码 | ✅ | — | ✅（自己的） | ✅（自己的） |
| 查看自己的 Key 列表 | ✅ | — | ✅（自己的） | ✅（自己的） |
| 申请 / 延期 / 注销自己的 Key | ✅ | — | ✅（自己的） | ❌（审计/只读角色不应自助申请 MCP 接入，需 admin 代发；MCP 主要给 operator / 普通用户执行任务用） |
| 查看他人 Key 列表 | ❌ | ✅ | ❌ | ❌ |
| 强制注销他人 Key | ❌ | ✅ | ❌ | ❌ |
| MCP 传输层用 Key 调 tool | ✅（权限=本人角色） | ✅ | ✅（权限=本人角色） | ✅（权限=本人角色，但本身被禁止申请 Key） |

**实现细节**：

- `/users/me/*` 端点用 `get_current_user` 依赖（任何登录角色），但在 `POST /users/me/mcp-keys`、`POST .../{id}/extend`、`DELETE .../{id}` 三个写端点上**额外加角色白名单**——服务端在写入前校验 `current_user.role.code not in ('viewer', 'auditor')` → `code=403` `审计/只读角色不可自助申请 MCP Key`（admin bypass 不影响）
- `/users/{id}/mcp-keys` 用 `require_role("admin")`（`app/core/permissions.py:94`）
- 审计 detail 记录 `via_role=<code>` + `via_endpoint=<path>`，便于后续按角色维度的合规审计
- viewer / auditor 想接入 MCP（虽然罕见）：走"admin 代发"流程 —— admin 用 admin 端点 `POST /users/{user_id}/mcp-keys` 代为申请，详情见 §6.6

## 8. 安全设计清单

| 威胁 | 对策 |
|---|---|
| 拖库后 Key 泄露 | 只存 SHA-256，无明文；key_prefix 仅 4 位不足以暴力还原 |
| Key 在传输中被窃听 | 生产强制 HTTPS（nginx 反代 TLS；本地 http 可接受） |
| Key 爆破 | 失败计数按 IP + 阈值锁定（配置中心）；Key 熵 32 字节不可枚举 |
| 明文 Key 泄露在日志/审计 | 审计只记 `key_prefix`；API 响应体一次性返回明文后，任何日志/接口不再出现 |
| 离职/权限变更后 Agent 仍可用 | 禁用用户 → 缓存主动失效 → 60s 内全断；改角色 → 权限实时跟随 |
| admin 滥用他人 Key | 不可能——admin 只能注销不能查看明文 |
| XSS 偷 Key | 明文只在生成瞬间存在于一次性弹窗，不入 store、不落 localStorage |
