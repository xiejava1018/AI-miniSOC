## 1. TL;DR（给决策者）

后台任务分**两类**，可见性天差地别：

| 类别 | 数量 | 当前能否看到执行情况 | 结论 |
|---|---|---|---|
| **周期调度任务**（lifespan 启动的后台 asyncio task / 线程） | **5 个** | ❌ 几乎完全不能 | **盲跑**：失败只进 stdout、无持久记录、3/5 无 Prometheus 指标、内存态重启清零、`/health` 写死 healthy |
| **用户触发异步任务**（资产同步 / 漏洞扫描 / AI 研判） | **3+ 类** | ⚠️ 部分能（状态在各自表，但分散、无统一视图、无失败告警） | 有状态表但**没有"任务中心"** |

**v0.3 相对 v0.1/v0.2 的核心改进**：
- **拆表根治单表矛盾**（`soc_task_registry` 当前态 + `soc_task_runs` 真历史）
- **僵尸/卡死检测**（双重超时：`started_at` + `last_progress_at` 都超 `timeout_s` 才判定）
- **超时实际执行**（`asyncio.wait_for` 协程自动取消；线程不杀靠 daemon）
- **复用 P4 已落地的 `single_worker_guard` / `soc_source_health` / `sync_dead_letter`**，不重复造轮子
- **通知通道定 default**（`NotificationService` 实时 + `AlertDigestService` 日报兜底）
- **可视化分两档**（Grafana Tier 0 零前端止血 → Vue Tier 1 任务中心）
- **手动操作有审计**（reason 强制填 + `soc_audit_logs`）

## 3. v0.3 完善设计

### 3.1 两张表（根治单表矛盾）

#### `soc_task_registry` —— 每任务一行（定义 + 当前态）

```text
soc_task_registry
  task_key            VARCHAR  PK          e.g. 'browsing_detector'
  task_name           VARCHAR              展示名
  task_type           VARCHAR              scheduled | async | thread
  owner_module        VARCHAR              来源模块
  schedule_expr       VARCHAR  nullable    '*/5m' | '0 8 * * *' | '60s'（async 类型可空）
  expected_interval_s INT  nullable        用于新鲜度计算（async 类型可空：用户触发型不查新鲜度）
  timeout_s           INT                  用于僵尸检测的硬超时
  enabled             BOOLEAN  default true
  current_run_id      VARCHAR  nullable    在跑的 run 行 id（应用层维护，不建 FK）
  lock_owner          VARCHAR  nullable    当前持锁 worker/pod 名（多 pod 调试用）
  last_run_at         TIMESTAMPTZ
  last_status         VARCHAR              success|running|failed|skipped|zombie|timeout|unknown
  last_error          TEXT
  last_duration_ms    INT
  last_stats          JSONB                本轮业务统计
  consecutive_failures INT  default 0
  total_runs          INT   default 0
  last_progress_at    TIMESTAMPTZ  nullable  最近一次进度更新（progress=True 任务用）
  created_at          TIMESTAMPTZ
  updated_at          TIMESTAMPTZ
```

**关键字段说明**：
- `timeout_s`：单轮允许最大时长；协程型任务装饰器据此 `asyncio.wait_for` 主动取消，线程型任务不取消仅事后判定
- `last_progress_at`：进度心跳；与 `started_at` 配合做**双重超时判定**（详见 §3.2）
- `lock_owner`：多 pod 调试时知道哪个 worker 在跑；持锁失败时记录"被谁持有"
- `current_run_id`：UI 展示"现在跑的是哪一轮"；不建 FK（避免跨表锁）

#### `soc_task_runs` —— 每执行一行（**真历史**）

```text
soc_task_runs
  id              VARCHAR  PK          uuid
  task_key        VARCHAR  NOT NULL   应用层 FK→registry.task_key（ON DELETE SET NULL：软删除兼容）
  trigger         VARCHAR              scheduled | manual | api | replay
  started_at      TIMESTAMPTZ
  finished_at     TIMESTAMPTZ nullable
  status          VARCHAR              running | success | failed | skipped | zombie | timeout
  duration_ms     INT
  error_text      TEXT
  stats_json      JSONB               业务统计
  total           INT  nullable       异步任务进度（总量）
  processed       INT  nullable       已处理
  percent         INT  nullable       完成百分比
  correlation_id  VARCHAR nullable    关联 API 请求 / sync_tasks 行（软引用，不强制 FK）
  host            VARCHAR nullable    pod/host 标识
  triggered_by_user VARCHAR nullable  手动触发时的用户 id
  created_at      TIMESTAMPTZ  default now()
索引：
  (task_key, started_at DESC)         主要查询路径
  (status, started_at)                僵尸扫描路径（partial index where status='running'）
  (correlation_id)                    跨系统关联（API 请求/同步任务）
```

> 借鉴 `soc_sync_tasks`（pending/running/completed/failed + error_message + started/completed_at 状态机），但做成横切统一表；`registry` 存当前态、`runs` 存历史，职责分离。
> **v0.3 修正**：任务删除采用 **soft delete**（`enabled=false` + `task_key` 保留），runs 历史不被级联删除（`ON DELETE SET NULL` 或干脆不建 FK）。

### 3.2 复用 `single_worker_guard` 做运行锁 + 僵尸看门狗

#### 运行锁（防重叠）

- 每次调度 tick 先 `try_acquire_scheduler_lease(owner=task_key, ttl=timeout_s)`；拿不到（上一轮仍活着）→ 跳过本轮并记 `skipped`。
- 仅对 `scheduled` / `thread` 单例任务加锁；`async` 用户触发型每请求是独立 run，不加锁。
- 持锁成功后写 `soc_task_registry.lock_owner = f"{host}:{pid}"`。

#### 僵尸看门狗（双重超时判定，**v0.3 核心改进**）

**v0.2 问题**：仅看 `started_at + timeout_s`，长任务假阳性（合法 2h 同步被误判）。

**v0.3 方案**：要求 `started_at` 和 `last_progress_at` **两者都**超时：

```python
# 伪代码
def find_zombies():
    return db.query(SocTaskRuns).filter(
        SocTaskRuns.status == 'running',
        or_(
            # case A: 无进度跟踪的任务
            and_(
                not_(SocTaskRegistry.last_progress_at.isnot(None)),
                SocTaskRuns.started_at < now() - timeout_s,
            ),
            # case B: 有进度跟踪的任务 - 必须进度也停了
            and_(
                SocTaskRegistry.last_progress_at.isnot(None),
                SocTaskRegistry.last_progress_at < now() - timeout_s,
                SocTaskRuns.started_at < now() - 2 * timeout_s,  # 启动超时更宽松
            ),
        )
    )
```

- 扫到的行标 `status='zombie'` + 写 registry `last_status='zombie'` + 触发实时告警。
- `progress=True` 的长任务（如大批量 OS 同步）只要还在 `processed/total/percent` 推进，**不会被误杀**。
- **不**试图中断 Python 线程（不可行）；线程型任务的 zombie 仅事后记录 + 告警。

#### 启动对账（lifespan 内）

进程启动时：
```sql
UPDATE soc_task_runs SET status='unknown', finished_at=now() 
WHERE status='running';
UPDATE soc_task_registry SET 
  current_run_id=NULL, 
  last_status='unknown',
  lock_owner=NULL
WHERE last_status='running';
```

> 上一进程遗留的 running 必是假活（进程都死了，run 不可能还活着）。

### 3.3 复用 `soc_source_health`（已建）做数据新鲜度

一个调度任务跑完，除写 runs/registry，也调 `SourceHealthRecorder.record_success(source_key, source_type, records=...)`。`soc_source_health` 已记 `last_success_at` + `is_healthy(×2 阈值)`。

**视角互补而非重复**：
- `registry/runs` 看"任务活没活"（**执行层面**）
- `soc_source_health` 看"数据鲜不鲜"（**数据层面**）

例：`browsing_detector` 任务成功但 Loki 拉到 0 条 → 任务视角 healthy、数据视角 stale——两层信号都要。

### 3.4 `track_task()` 埋点契约（v0.3 增强：硬超时 + 进度心跳 + 优雅降级 + 手动触发审计）

#### 装饰器形态

```python
# 协程型（周期任务）
@track_task(
    task_key="browsing_detector",
    task_type="scheduled",
    timeout_s=360,
    hard_timeout=True,        # v0.3 新增：包 asyncio.wait_for 主动取消
    source_key="loki_browsing",  # 可选：成功后调 source_health.record_success
    progress=False,           # 长任务开启，进度心跳
)
async def _run_detection(...): ...

# 线程型（v0.3 新增范式：每 tick 一次 with 上下文管理器）
def _mcp_refresher_loop(stop_event):
    while not stop_event.is_set():
        with track_task(        # v0.3 定方案 1：每 tick 一次 run
            task_key="mcp_token_refresher",
            task_type="thread",
            timeout_s=120,
        ) as ctx:
            try:
                refresh_token()
                ctx.success(stats={"tokens_refreshed": 1})
            except Exception as e:
                ctx.fail(error=e)
        stop_event.wait(60)

# 用户异步任务（async 类型）
@track_task(task_key="asset_sync", task_type="async", timeout_s=1800, progress=True)
async def sync_assets(...): ...
```

#### v0.3 四条契约（相对 v0.2 强化）

1. **自动注册**：首次 track 自动 upsert `registry` 行（开发者忘加也不会漏监控）。
2. **双上下文**：同一包装在 asyncio 协程（周期任务）和线程（MCP token 刷新）中都能用（内部按上下文选 sync/async DB 调用）。
3. **优雅降级**：埋点自身所有 DB 写入包 `try/except` 吞掉，**绝不让监控把真实任务搞挂**。
4. **硬超时（v0.3 新增）**：`hard_timeout=True`（默认）时，协程场景用 `asyncio.wait_for(body, timeout=timeout_s)`：
   - 真超时（任务还在跑）→ 取消 + run.status='timeout' + registry.last_status='timeout' + 实时告警
   - 假超时（实际超时内有进度更新）→ 看门狗放过，**不**误报
   - 线程场景：`hard_timeout` **不生效**（Python 无法中断线程），靠 daemon + 僵尸看门狗兜底

5. **进度心跳（v0.3 新增）**：`progress=True` 时长任务在循环里调 `ctx.update_progress(processed=N, total=M)`，装饰器同时更新：
   - `soc_task_runs.processed/total/percent`（本轮）
   - `soc_task_registry.last_progress_at`（用于双重超时判定）

#### 执行流

```
拿锁（single_worker_guard） → 插 run(status=running, 设 registry.current_run_id+lock_owner）
  → 跑 body（asyncio.wait_for 包裹，硬超时自动取消）
    → 成功：run.success + registry(last_run_at=now, last_status=success, 
        consecutive_failures=0, total_runs+=1, last_stats) 
        + （若 source_key）source_health.record_success
    → 失败：run.failed+error + registry(consecutive_failures+=1, last_error) 
        + 失败 Counter + 若 consecutive_failures≥N → 实时告警 + 死信
    → 超时：run.timeout + registry.last_status='timeout' + 实时告警
    → skipped：拿不到锁 → run.skipped（不进总统计）
  → finally：释放锁、清 current_run_id 和 lock_owner；确保 run 行关闭
```

### 3.5 指标从"计数"升级为"可告警"

在 `browsing_detection/scheduler.py:30-35` 的 Counter 范式基础上，推广为覆盖**全部任务**的 Gauge/Counter（注册到已挂的 `/metrics`）：

| 指标 | 类型 | 标签 | 用途 |
|---|---|---|---|
| `task_staleness_seconds{task_key}` | Gauge | task_key | **关键**：Grafana 告警规则 threshold |
| `task_consecutive_failures{task_key}` | Gauge | task_key | 连续失败数 |
| `task_last_duration_seconds{task_key}` | Gauge | task_key | 最近一轮耗时（粗粒度） |
| `task_runs_total{task_key,status}` | Counter | task_key, status | 累计轮次（success/failed/timeout/zombie/skipped） |
| `task_zombie_total{task_key}` | Counter | task_key | 僵尸触发次数（仅看门狗） |

> **v0.3 决策**：**不**用 Histogram（v0.2 评审建议），改用 `soc_task_runs.duration_ms` DB 查询——周期任务一天 < 300 次，低频场景 DB 查询更灵活；高频分析（如果将来有）再补 Histogram。
> **label 维度**：`task_key` 受控（枚举值），`status` 也是闭集（success/failed/timeout/zombie/skipped），cardinality 安全。

### 3.7 真实健康检查 + 启动对账

`GET /health`（`main.py:134`）升级：

```json
{
  "status": "healthy | degraded | down",
  "checks": {
    "stale_tasks": [
      {
        "task_key": "cisa_kev",
        "last_success_at": "2026-08-15T10:00:00Z",
        "stale_seconds": 90000,
        "expected_interval_s": 86400
      }
    ],
    "zombies": [
      {
        "task_key": "browsing_detector",
        "run_id": "uuid-xxx",
        "started_at": "2026-08-16T08:00:00Z",

    ],
    "locked_tasks": [
      {"task_key": "mcp_token_refresher", "lock_owner": "pod-1:12345"}
```

**判定规则**：
- 任一 `enabled` 任务 `now - last_success_at > 2×expected_interval_s` → `degraded` 并列出

- 多个 zombie 同时出现 → `down`
- 启动对账：lifespan 内必须先完成残留 running → unknown 的清理，再开始 health check

Docker healthcheck / LB 才真有用。

### 3.9 手动操作审计（v0.3 新增）

`POST /api/v1/tasks/executions/{key}/trigger` 和 `/toggle` 必须写审计：

```python
# 伪代码
@router.post("/{key}/trigger")
def trigger_task(key: str, reason: str, current_user: User = Depends(require_auth)):
    require_menu_permission(current_user, "task:trigger")
    if not reason or len(reason.strip()) < 3:
        raise HTTPException(400, "reason required (min 3 chars)")
    
    # 同步触发（不开新线程，简化追踪）
    run_id = start_task(key, trigger="manual", triggered_by=current_user.id)
    
    # 写审计
    audit_log(
        action="task.trigger",
        resource=key,
        user_id=current_user.id,
        details={"reason": reason, "run_id": run_id},
    )
    return {"run_id": run_id, "status": "running"}
```

- UI 弹窗强制填 reason（min 3 字符）
- 权限粒度到按钮：`task:trigger` / `task:toggle`（用现有菜单 `permissions` JSONB 范式）
- 触发/禁用都查 `soc_audit_logs` 可见

## 6. 验收指标

| 类别 | 指标 | 测量方式 |
|---|---|---|
| 轮内失败检测 | 任一周期任务失败 → **30s 内** `soc_task_runs` 出现 `failed` 行 + registry `consecutive_failures` +1 | 注入故障 → 查 DB 时间戳 |
| 僵尸检测 | 某任务启动后崩溃（running 永不结束）→ 看门狗在 `2×timeout_s` 内将其标 `zombie` 并通过 NotificationService 实时推送 | kill -9 进程 → 验证 NotificationService 收到 alert |
| 假阳性避免 | 长任务有进度更新 → 不被误判 zombie（`last_progress_at` 在 `timeout_s` 内） | 跑 progress=True 任务，验证不触发 alert |
| 健康检查 | `/health` 在某调度器停跑 `2×expected_interval_s` 后返回 `degraded`（而非恒 healthy），并列出失活任务 | 手动 disable 任务 → curl /health |
| 启动对账 | 进程重启后状态从 DB 读取（不依赖内存态），历史不丢；遗留 running 行被标 `unknown` | 启动后查 soc_task_runs WHERE status='unknown' |
| 可视化 | Grafana 看板（Tier 0）能展示全部任务的新鲜度/失败率/时长/僵尸数 | curl /metrics 验证 5 个指标 |
| 通知 | NotificationService 收到 `task_deadman_alert` 类型消息 | WebSocket 客户端收到推送 |
| 审计 | 手动 trigger/toggle 写 `soc_audit_logs`，含 `reason` 字段 | 调 API → 查 audit_logs 表 |
| Tier 1 | （Phase 3 后）任务中心页能列出全部后台任务及其实时状态/最近错误/运行历史 | 浏览器访问 |
