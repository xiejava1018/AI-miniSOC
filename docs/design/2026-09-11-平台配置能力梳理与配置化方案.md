## 0. 一句话结论

平台目前是**"三套配置体系并存 + 一批幽灵配置"**的状态：数据库里已有可用的运行时配置表（`soc_system_config`，覆盖 8 个业务域），但**所有外部系统对接参数（Wazuh / OpenSearch / Loki / AI 模型）仍锁死在 `.env` 里，改一次要重启后端**；采集器配置散落在服务器上的 YAML 文件里；而 `.env` 中约 20 个键（邮件/钉钉/微信/Redis/Grafana/数据保留）**代码从未消费，是"看起来能配、实际无效"的假配置**。

**建议做的不是"再加一个配置页面"，而是把配置分成 4 层、统一入口、统一生效语义，并优先补齐"数据源对接（Wazuh/Loki/OpenSearch）"这一层——这是当前 ROI 最高、也是用户点名的痛点。**

## 1. 现状盘点：平台到底有哪些"配置"

### 1.1 配置资产分层全景 【代码核实】

| 层 | 载体 | 改配置的代价 | 现状包含的内容 | 是否需重启 |
|---|---|---|---|---|
| **L0 代码常量** | `.py` 文件内的常量 | 改代码 + 发版 | AI 预算（QPS=2、日上限 500、熔断阈值）、扫描 watchdog 超时（6h/90min）、快照周期（6h）、部分调度间隔 | 是 |
| **L1 进程环境变量** | `src/backend/.env` → `Settings` 类 | 改文件 + **重启后端** | DB 连接、Wazuh API、OpenSearch、Loki、GLM（key/model/base）、JWT/加密密钥、CORS、Collector API Key、Webhook 密钥与 IP 白名单、KEV 情报源 URL、调度开关与周期、Claude CLI | 是 |
| **L2 数据库运行时配置** | `soc_system_config` 表（category/key/value） | 界面改，**60s 内生效** | 已落 8 个域（见 1.2） | 否（60s 缓存） |
| **L3 采集器侧配置** | `src/collectors/{tplink,wazuh,scanner}/config.yaml` + `.env` | SSH 上服务器改文件 + **重启容器** | miniSOC 地址与 API Key、路由器地址/账号、采集类型与间隔、扫描目标与超时 | 是（远端） |
| **L4 幽灵配置** | `.env` 中**存在但代码不消费**的键 | 改了也没用 | 见 1.3 | —— |

`soc_system_config` 表结构：`category / key / value / value_type / is_encrypted / description / updated_by`。已有完整 CRUD API（`GET /api/v1/system-configs/...`）与前端页面 `views/system/config/index.vue`。

| category | 承载内容 | 消费方 | 备注 |
|---|---|---|---|
| `browsing_detection` | 18 个键：开关、检测间隔、评分阈值、严重级分界、夜间时段、隧道关键词、黑白名单域名、抑制时长、启用规则 R1-R6 | `browsing_detection/config.py` | **做得最规范的一个**：默认值自注册 + 60s 缓存 + 强类型 dataclass |
| `alert_governance` | `triage_top_n`、`suppress_rule_ids`、`min_group_count` | `alert_governance_config.py` | 缺失自动补默认行 |

> **产品判断**：L2 的**机制是好的**（表 + 缓存 + 默认值自注册），问题出在**覆盖面**——它目前只装了"业务策略/阈值"，没装"对接参数"。

以下键在 `.env` 中存在，但 `app/core/config.py` 的 `Settings` 类**没有对应字段**，且全仓检索不到消费方：

| `DINGTALK_WEBHOOK/SECRET` | 已填 | **未实现** |
| `WECHAT_WEBHOOK` | 已填 | **未实现** |
| `ALERT_EMAIL_ENABLED` / `ALERT_DINGTALK_ENABLED` / `ALERT_WECHAT_ENABLED` | true/true/false | **未实现** |
| `REDIS_HOST/PORT/PASSWORD` | redis:6379 | **未接入**（代码无 Redis 依赖） |
| `GRAFANA_URL` / `GRAFANA_ADMIN_PASSWORD` | 192.168.0.30:3000 | **无代码消费** |

### 1.4 关键缺口 【代码核实】

| 缺口 | 证据 | 影响 |
|---|---|---|
| **没有"数据源"实体** | `soc_source_health` 表只存健康状态与统计，**无连接配置**；Wazuh 参数只能从 `settings` 读 | 无法在界面上管理"接了哪些数据源" |
| **采集器无远程配置** | `tplink/config.yaml`、`wazuh/config.yaml`、`.env` 散落，靠 SSH 改 + 重启容器 | 加一个采集器 = 一次运维工单 |
| **无连接测试能力** | 全仓无 "test_connection" 类接口 | 配错了只能等数据不来才发现 |
| **无配置变更审计/回滚** | `SystemConfig` 只有 `updated_by`，无版本历史 | 改坏了无法追溯与回滚 |
| **无 schema 校验** | 前端是通用 KV 编辑器，值类型靠手选，无格式/范围校验 | 填错值静默降级为默认值 |
| **AI 预算硬编码** | `ai_budget.py` 注释自述"MVP 硬编码，后续可接 soc_system_config" | 成本控制策略不可调 |

## 2. 产品判据：什么东西"该"做成配置功能

不是所有参数都值得做成界面配置。我用四条判据筛：

| 判据 | 说明 | 反例（不该做成界面配置） |
|---|---|---|
| **J1 变更频率** | 部署后是否会被反复调整？ | `SECRET_KEY`、`ENCRYPTION_KEY`——改一次全量 token 失效，属安装期配置 |
| **J2 变更代价** | 现在改一次的代价（重启？发版？） | `DB_HOST`——改了本来就得重启 |
| **J3 责任人** | 是否应由**非运维角色**（安全分析师/主管）调整？ | CORS 来源——纯运维事项 |
| **J4 出错可恢复性** | 配错了能否快速发现并回退？ | 无测试/校验手段的参数，先补校验再开放 |

**核心原则：J1 + J3 同时成立 → 必做；只有 J2 成立 → 优先做迁移到 L2，但可以不给界面；J4 不成立 → 先补"连接测试 + 校验"，再谈开放。**

## 3. 候选配置域清单与优先级

> 优先级 = 价值（覆盖用户 × 痛点强度） ÷ 成本（改造量 × 风险）。标 * 为含密钥，必须走加密字段。

### P0 — Now（本迭代，ROI 最高）

| # | 配置域 | 现状 | 建议落层 | 关键改造 | 为什么优先 |
|---|---|---|---|---|---|
| 1 | **数据源对接（Wazuh / OpenSearch / Loki）\*** | `.env`，重启生效 | **L2（`category=datasource`）** | 新增数据源连接配置 + 测试连接 + 凭据加密 | 用户点名；对接参数是部署后最常被改的（换 IP、换账号）；改错频繁 |
| 2 | **AI 模型与密钥\*** | `.env`，重启生效 | **L2（`category=ai_provider`）** | 多 Provider 注册表（GLM/Claude CLI/Agnes）+ 模型选择 + 预算参数 | AI 是平台卖点，换模型/调预算是高频操作，且直接影响成本 |
| 3 | **清理幽灵配置** | 假配置 | 删除或实现 | 从 `.env.example` 移除；或立项实现邮件/钉钉 | 低成本、高诚信收益（见 1.3） |
| 4 | **配置 schema 注册表** | 通用 KV 编辑器 | L2 增强 | 每个 category 声明字段名/类型/默认值/校验规则/中文名 | 是所有后续配置页面的地基，且能立刻解决"填错静默降级" |

### P1 — Next

| # | 配置域 | 现状 | 建议落层 | 说明 |
|---|---|---|---|---|
| 5 | **采集器远程配置\*** | 服务器 YAML 文件 | **L2 + 下发通道** | 平台侧维护采集器配置，采集器启动/轮询时拉取；含路由器地址、采集类型与间隔、扫描目标 |
| 6 | **通知渠道\*** | 未实现 | L2（`category=notification`） | 站内信已有；补齐邮件/钉钉/企业微信/Webhook，含"发送测试" |
| 7 | **调度任务周期** | 部分 `.env`、部分硬编码 | L2（`category=scheduler`） | 统一各调度器的周期/开关/首次延迟，允许界面启停 |
| 8 | **数据保留策略** | 未在代码中消费 | L2（`category=retention`） | 告警/日志/事件/快照的保留天数与清理窗口（呼应 P4 数据可靠性） |

### P2 — Later

| # | 配置域 | 说明 |
|---|---|---|
| 9 | 安全策略（登录锁定、密码复杂度、会话时长） | 有合规价值，变更频率低 |
| 10 | 采集器 API Key 生命周期管理 | 现在是 `.env` 里一个静态逗号分隔串，应做成可签发/吊销 |
| 11 | 威胁情报源（CISA KEV 等）管理 | P5 阶段随情报 feed 一起做 |
| 12 | 报表/大屏默认参数 | 已有 `reports` 域，扩展到可视化默认值 |

### 明确 Non-goals（不做）

| 项 | 不做的理由 |
|---|---|
| `SECRET_KEY` / `ENCRYPTION_KEY` 界面化 | 改动导致全量 token 与加密数据失效，属安装期一次性配置，界面化只会制造事故 |
| `DB_HOST` / 数据库连接 | 变更必然伴随重启，界面化无收益 |
| CORS 来源 | 纯部署运维事项，且配错会直接锁死前端 |
| 任意代码级常量无脑配置化 | 会造成"配置爆炸"，反而降低可维护性（见第 6 节风险） |

## 4. 样例展开：Wazuh 对接配置应该长什么样

用户点名了这个例子，这里把它作为一个**样板**，因为它的设计可以复用到 Loki / OpenSearch / 其他数据源。

### 4.1 现在的问题 【代码核实】

```
改 Wazuh 地址/账号 → 编辑 src/backend/.env → 重启 uvicorn → MCP(8100) 同进程重启
                   → 所有 MCP 令牌失效 → 需重连并重新 set_mcp_credentials
```

一次参数调整，代价是**整个平台中断 + MCP 重连**。这对一个"安全运营平台"来说是不可接受的——它意味着**改配置 = 停监控**。

### 4.2 目标交互 【设计建议】

**页面：系统管理 → 数据源 → Wazuh**

| 区块 | 字段 | 控件 | 说明 |
|---|---|---|---|
| 基本信息 | 数据源名称、类型（Wazuh/OpenSearch/Loki/…）、启用开关 | 文本 / 下拉 / Switch | 预留多实例（未来可能接 2 套 Wazuh） |
| 连接参数 | API 地址、用户名、密码\*、SSL 校验开关、超时、并发 | 文本 / 密码框 / Switch | 密码字段 `is_encrypted=true`，**只写不读**（界面显示为 `••••••`，留空表示不修改） |
| 采集范围 | 同步类型（asset/vulnerability/baseline）、同步间隔、Agent 过滤条件 | 多选 / 数字 / 表达式 | |
| 高级 | 重试次数、重试退避、代理 | 数字 / 文本 | |
| **操作** | **【测试连接】**、保存、恢复默认 | 按钮 | **测试连接是 P0 必备**——保存前先验活 |

**测试连接返回什么（设计建议）**：
```
✅ 连接成功
   API 版本：4.7.2
   认证方式：Basic → JWT
   可访问端点：/agents ✅  /agents/{id} ✅  /vulnerability ⚠️ 404（本环境不支持，CVE 走 OpenSearch）
   响应时间：128ms
```
> 注：最后一行是真实有价值的——代码注释已记录"本环境 Wazuh API 无 `/vulnerability` 路由，CVE 真实数据源为 OpenSearch"。把这个**环境事实探测**做进测试连接，能让实施人员少踩一个已知的坑。

### 4.3 生效语义（三种，必须在界面上明确标注）

| 配置类型 | 生效方式 | 界面标注 |
|---|---|---|
| 连接参数 | 保存后**热生效**（重建客户端实例，60s 缓存内） | 🟢 立即生效 |
| 采集范围/间隔 | 下一轮调度周期生效 | 🟡 下个周期生效 |
| 环境级参数（如 MCP 端口） | 需重启 | 🔴 需重启服务 |

**产品要求：每个配置项必须显式标注生效方式。** 当前界面完全没有这个概念，用户改完不知道有没有生效——这是配置类功能最常见的投诉来源。

### 4.4 多实例数据模型（D1 已决策）【设计建议】

**决策：数据源从第一版就支持多实例**，表结构直接按多实例设计，避免后期从单实例改造（改造成本远高于一开始预留）。

#### 4.4.1 表设计：`soc_data_sources`（新表）

> ⚠️ **命名警示【代码核实】**：`soc_asset_sources` **已被占用**（资产多源溯源表，语义是"一条资产来自哪些数据源"）。新表必须命名 `soc_data_sources`，两者语义完全不同，勿混淆。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BigInteger PK | |
| `source_code` | String(64) **唯一** | 实例编码，如 `wazuh-prod`、`loki-main`、`wazuh-branch` |
| `source_type` | String(32) | `wazuh` / `opensearch` / `loki` / `tplink` / `scanner` / `collector` |
| `name` | String(200) | 显示名，如"生产 Wazuh（192.168.0.40）" |
| `endpoint` | String(512) | 服务地址 |
| `auth_type` | String(32) | `basic` / `token` / `apikey` / `none` |
| `auth_username` | String(200) | 可空 |
| `auth_secret` | Text（**Fernet 加密**） | 可空；**只写不读**，界面显示为 `••••••`，留空表示不修改 |
| `verify_ssl` | Boolean, default False | Wazuh/OpenSearch 多为自签名证书 |
| `timeout_seconds` | Integer, default 30 | |
| `retry_times` / `retry_backoff_seconds` | Integer | 复用现有 `http_retry.py` 的能力 |
| `enabled` | Boolean, default True | 停用后不参与解析 |
| **`is_default`** | Boolean, default False | **多实例的核心**：同 `source_type` 下最多一个默认实例 |
| `config_json` | Text(JSON) | 类型特有参数（Wazuh 的采集类型、Loki 的租户/标签等） |
| `last_test_at` / `last_test_ok` / `last_test_message` | DateTime / Boolean / Text | **测试连接结果留痕**，列表页直接展示健康状态 |
| `created_at` / `updated_at` / `updated_by` | 标准审计字段 | |

**约束（必须在建表时落）**：
- `source_code` 唯一索引
- 同 `source_type` 下 `is_default=True` 至多一个（部分唯一索引；或应用层在设为默认时先清零同类型其他行）

#### 4.4.2 与既有 `soc_source_health` 的对齐

`soc_source_health.source_key` 现有取值形如 `loki:browsing_detection` 【代码核实】。多实例后建议统一为 **`{source_code}:{场景}`**，例如 `wazuh-prod:vulnerability_sync`。

- 迁移期：老 key 保留不动，新写入用新格式；`source_health` 表增加可空字段 `source_id` 外键指向 `soc_data_sources.id`，逐步收敛。
- **不做的**：不做硬外键强约束，避免健康检查写入被配置删除阻塞。

#### 4.4.3 解析优先级（避免迁移期双源冲突）

```
1. DB 中存在 source_type=X 且 enabled=True 且 is_default=True 的实例  → 用它
2. 否则 DB 中存在 source_type=X 且 enabled=True 的实例（任意一条）     → 用它（并告警提示未设默认）
3. 否则回落 settings.WAZUH_API_URL / LOKI_API_URL / OPENSEARCH_URL   → 兼容现有部署
```

**界面必须显示当前生效来源**（如"当前来源：数据库 `wazuh-prod`" / "当前来源：环境变量"），这是排查"我改了怎么没生效"的关键。

#### 4.4.4 多实例带来的产品约束

| 约束 | 说明 |
|---|---|
| 列表页必带"默认"标记 | 同类型多实例时，用户需要一眼看出哪个是默认 |
| 删除保护 | 被任务/调度引用的实例不允许直接删，需先改引用或停用 |
| 测试连接批量化 | 列表页支持"批量测试"，新增实例后一键验证 |
| 第一版 UI 不暴露多实例的复杂度 | 单实例用户看到的就是"一个 Wazuh 配置"，多实例能力在底层就位即可 |

## 5. 目标架构：统一配置中心

```
┌─────────────────────────────────────────────────────────┐
│  统一配置入口（系统管理 → 配置中心）                        │
│  ├─ 数据源对接（Wazuh / OpenSearch / Loki …）  [P0]      │
│  ├─ AI 服务（Provider / 模型 / 预算 / 熔断）     [P0]      │
│  ├─ 检测与治理策略（已有 alert_governance 等）  [保留]     │
│  ├─ 采集器（远程下发配置）                       [P1]      │
│  ├─ 通知渠道（邮件 / 钉钉 / 企微 / Webhook）     [P1]      │
│  ├─ 调度任务（周期 / 开关）                      [P1]      │
│  └─ 数据保留                                    [P1]      │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  配置内核（4 件套，新增）                                  │
│  1. Schema 注册表：字段定义/类型/默认值/校验/中文名/生效方式 │
│  2. 加密存储：is_encrypted 字段（已有）+ Fernet（已有）     │
│  3. 变更审计：谁在什么时候把什么从 A 改成 B（新增表）        │
│  4. 生效引擎：60s 缓存（已有）+ 显式 invalidate            │
└─────────────────────────────────────────────────────────┘
                          ↓
        L2 soc_system_config（热生效）  ┊  L1 .env（仅安装期）
```

**分层约定（写进团队规范）**：
- **L1 `.env` 只保留 3 类**：数据库连接、密钥种子（SECRET_KEY/ENCRYPTION_KEY）、服务端口与 CORS。**其余一律下迁 L2。**
- **L0 代码常量**：新增魔数前先问一句"这个运营同学会想调吗？"，会 → 直接进 L2。
- **L3 采集器**：配置归平台管，采集器只保留"平台地址 + 自身 API Key"两个启动参数。

## 6. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **配置爆炸** | 什么都做成配置 → 界面变成几百个开关，没人看得懂 | 用第 2 节四条判据卡；每个域的配置项控制在 10 个以内，其余走"高级"折叠 |
| **配错导致平台不可用** | 把 Wazuh 地址改错 → 全线数据断流 | 强制"测试连接"前置；保存时双写（新值生效 + 保留上一版，支持一键回滚） |
| **密钥泄露** | 界面可读回明文密码 | 加密字段**只写不读**；API 返回脱敏；审计日志不记录 value |
| **多实例部署下缓存不一致** | 60s 缓存是单进程的 | 当前单 worker 部署可接受；多 worker 时改为 Redis 发布订阅失效 |
| **迁移期双源冲突** | `.env` 和 DB 同时有 Wazuh 配置，听谁的 | 明确优先级：**DB 有值 → 用 DB；DB 无值 → 回落 `.env`**；并在界面提示当前来源 |
