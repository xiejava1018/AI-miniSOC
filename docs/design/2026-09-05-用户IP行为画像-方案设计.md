## 0. 先说结论：这件事有个前提，必须先定

你问的是"给某个**用户（IP）**做深度行为画像"。我把数据盘完之后，必须先指出一个**术语上的陷阱**：

> **在 AI-miniSOC 现有数据里，IP ≠ 用户。而且三个数据源里的"IP"含义互不相同。**

**[实测]** 同一次真实事件 —— `xiejava` 从 `192.168.0.8` SSH 登录到 `192.168.0.102` —— 三个数据源的记录是：

| 数据源 | 记录的 IP | 语义 | 有用户名吗 |
|--------|-----------|------|-----------|
| Loki 路由器日志 | `192.168.0.8` | **行为发起方**（谁在上网） | ❌ 无 |
| PG 聚合表 `soc_alert_groups.agent_ip` | `192.168.0.102` | **被监控端**（哪台主机出事了） | ❌ 无（`srcip` 字段为 NULL） |
| OpenSearch 原始日志 `data.srcip` + `full_log` | `192.168.0.8` | **真正的操作者** | ✅ 有（`Accepted publickey for xiejava from 192.168.0.8`） |

**[实测]** OpenSearch 中 `rule_id=5715`（sshd 认证成功）原始记录 4543 条，形如：

```
agent.ip    = 192.168.0.102        ← 被登录的主机
data.srcip  = 192.168.0.8          ← 谁登录的
full_log    = Sep 01 11:59:58 xiejava-8g-host sshd[680397]:
              Accepted publickey for xiejava from 192.168.0.8 port 54077 ssh2
```

**[产品判断]** 这决定了三件不同的事，必须先选一件：

| 画像类型 | 主体 | 回答的问题 | 数据就绪度 |
|---------|------|-----------|-----------|
| **A. 设备画像** | 一台 IP / 资产 | "这台设备是怎么的？它安全吗？它在干什么？" | ✅ **现成，今天可做** |
| **B. 用户画像** | 一个人 | "这个人平时怎么工作？有没有异常？" | ⚠️ 需从 OpenSearch 抽身份，约 1 周 |
| **C. 实体画像** | 账号 + 设备 + 行为的关联体 | "这个账号在哪些设备上活动？设备又关联哪些风险？" | ⚠️ 需建立身份基线，约 2–3 周 |

**我的建议：先做 A（设备画像）打底，用 A 的数据管道顺带产出 B 需要的身份映射，再演进到 C。** 因为 A 的全部数据在库表里，打通率经实测是 100%（见 §2.2），能最快拿到成果；而 B 依赖的"用户名"只存在于 OpenSearch 的 `full_log` 文本里，需要额外建抽取管道。

## 2. 可行性验证（已做的核查）

### 2.1 好消息：IP 打通率极高

**[实测]**

| 打通路径 | 结果 |
|---------|------|
| 告警 IP → 资产表 | **17 / 17 = 100%** |
| 上网行为 IP → 资产表 | **11 / 13 = 84.6%** |
| 上网行为 IP ∩ 告警 IP | 3 个（192.168.0.17 / .30 / .102） |

**[产品判断]** 资产表的 IP 覆盖是完整的，这给了画像一个可靠的"身份底座"。

### 2.2 坏消息：三个缺口

**缺口 1 · 责任人字段几乎全空**

**[实测]** `soc_assets.owner` 分布：

| owner | 资产数 | 占比 |
|-------|--------|------|
| NULL | **72** | **94.7%** |
| xiejava | 3 | 3.9% |
| 佳佳 | 1 | 1.3% |

→ **76 个资产里只有 4 个知道是谁的。** 这是"IP → 人"在库表层的直接断裂点。

**缺口 2 · 聚合表丢了原始上下文**

**[实测]** `soc_alert_groups` 中 `top_srcips` 与 `distinct_srcips` **全部为 NULL**（抽查 rule 5715 全部记录）。该表只有 `count` / `first_seen` / `last_seen`，**没有用户名、没有源 IP、没有原始日志**。要拿这些必须回 OpenSearch。

**缺口 3 · 风险历史不是连续序列**

**[实测]** `soc_asset_risk_history` 828 行，覆盖 69 个资产，但时间范围只有 **2026-08-21 08:56 ~ 08-22 16:55（约 1.3 天）**。

→ **[产品判断]** 这是一次性的评分快照，不是持续追踪的时序数据。**"风险趋势"这个画像维度目前没有数据支撑**，要么先建立每日评分落库机制，要么在画像里明确标注"趋势暂不可用"。

### 2.3 推荐的 POC 样本

**[产品判断]** 基于数据丰富度，建议用两个对象分别验证两条路径：

| 对象 | 数据量 | 为什么选它 |
|------|--------|-----------|
| **192.168.0.102**（设备画像） | 告警 866 + 上网行为 3 | ⭐ **身份链最完整**：资产表有记录，且 OpenSearch 明确记录了"xiejava 从 192.168.0.8 登录它"。一台被多人 SSH 的主机，最适合验证"设备视角"全景 |
| **192.168.0.8**（用户画像） | 上网行为 4 + OpenSearch 登录记录数千 | ⭐ **真正的"人"的入口**：它是 xiejava 的操作端，能验证"用户视角" |
| 192.168.0.30（备选） | 告警 881 + 上网行为 931 | 数据量最大（Wazuh/Loki 服务器），但它是基础设施，行为模式单一 |
| 192.168.0.17（备选） | 告警 329 + 上网行为 961 | 上网行为最活跃，适合看"行为节律"维度 |

### 3.0 总体界面框架（画像详情页如何组织）

**[产品判断]** 五层不是五个独立页面，而是**一个"画像详情页（Profile）"内的五个分区/Tab**。理由：用户要的是"对一个 IP 的整体判断"，来回跳五个页会打断心流；且层与层必须能交叉印证（如"行为节律突变"要能点开看"具体哪些域名新增"）。

**页面布局**（对应 §9.5 `src/frontend/src/views/behavior-profile/Profile/index.vue`）：

```

│ 主体标识条：IP · 主机名 · 资产类型 · 责任人 · 置信度 · 流量类型          │
│           ⚠ 右上角常驻「本数据仅用于安全审计」水印（§6 用途锁定）       │
├──────────────┬───────────────────────────────────────────────────────┤
│ 左栏          │ 主区（Tab 切换）                                       │
│ 身份档案卡    │  [ 行为画像 ] [ 风险画像 ] [ 关系画像 ] [ 异常判定 ]    │
│ (层1 精简)    │                                                        │
│ · 基本信息    │  ── 行为画像 ──                                        │
│ · 关联账号    │  24h 曲线 | 星期热力 | 时段占比 | 兴趣分类              │
│ · 来源/同步   │  分类×时段 | 域名 TOP20(可下钻) | 人格标签卡            │
└──────────────┴───────────────────────────────────────────────────────┘
```

- **异常判定（层5）特殊位置**：除独立 Tab 外，还在标识条下方挂一条**红色/黄色异常横幅**（有信号才显示），让"结论"一进页面就能看到。
- **三个入口（三级联动，§9.5）**：资产列表点 IP → 上网行为基线点 IP → 告警详情点 `agent_ip`，均跳到此详情页。未装 Wazuh agent 的设备（如 .8 开发机）也能进入，仅风险/关系分层显示"数据不足"。
- **复用 POC 可视化组件**（§9.5）：`hour_bars`(24h 曲线)、`heatmap`(星期热力)、`block_bars`(时段)、`cat_bars`(兴趣)、`cat_block_stack`(分类×时段)、`domain_table`(TOP N)、`tag_cards`(标签)、`risk_bars`(告警/漏洞)、`rel_graph`(关系网络)。

> 原型含 5 个可切换主体（.8 开发机 / .102 服务器 / .100 AI 工作站 / .17 NAS / .25 手机），每个主体均渲染**左栏身份卡 + 四个 Tab**，
> 真实数据均来自本报告与 POC 实查（Loki 行为 + PostgreSQL 告警/端口 + OpenSearch 认证抽取），未装 agent 设备的空态也一并画出。

### 层 5 · 异常判定（So What）

**[产品判断]** 前四层是"描述"，这一层才是"结论"，也是画像真正的价值所在。建议的判定规则：

| 异常信号 | 判定逻辑 | 数据支撑 |
|---------|---------|---------|
| **新设备/新账号出现** | 该 IP 或账号首次出现于 30 天内 | ✅ 可做 |
| **行为节律突变** | 近期活跃时段偏离自身历史基线 | ✅ 可做（需建基线） |
| **访问域名突变** | 新增域名速率显著高于历史 | ✅ 可做 |
| **登录地点/时间异常** | 凌晨登录、非惯用源 IP 登录 | ⚠️ 需 OpenSearch |
| **权限扩散** | 账号登录的主机数量增加 | ⚠️ 需 OpenSearch |
| **失败登录激增** | 认证失败次数超自身基线 | ⚠️ 需 OpenSearch |
| **风险叠加** | 高危漏洞 + 公网暴露 + 活跃告警 | ✅ 可做 |
| **离群度** | 与同网段/同类型设备的行为偏离度 | ✅ 可做（需建群体基线） |

**层 5 · 落地字段与界面体现**

**[产品判断]** 前四层是"描述"，层 5 是"结论"，是画像真正产生安全价值的一层。每个异常信号 = 一条**可审计的规则**，命中后给出证据与处置入口，而非只打标签。

## 6. 风险与合规（必须前置考虑）

**[产品判断]** 这一节是我主动增加的。给**人**做行为画像，在中国境内受《个人信息保护法》约束，即使是企业内网也不例外。作为产品经理我必须标注：

| 风险 | 说明 | 缓解建议 |
|------|------|---------|
| **告知与同意** | 对员工上网行为、登录行为做画像，属于个人信息处理 | 需在员工手册/IT 制度中明确告知；建议有正式的《员工行为审计告知》 |
| **最小必要** | 不应采集与工作无关的内容 | 画像维度聚焦"安全风险"，不做绩效/效率评价；不采集具体浏览内容（当前只采域名，这点设计是对的） |
| **留存期限** | 行为数据不应无限留存 | 明确留存期（建议 ≤ 180 天），到期自动清理；Loki 7 天保留已是天然约束 |
| **访问控制** | 画像页能看到某个人的完整行为 | 严格权限管控（建议仅管理员 + 审计角色），且**所有画像查看行为本身要记入 `soc_audit_logs`** |
| **用途锁定** | 防止画像被挪作他用 | 页面显著位置标注"本数据仅用于安全审计"；导出加水印 |
| **误判伤害** | 画像给出"异常"结论可能对员工造成实际影响 | 画像只输出"信号"不输出"定性"；定性必须经人工复核（这也呼应了事件闭环的设计） |

**[产品判断]** 如果这是要给客户交付的功能，上述几条需要在 PRD 里作为**非功能性需求**明确写死，不能等开发完再补。

### 9.0 起点：POC 已经证明了什么 **[POC]**

`scripts/behavior_profile_collect.py` + `behavior_profile_report.py` 已对 8 个 IP 跑出完整画像，
报告的五层（身份 / 活跃节律 / 访问构成 / 画像标签 / 数据说明）**全部由真实数据驱动**。

| 你要的维度 | POC 是否已实现 | 实现方式（可直接搬进平台） |

**已经跑出来的真实结论（样本）**：
- `.100`（AI 工作站）：copilot.tencent.com 占主动行为 26.9%，AI+开发占 70% → 标签「AI 重度用户 / 码农 / 周末战士」
- `.8`（你的开发机）：榜单被网易邮箱心跳（countly+woodcattle 占 95%）占满，但**真信号**是 copilot/vscode/github → 需扣掉系统背景

**关键工程经验（必须写进平台，不能丢）**：
> **[POC]** Loki 的 `count_over_time` 聚合在 `step=1h` 下存在**窗口标签错位**（真实 20 点标到 21 点）与**边界重复计数**（凭空多 11 点尖峰）。

### 9.2 数据模型（新增表）

### 9.3 后端服务模块（把 POC 脚本搬进来）

建议目录（与 `browsing_detection/` 对称）：

`start_behavior_profile_scheduler()`（默认每日 02:00 跑全量快照；对离线设备跳过，避免 §6 覆盖偏差）。

**⚠ 断点补拉与缺口标记（v1.5 修订，评审意见——原方案缺失的 P0 能力）**：
Loki 仅留 7 天 + 快照每日定时跑 ⇒ **后端宕机/重启错过一天，当天行为数据永久丢失**。
若不处理，30 天趋势图上会出现"静默的 0"（假绿），违反本项目"数据缺失必须显式声明"原则。修法：
1. **水位回溯**：新增 `soc_behavior_profile_watermark`（或复用 `soc_sync_tasks` 记录），
   snapshot_job 启动时对比 `last_completed_date` 与今天，**补齐 ≤7 天内的所有缺口日**（Loki 窗口内可补）；
2. **缺口显式标记**：超出 Loki 窗口补不回的日子，落一行 `status='gap'、confidence=0、total=0` 的占位快照，
   前端渲染为"数据缺失"灰块而非 0 柱（与 `coverageRatio` 在 total=0 返回 null 的既有原则一脉相承）；
3. **单日部分截断**：沿用已有 `truncated_windows` 字段，>0 时该日快照打 `confidence` 降级。
