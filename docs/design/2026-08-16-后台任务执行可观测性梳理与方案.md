# 后台任务执行可观测性 —— 梳理与完善方案

> 版本：v0.1（2026-08-16）
> 关联：P4 数据可靠性；《2026-08-16-数据可靠性全面梳理与完善方案.md》
> 触发：用户反馈"定时任务和异步任务没有执行或执行失败了都不知道"

---

## 0. TL;DR（给决策者）

系统后台任务分**两类**，可见性天差地别：

| 类别 | 数量 | 当前能否看到执行情况 | 结论 |
|---|---|---|---|
| **周期调度任务**（lifespan 启动的后台 asyncio task / 线程） | **5 个** | ❌ 几乎完全不能 | **盲跑**：失败只进 stdout、无持久记录、3/5 无 Prometheus 指标、内存态重启清零、`/health` 写死 healthy |
| **用户触发异步任务**（资产同步 / 漏洞扫描 / AI 研判） | **3+ 类** | ⚠️ 部分能（状态在各自表，但分散、无统一视图、无失败告警） | 有状态表但**没有"任务中心"** |

**根因**：系统缺一个**统一的"任务执行登记 + 心跳/死信开关"**机制。周期任务尤其严重——它们是数据保鲜的命脉（行为检测、告警快照、KEV 同步），一旦静默失修，上层 P0–P2 所有功能在"看起来正常"下悄悄 GIGO。

**建议**：新建 `soc_task_executions` 统一执行登记表 + 轻量 `track_task()` 埋点 + 让 `/health` 真正检查调度器存活 + 任务中心前端页。这直接补 P4 的"数据在不在、全不全、断没断"。

### 关键代码事实
- `main.py:129-135` 的 `/health` 端点**写死**返回 `{"status":"healthy"}`，**不检查任何调度器是否存活、上次是否成功**。
- 只有 #1 行为检测注册了 Prometheus 指标（`browsing_detection/scheduler.py:30-35`）；#2/#3/#4 连 Counter 都没有，`/metrics` 端点（`api/metrics.py`）因此对其他 3 个调度器是盲的。
- 唯一的"上次运行时间"记录 `_LAST_RUN_SECONDS`（`browsing_detection/scheduler.py:36`）是**模块级内存变量**，进程重启即清零，无法跨重启追溯。

## 2. 为什么"看不到执行情况"——根因分析

1. **失败只进 `logger.exception` → stdout**：容器重启、日志轮转后即丢失；API/UI 根本查不到；生产环境 stdout 往往也无长期留存策略。
2. **周期任务无持久化执行记录表**：4/5 周期任务（#2/#3/#4/#5）执行历史无处可查；3/4（除 #1）甚至无 Prometheus 指标，连"计数"都没有。
3. **内存态重启清零**：唯一有的 `_LAST_RUN_SECONDS` 是内存变量，重启后无法判断"上次跑没跑"。
4. **`/health` 是假的**：写死 healthy，调度器全挂了它也说 healthy，运维被误导。
5. **无"死信开关"（dead-man's switch）**：没有任何机制检测"某任务已超过 N×interval 没跑"——任务停摆无人知晓，是最隐蔽的失修。
6. **用户触发型虽有状态表但分散**：`soc_sync_tasks` / `soc_scan_tasks` / `soc_ai_analyses` 各管各的，没有统一"任务中心"能把所有后台活动汇总给运维看，也没有失败告警。
7. **没有"任务中心"前端页**：前端 grep 确认无任何"任务中心/TaskCenter/调度监控"页面。

---

## 3. 风险：静默失修的连锁反应（为何归 P4）

这正是数据可靠性最危险的一类——**上层功能外观正常，地基悄悄烂掉**：

- KEV 同步（#4）静默失败 → `has_exploit` 永远不富化 → 漏洞 KEV 命中恒为 0（与上一份 P4 文档发现的"KEV∩漏洞=0"互为表里）。
- 行为检测（#1）静默失败 → `soc_browsing_events` 停止增长 → 行为异常 KPI 悄悄失真，却无任何告警。
- 告警快照（#2）静默失败 → 仪表板"告警趋势"逐渐陈旧，趋势图看似正常实已断流。
- 这些都让 P0–P2 已建好的能力在"看起来正常"下持续 GIGO。

## 4. 完善方案：统一任务执行可观测性

### 4.1 统一执行登记表 `soc_task_executions`

```text
soc_task_executions
  task_key           VARCHAR  PK/唯一   e.g. 'browsing_detector'
  task_name          VARCHAR            展示名
  task_type          VARCHAR            scheduled | async | thread
  owner_module       VARCHAR            来源模块
  schedule_expr      VARCHAR            周期描述（'*/5m' | '0 8 * * *' | '60s'）
  enabled            BOOLEAN
  last_run_at        TIMESTAMPTZ        上次触发
  last_status        VARCHAR            success | running | failed | skipped
  last_error         TEXT               失败堆栈/消息
  last_duration_ms   INT
  last_stats         JSONB              本轮业务统计（如 fetched/events）
  run_count          INT
  consecutive_failures INT
  next_run_at        TIMESTAMPTZ        预期下次
  updated_at         TIMESTAMPTZ
```

> 借鉴已有的 `SyncTask` 状态机（`soc_sync_tasks`：pending/running/completed/failed + error_message + started/completed_at），但做成**横切统一表**，而非每个功能各建一张。

### 4.2 轻量埋点 `track_task(task_key)` 包装器

每个调度器迭代 + 每个用户异步任务入口包一层，自动 upsert 对应行：

- 成功：`last_run_at=now`、`last_status=success`、`consecutive_failures=0`、`run_count+=1`
- 失败：`last_status=failed`、`last_error=...`、`consecutive_failures+=1`
- 复用 #1 的 Prometheus 范式，但改为 **Gauge**（`task_last_run_ts`、`task_consecutive_failures`）覆盖全部任务（不只有 Counter）。

### 4.3 真实健康检查

- **`/health` 升级**：检查各调度器 `last_run_at` 新鲜度，超阈值（如 2×interval）→ 返回 `degraded` + 列出失活任务。
- 新增 `GET /api/v1/tasks/executions`（列表）+ `GET /api/v1/tasks/executions/{key}`（详情/错误）。

### 4.4 死信开关 + 告警

- 若 `consecutive_failures ≥ N` 或 `(now - last_run_at) > 阈值` → 在仪表板「我的待办」标红 + （可选）走现有通知推送（`AlertDigestService` 范式）。
- 这是把"静默失修"变成"主动可见"的关键一招。

### 4.5 任务中心前端页

- 列表：所有任务 + 上次运行 / 状态（色码）/ 下次运行 / 连续失败数 / 最近错误。
- 详情：运行历史、错误信息、手动触发 / 禁用。
- 路由接后端菜单树（仿 browsing 页范式：`soc_menus` 插记录 + 前端 `views/task/center/index.vue`）。

## 5. 实施建议（分阶段，对齐 P4）

| 阶段 | 内容 | 解决什么 |
|---|---|---|
| **Phase 1（地基，最优先）** | 4.1 建表 + 4.2 埋点（#1–#5 周期任务）+ 4.3 `/health` 升级 + Prometheus Gauge 全量 | 任务"在不在、成没成、挂没挂"有记录、可查、可探活 |
| **Phase 2（可视）** | 4.4 死信开关进仪表板 + 4.5 任务中心页 | 失败从"静默"变"主动可知"，运维一处看全 |
| **Phase 3（统一）** | 把用户触发型（#6/#7/#8）也纳入 `soc_task_executions` | 全系统后台活动一处汇总，消除分散状态表盲区 |

---

## 6. 验收指标

- 任一周期任务失败 → **30s 内** `soc_task_executions` 出现 `failed` 行 + `consecutive_failures` +1。
- `/health` 在某调度器停跑 2×interval 后返回 `degraded`（而非恒 healthy）。
- 任务中心页能列出全部 5+ 后台任务及其实时状态/最近错误。
- 进程重启后状态从 **DB 读取**（不依赖内存态），历史不丢。

## 8. 本期不做（Non-goals）

- 任务编排 / DAG 依赖（留给 P5 SOAR）。
- 分布式任务队列（Celery/RQ）改造——当前 `asyncio.create_task` + 线程足够，先解决"可见性"再谈"伸缩性"。
- 历史执行明细的无限留存（保留最近 N 条 + 聚合即可）。
