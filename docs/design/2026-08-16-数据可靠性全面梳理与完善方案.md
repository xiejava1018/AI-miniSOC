# AI-miniSOC 数据可靠性全面梳理与完善方案（P4·修订稿）

> 初版盘点：2026-08-16｜**修订：2026-08-16（v2，二次代码核实）**
> 视角：产品管理 + 工程审计｜方法：**逐条代码 + 真实库核实**（非凭记忆）
>
> **v2 修订说明**：对初版"经核实"的断言做了二次代码核对，修正 4 处与代码不符的事实（见第七节），并补入初版遗漏的幂等落库、备份、失败可追踪等结构性缺口。结论不变——数据可靠性是安全运营的"地基"，但**真问题的样貌与初版描述有出入**，请以本稿为准。
>
> 核心结论：当前 P0–P2 功能已建成，但地基有 3 类结构性裂缝（**迁移图损坏 / 查询静默截断 / 检测结果无幂等落库**），以及若干契约与可观测性缺口。

---

## 一、为什么这是 P0 级（Why）

安全运营的所有上层能力——AI 研判、事件闭环、行为检测、概览仪表板——都建立在"底层数据真实、完整、可溯"之上。任何一层数据不可靠，上层就是 GIGO（垃圾进垃圾出）：
- 仪表板 KPI 不可信 → 运营者不敢据此决策；
- 漏洞/资产关联错 → AI 研判结论错；
- 告警查询被截断 → 漏报真实威胁；
- 检测事件重复落库 → KPI/告警虚高，研判被噪声淹没。

因此 P4 不是"修 bug"，是**让已建成的系统从"能跑"变成"可信"**。

## 二、已核实的问题清单（按严重级）

### 🔴 P0 阻断级（数据完整 / 生产硬门槛）

**A. Alembic 迁移图已损坏，schema 不在版本控制下**
- 实测（修正初版）：`src/backend/alembic.ini` **存在**，`alembic/versions/` 下有 **7 个迁移文件**——问题**不是"没有迁移体系"**，而是**迁移图本身已损坏**，且代码已自认：
  - `app/models/cisa_kev.py:6` 注释写明 *"alembic 迁移图已损坏，本期 DB 变更一律走 scripts"*；
  - **重复 revision id**：`a1b2c3d4e5f6_add_asset_data_classification_and_owner_contact.py` 与 `a1b2c3d4e5f6_add_vulnerability_management_tables.py` 共用同一 revision `a1b2c3d4e5f6`；
  - **链分叉 / 多 head**：两份 `a1b2c3d4e5f6` 的 `down_revision` 分别指向 `807124bfc2bc` 与 `36b64094249e`，下游 `b2c4d6e7f8a9`、`c3d4e5f6g7h8` 再各自分叉，`alembic upgrade head` 无法解析；
  - **alembic 未入依赖**：venv 中 `No module named alembic`，`requirements.txt` 也无 alembic；
  - **运行时绕过迁移建表/改表**：6+ 处 `Base.metadata.create_all(checkfirst=True)`（`browsing_detection/scheduler.py:46`、`alert_digest_service.py:37`、`alert_group_triage_service.py:42`、`alert_group_snapshot_scheduler.py:32` 等），甚至有运行时 DDL：`alert_group_snapshot_service.py:58` 的 `ALTER TABLE soc_alert_groups ADD COLUMN IF NOT EXISTS ...`（带进程内 `_schema_ensured` 开关，多 worker 下有竞态）。
- 影响：`create_all` 只建缺失表、不改已有表；当前 schema 实际由"启动 create_all + 散落脚本 + 运行时 ALTER"共同拼成，与迁移文件**必然漂移**。未来加列/改类型/加索引**没有安全、可回滚路径**，换环境即炸。这是最隐蔽但最致命的一项。

**B. Loki 查询静默截断（数据不完整）**
- 实测：`loki_client.py:32` 的 `query_range` 默认 `limit=10000`，**无翻页**；超量结果被直接丢弃（只返回前 1 万条）。
- 影响：行为检测按时间窗拉日志时，若窗口内日志 >1 万行（24h 实测 20 万+ 行），基线/异常事件**基于不完整样本**，且管理员无感知。配合 7 天保留，长窗口分析本就受限，再叠加截断，完整性双重受损。
- **技术澄清（修正初版）**：Loki `query_range` 响应**没有 `next` 游标**，翻页只能靠**时间边界推进**（取本页末条时间戳作下一页 `start`）或**时间分片**；且大查询重试会放大负载。更治本的方向是**把聚合下推到 LogQL**（代码已有 `query()` 支持 `count_over_time`/`sum by`/`topk`），明细只在命中后拉取。

**C. 检测结果落库无幂等/去重（KPI 与告警可能虚高）**
- 实测（新增）：`event_service.py:53-65` 对每个 finding 直接 `db.add(BrowsingEvent(...))`，仅靠 `_is_suppressed`（时间窗抑制）防重；而 `soc_browsing_events`（`browsing_event.py:19-23`）**没有 `(ip, domain, window_start, window_end)` 唯一约束**。
- 影响：调度器重跑、窗口边界重叠、未来多 worker 部署都会**重复落事件** → 事件数/KPI/告警虚高，研判被噪声淹没。与 B（全量拉取）叠加风险更大。这是初版完全漏掉的"进来后对不对"的核心问题。

### 🟠 P1 重要级（可信度 / 契约一致）

**D. OpenSearch 字段一致性（双源结构并存）**
- 实测：`opensearch_scap_sync.py:10-11` 注释自认 —— `wazuh-states-vulnerabilities-*` 用 ECS **顶层**结构（`vulnerability.id` 无 `data.` 前缀），而 `wazuh-alerts-4.x-*` 用 `data.vulnerability.*` 结构，"两者均为真实结构"。
- 影响：同一逻辑实体在 OS 里两套字段路径。查询/解析假设错结构就静默取到空值 → 落库漏洞缺字段、关联失败。脆弱性 PG 数据直接源自此同步，源头不一致会层层下传。

**E. `soc_browsing_events` 缺外键（孤儿引用风险）**
- 实测：`browsing_event.py:46,48` 的 `incident_id` 与 `ai_analysis_id` **无 FK 约束**。
- 影响：行为事件可指向不存在的事件/研判（孤儿引用），事件闭环时可能关联到已删除对象，引用完整性无保障。

**F. 数据新鲜度不可观测（采集中断无感知）**
- 实测：`.env` 中 `LOKI_RETENTION_DAYS=7`；历史已知 `192.168.0.2`（TL-R479GP-AC 路由器）日志凌晨 1:27 后中断。资产侧已有 `asset.last_synced_at` / `asset_source.last_seen_at`，但 browsing/OS/各同步任务**无统一健康信号**。
- 影响：Loki 仅留 7 天、某采集源可能已静默中断，但系统**无"数据截至/采集健康"主动监控**——仪表板"数据截至"即使补上，也无法区分"正常 7 天窗口"与"采集源挂了"。

**G. 同步失败不可追踪、不可重放**
- 实测（新增）：`soc_sync_tasks` 表在，但采集器推送/OS 同步部分失败时，**缺少批次级错误明细、死信与重放机制**。
- 影响：只知道"上次成功时间"（F），不知道"哪些记录失败、为什么、能不能补"。数据同步的"可靠"不只是成功时间戳，还有"失败的不丢、可追、可重放"。

**H. OS 漏洞同步的写入幂等需核查**
- 实测（新增）：B 只谈字段映射，但同步落库是 upsert 还是追加、重试是否重复、去重键 `(agent.id, vulnerability.id, package.name+version)` 在 PG 侧是否有对应唯一约束，均需逐项核实并与 C 一并收口。

**I. 时间/时区一致性**
- 实测（新增）：Loki 纳秒 UTC、PG `DateTime(timezone=True)`、检测窗口、仪表板 24h/7d 切换——跨时区、窗口开闭边界、NTP 偏差没有统一核查。
- 影响：直接关系到 C 的重复/遗漏。需明确窗口语义（建议左闭右开）、统一 UTC 存储、展示层转本地。

### 🟡 P2 改进级（健壮性 / 可观测 / 防护）

**J. 外部源客户端无重试/退避**
- 实测：`loki_client.py` / `opensearch_scap_sync.py` / `wazuh_client.py` 均为单次 `httpx` 调用，超时直接抛；无重试、无指数退避、无熔断，`requirements` 也无 tenacity。
- 影响：内部网络瞬时抖动即整批同步/查询失败，无自愈能力。重试需配合截断上限与退避，避免大查询重试放大负载（见 B）。

**K. 测试覆盖缺口（在现有 19 个测试基础上补）**
- 实测（修正初版）：`tests/` 下有 **19 个 `test_*.py`**（models / schemas / services / integration 均有），并非"仅一个集成测试"。真实缺口是：**无迁移/数据层测试、envelope 业务码断言缺失**。
- 活的反例：`tests/integration/test_user_workflow.py:25` 仍是 `assert response.status_code == 201`（中间件恒包 200 + `body.code`），初版误称该文件"不存在"，实际存在且问题未修。
- 影响：数据层改动（迁移、字段映射、幂等约束）无防护网，P4 自身修复也易引入回归。

**L. KEV ∩ 漏洞 = 0（数据探查，非"对齐未建"）**
- 实测（修正初版）：对齐层**已经存在** —— `cisa_kev_service.py` 的 `is_known_exploited()` 用 `cve_id.strip().upper()` 归一化，有 24h 调度 + 手动触发 + 离线快照兜底 + 10 分钟 TTL 缓存 + `enrich_has_exploit()` 存量富化。问题不是"对齐方式未建立"，而是**数据为何 join 不上**。
- 影响：仪表板"KEV 命中 N"恒为 0，误导"无在野利用漏洞"。需先做数据探查：比对 `soc_vulnerabilities.cve_id`（源自 Wazuh states `vulnerability.id`）与 `soc_cisa_kev.cve_id` 的实际样本，定位是大小写/前缀/CVE 为空/软件集不重叠/快照陈旧中的哪一种，再决定是否回流 OS 侧命中。

**M. 多 worker / 调度器单例约束**
- 实测（新增）：browsing、KEV、snapshot、digest 等均为**内存型调度器**，`_schema_ensured` 等也是进程内全局标志。当前隐含"单 worker"假设。
- 影响：若以 `uvicorn --workers N>1` 部署，调度会多实例重复执行（与 C 叠加产生重复事件）、缓存不一致、运行时 DDL 竞态。需在文档写明单 worker 约束，或给调度器加分布式锁。

**N. 数据库备份/恢复策略缺失**
- 实测（新增）：通篇谈"数据进来对不对"，未谈"数据丢了怎么办"。无 `pg_dump` 周期备份/保留策略，Loki 7 天、OpenSearch 的备份/保留也未界定。
- 影响：这是"数据可靠性"最字面的含义，缺了不完整。关键阶段应讨论 PITR。

## 四、完善方案（问题 → 影响 → 方案 → 验收）

### A. Alembic 迁移体系（地基，最高优先）
- **方案**（按顺序，缺一不可）：
  1. **收敛损坏的迁移图**：先解决重复 revision `a1b2c3d4e5f6`（重命名其一并修 down_revision），把分叉链合并为单链或用 `alembic merge` 合成一个 merge revision，确保 `alembic heads` 只有一个；
  2. **把 alembic 加入 `requirements.txt`** 并装入 venv；
  3. **以当前线上 PG schema 为基线**：核对模型与库一致后 `alembic stamp head`（而非裸 autogenerate 出一份与线上不符的 baseline）；
  4. **收口所有运行时 DDL**：把 6+ 处 `create_all` / `ALTER TABLE ADD COLUMN` 改为迁移；**生产启动路径不允许任何 `create_all` / 运行时 ALTER**；
  5. 启动流程改为 `alembic upgrade head`，后续表结构变更一律走 migration。
- **验收**：`alembic heads` 单一 head；`alembic upgrade head` 在新库可幂等执行；`alembic current` 显示有效修订；代码中无生产路径的 `create_all`/运行时 ALTER；CI 加迁移生成/漂移检查。

### B. Loki 分页与完整性（截断）
- **方案**：`query_range` 增加**时间分片/时间边界翻页**（非 next token），累计返回直至窗口耗尽；设硬上限，超阈值记 warning 并透出"已截断 N 条"信号给上层；**能用 LogQL 聚合的（计数/topk）走 `query()` 下推**，明细按需拉取；重试配退避与上限。
- **验收**：注入 >1 万行日志的窗口，行为检测基于全量样本（或聚合结果正确）；截断时有明确日志/状态透出。

### C. 检测结果幂等落库（防重）
- **方案**：明确窗口语义（左闭右开），给 `soc_browsing_events` 加 `(ip, domain, window_start, window_end)` 唯一约束；落库改 `INSERT ... ON CONFLICT DO NOTHING/UPDATE`；迁移先清存量重复。
- **验收**：同窗口重复跑/重放不产生重复事件；唯一约束在库生效；KPI 在重跑前后稳定。

### D. OpenSearch 字段一致性（源头）
- **方案**：抽离**统一 OS 字段映射层**（`os_field_map.py`），所有查询/解析只走该层，禁止 `data.vulnerability.*` 与顶层混写；对 `wazuh-states-*` 与 `wazuh-alerts-*` 做适配封装；加字段存在性探针 + 缺字段告警。
- **验收**：双源结构下均能取到 `cve_id/severity/cvss`，落库缺字段率 = 0。

### E. browsing_events 外键（引用完整性）
- **方案**：先清理孤儿引用（`UPDATE ... SET incident_id=NULL WHERE NOT EXISTS (...)`），再加 `FK ... REFERENCES soc_incidents(id)` / `soc_ai_analyses(id)`（含 `ON DELETE SET NULL`）。
- **验收**：插入指向不存在对象的记录被 DB 拒绝；现有孤儿清零。

### F. 数据新鲜度监控（可观测）
- **方案**：统一"数据源健康"采集——各采集器/源/同步任务记录 `last_success_at`（含失败计数）；仪表板态势条据其计算"数据截至"并区分"正常窗口"vs"中断"（>2× 周期未更新标红）；对 `192.168.0.2` 等已知源设中断告警。
- **验收**：主动停掉某采集源，仪表板在 1 个周期内标红"采集中断"，而非静默显示陈旧数据。

### G. 同步失败可追踪/重放
- **方案**：批次级错误明细落表（或日志结构化），失败记录入死信队列，支持按批次重放；部分失败不阻断整批、成功部分可见。
- **验收**：注入一批含坏数据的推送，能查到失败记录与原因，可重放成功记录，整批不丢。

### H. OS 同步写入幂等
- **方案**：核实 upsert 语义，PG 侧建立与去重键一致的唯一约束，重试/重跑不产生重复漏洞记录。
- **验收**：重复触发 OS 同步，漏洞数与关联数不增长。

### I. 时间/时区统一
- **方案**：统一 UTC 存储、展示层转本地；窗口一律左闭右开；关键节点核对 NTP；纳秒/秒/时区转换集中到工具函数并加测试。
- **验收**：跨窗口边界不重不漏；24h/7d 切换计数一致。

### J. 客户端重试（健壮性）
- **方案**：为 Loki/OS/Wazuh 客户端加 `tenacity` 重试 + 指数退避 + 超时分级；区分可重试（5xx/超时）与不可重试（4xx）；大查询加重试上限。
- **验收**：模拟源端瞬时 503，客户端自愈成功，无整批失败，且无重试风暴。

### K. 测试网（回归防护）
- **方案**：在现有 19 个测试基础上补：迁移可跑/无漂移、字段映射、FK 与唯一约束、幂等落库等数据层测试；envelope 业务码断言（修 `test_user_workflow.py:25` 为 `body["code"]`）；P4 修复的回归用例；接入 CI。
- **验收**：CI 跑通数据层 + API 回归；P4 改动有对应测试。

### L. KEV 数据对齐探查
- **方案**：先 `SELECT cve_id FROM soc_vulnerabilities LIMIT 20` 与 KEV 表样本比对，定位格式/覆盖问题；按需做 cve_id 标准化（对齐层已 `strip().upper()`，再查空值/前缀）；确认 OS 侧 KEV 命中是否应回流；核实离线快照时效性。
- **验收**：KEV 命中数反映真实在野利用（非恒 0），仪表板标注口径可信。

### M. 多 worker / 调度器单例
- **方案**：文档明确单 worker 约束，或为内存型调度器引入分布式锁（PG 行锁/Redis）；`_schema_ensured` 类进程内标志替换为迁移或可并发安全的检查。
- **验收**：多 worker 下调度不重复执行、无 DDL 竞态。

### N. 备份与恢复
- **方案**：PG 周期 `pg_dump` + 保留策略，关键阶段评估 PITR；明确 Loki/OpenSearch 备份与保留边界；定期做一次恢复演练。
- **验收**：有可执行的备份脚本与保留策略；最近一次恢复演练成功（记录耗时与 RPO/RTO）。

## 五、分阶段实施建议

| **Phase 1 地基** | A（迁移）+ B（Loki 截断）+ C（幂等落库）+ I（时间语义） | 杜绝"改表即炸 / 查询截断 / 重复落库"，统一窗口口径 | 中 |

> 优先级理由：Phase 1 解决"数据是否在、是否全、是否重复、是否断"——这是可信前提；Phase 2 解决"数据是否准、是否一致、失败能否追"；Phase 3 解决"能否长期稳定不退化、丢了能否回"。

## 六、可衡量验收指标（Metrics）

- 迁移：`alembic heads` 单一 head；新环境 `alembic upgrade head` 成功率 100%；生产路径无 `create_all`/运行时 ALTER；
- 完整性：行为检测窗口日志截断率 = 0；同窗口重跑事件重复率 = 0；OS 同步重跑漏洞记录增长 = 0；
- 一致性：漏洞落库缺字段率 = 0；browsing_events 孤儿引用数 = 0；
- 可观测：采集源中断到仪表板标红 ≤ 1 个采集周期；同步失败批次 100% 可查可重放；
- 健壮性：瞬时 5xx 自愈成功率达标、无重试风暴；CI 数据层 + API 测试通过率 100%；
- 灾备：备份可用率 100%，恢复演练 RPO/RTO 达标。
