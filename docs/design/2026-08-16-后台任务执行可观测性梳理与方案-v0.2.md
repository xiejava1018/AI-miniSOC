# 后台任务执行可观测性 —— 梳理与完善方案（v0.2）

> 版本：v0.2（2026-08-16）
> 前身：v0.1 `2026-08-16-后台任务执行可观测性梳理与方案.md`（同目录）
> 关联：P4 数据可靠性；《2026-08-16-数据可靠性全面梳理与完善方案.md》（v2）
> 触发：用户反馈"定时任务和异步任务没有执行或执行失败了都不知道"
> 本次变更：基于已验证代码现状重写方案，修正 v0.1 的单表矛盾/漏僵尸检测/重复造轮子/可视化虚化四类缺陷。

---

## 0. TL;DR（给决策者）

后台任务分**两类**，可见性天差地别：

| 类别 | 数量 | 当前能否看到执行情况 | 结论 |
|---|---|---|---|
| **周期调度任务**（lifespan 启动的后台 asyncio task / 线程） | **5 个** | ❌ 几乎完全不能 | **盲跑**：失败只进 stdout、无持久记录、3/5 无 Prometheus 指标、内存态重启清零、`/health` 写死 healthy |
| **用户触发异步任务**（资产同步 / 漏洞扫描 / AI 研判） | **3+ 类** | ⚠️ 部分能（状态在各自表，但分散、无统一视图、无失败告警） | 有状态表但**没有"任务中心"** |

**v0.2 相对 v0.1 的核心改进**：① 拆成 `registry`（当前态）+ `runs`（真历史）两张表，根治单表既要当前态又要历史的自相矛盾；② 新增**僵尸/卡死检测**（running 永不结束的更隐蔽失败）；③ **复用 P4 已落地的 `single_worker_guard` 与 `soc_source_health`**，不再另起炉灶；④ 可视化**分两档**——先用现有 Prometheus+Loki+Grafana 栈出看板（零新前端、当天止血），再上 Vue 任务中心。

## 2. v0.1 的四类缺陷（为何要 v0.2）

1. **单表既要"当前态"又要"历史"，自相矛盾。** §4.1 的 `soc_task_executions` 只有 `last_*` 单行，但 §4.5 任务中心要展示"运行历史"——一行存不下历史。
2. **漏了"跑飞/卡死"检测。** 死信开关只查 `last_run_at` 新鲜度，但还有更隐蔽的失败：任务**启动后（running）再也没结束**（进程崩了/异常被吞），会永远卡在 running。v0.1 完全没覆盖。
3. **没复用 P4 已建资产。** `single_worker_guard`（租约锁，天然可做运行锁+僵尸检测）、`soc_source_health`（新鲜度）已存在，v0.1 另起炉灶会重复造轮子。
4. **告警与可视化都"虚"。** "（可选）走现有通知推送""任务中心页"——既没说清告警通道，也没利用已有的 Prometheus+Loki+Grafana 栈，反而一上来就规划重做 Vue 页，成本高、见效慢。

## 3. v0.2 完善设计

### 3.1 两张表（根治单表矛盾）

**`soc_task_registry`** —— 每任务一行（定义 + 当前态）：

```text
soc_task_registry
  task_key            VARCHAR  PK          e.g. 'browsing_detector'
  task_name           VARCHAR              展示名
  task_type           VARCHAR              scheduled | async | thread
  owner_module        VARCHAR              来源模块
  schedule_expr       VARCHAR  nullable    '*/5m' | '0 8 * * *' | '60s'
  expected_interval_s INT                  用于新鲜度计算
  timeout_s           INT                  用于僵尸检测（运行超此时长判卡死）
  enabled             BOOLEAN  default true
  current_run_id      VARCHAR  nullable   在跑的 run 行 id（运行锁可视）
  last_run_at         TIMESTAMPTZ
  last_status         VARCHAR              success|running|failed|skipped|zombie|unknown
  last_error          TEXT
  last_duration_ms    INT
  last_stats          JSONB                本轮业务统计
  consecutive_failures INT  default 0
  total_runs          INT   default 0
  created_at          TIMESTAMPTZ
  updated_at          TIMESTAMPTZ
```

**`soc_task_runs`** —— 每执行一行（**真历史**）：

```text
soc_task_runs
  id              VARCHAR  PK          uuid
  task_key        VARCHAR  FK→registry.task_key
  trigger         VARCHAR              scheduled | manual | api
  started_at      TIMESTAMPTZ
  finished_at     TIMESTAMPTZ nullable
  status          VARCHAR              running | success | failed | skipped | zombie | unknown
  duration_ms      INT
  error_text      TEXT
  stats_json      JSONB               业务统计
  total            INT  nullable       异步任务进度（总量）
  processed        INT  nullable       已处理
  percent          INT  nullable       完成百分比
  correlation_id   VARCHAR nullable    关联 API 请求 / sync_tasks 行
  host             VARCHAR nullable     pod/host 标识
  created_at       TIMESTAMPTZ
索引：(task_key, started_at DESC)
```

> 借鉴 `soc_sync_tasks`（pending/running/completed/failed + error_message + started/completed_at 状态机），但做成横切统一表；`registry` 存当前态、`runs` 存历史，职责分离。

### 3.2 复用 `single_worker_guard` 做运行锁 + 僵尸看门狗

- **运行锁（防重叠）**：每次调度 tick 先 `try_acquire_scheduler_lease(owner=task_key, ttl=timeout_s)`；拿不到（上一轮仍活着）→ 跳过本轮并记 `skipped`。仅对 scheduled/thread 单例任务加锁；用户异步任务每请求是独立 run，不加锁。
- **僵尸看门狗**：扫 `soc_task_runs` 中 `status='running'` 且 `started_at < now - timeout_s` 的行 → 标 `zombie` + 写 registry `last_status='zombie'` + 触发告警。这是 v0.1 漏掉的"跑飞"场景。
- **启动对账（lifespan 内）**：进程启动时 `UPDATE soc_task_runs SET status='unknown' WHERE status='running'`（上一进程遗留的 running 必是假活），并复位 registry `current_run_id`。

### 3.3 复用 `soc_source_health`（已建）做数据新鲜度

一个调度任务跑完，除写 runs/registry，也调 `SourceHealthRecorder.record_success(source_key, source_type, records=...)`。`soc_source_health` 已记 `last_success_at` + `is_healthy(×2 阈值)`。

**视角互补而非重复**：`registry/runs` 看"任务活没活"（执行层面），`soc_source_health` 看"数据鲜不鲜"（数据层面）。例如 browsing_detector 任务成功但 Loki 拉到 0 条，任务视角 healthy、数据视角 stale——两层信号都要。

### 3.4 `track_task()` 埋点契约（v0.2 新增 4 条 v0.1 没说的）

```python
@track_task(task_key, task_type="scheduled", timeout_s=360,
            source_key=None, progress=False)
async/sync def _body(...): ...
```

1. **自动注册**：首次 track 自动 upsert `registry` 行（开发者忘加也不会漏监控）。
2. **双上下文**：同一包装在 asyncio 协程（周期任务）和线程（MCP token 刷新）中都能用（内部按上下文选 sync/async DB 调用）。
3. **优雅降级**：埋点自身所有 DB 写入包 `try/except` 吞掉，**绝不让监控把真实任务搞挂**。
4. **异步进度**：`progress=True` 时长任务周期更新 `processed/total/percent`（同步/扫描类）。

执行流：拿锁 → 插 run(status=running, 设 registry.current_run_id) → 跑 body →
- 成功：run.success + registry(last_run_at=now, last_status=success, consecutive_failures=0, total_runs+=1, last_stats) + （若 source_key）source_health.record_success
- 失败：run.failed+error + registry(consecutive_failures+=1, last_error) + 失败 Counter + 若 `consecutive_failures≥N` → `sync_dead_letter`/告警
- finally：释放锁；确保 run 行关闭。

### 3.5 指标从"计数"升级为"可告警"

在 `browsing_detection/scheduler.py:30-35` 的 Counter 范式基础上，推广为覆盖**全部任务**的 Gauge/Counter（注册到已挂的 `/metrics`）：

- `task_staleness_seconds{task_key}` Gauge = `now - last_success_at`（**关键**：Grafana 告警规则可直接 threshold）
- `task_consecutive_failures{task_key}` Gauge
- `task_last_duration_seconds{task_key}` Gauge
- `task_runs_total{task_key,status}` Counter

### 3.6 可视化分两档（先止血后建页）

- **Tier 0（零新前端，当天见效）**：Grafana 直接吃上述 Prometheus 指标 + 给 runs 打 `task_key` 标签落 Loki，出"任务新鲜度/失败率/时长"看板 + Grafana Alert 规则。完全复用现有栈，**不写一行业务前端**。
- **Tier 1（正经页）**：Vue「任务中心」`views/task/center/index.vue` + `GET /api/v1/tasks/executions`（列表）+ `GET /api/v1/tasks/executions/{key}`（详情/历史）+ `POST .../trigger`、`POST .../toggle`（手动触发/禁用）。菜单接 `soc_menus`（仿 browsing 页范式）。

### 3.7 真实健康检查 + 启动对账

`GET /health`（`main.py:134`）升级：

```json
{
  "status": "healthy | degraded | down",
  "stale_tasks": [{"task_key": "cisa_kev", "last_success_at": "...", "stale_seconds": 90000}],
  "zombies": [{"task_key": "browsing_detector", "run_id": "...", "started_at": "..."}]
}
```

判定：任一 enabled 任务 `now - last_success_at > 2×expected_interval_s`，或存在 `zombie` run → `degraded` 并列出。Docker healthcheck / LB 才真有用。

## 6. 验收指标

- 任一周期任务失败 → **30s 内** `soc_task_runs` 出现 `failed` 行 + registry `consecutive_failures` +1。
- 某任务启动后崩溃（running 永不结束）→ 看门狗在 `timeout_s` 内将其标 `zombie` 并告警。
- `/health` 在某调度器停跑 `2×interval` 后返回 `degraded`（而非恒 healthy），并列出失活任务。
- Grafana 看板（Tier 0）能展示全部任务的新鲜度/失败率/时长。
- 进程重启后状态从 **DB 读取**（不依赖内存态），历史不丢；遗留 running 行被标 `unknown`。
- （Phase 3 后）任务中心页能列出全部后台任务及其实时状态/最近错误/运行历史。

## 8. 本期不做（Non-goals）

- 任务编排 / DAG 依赖（留给 P5 SOAR）。
- 分布式任务队列（Celery/RQ）改造——当前 `asyncio.create_task` + 线程足够，先解决"可见性"再谈"伸缩性"。
- runs 历史无限留存（保留最近 N 天/行 + 聚合即可）。
- 不重复建设 `soc_source_health` 已覆盖的数据源新鲜度能力。
