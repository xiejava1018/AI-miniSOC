## 零、文档结构与编号约定

### 0.1 主从关系

```
本文（诊断基线）
├── DEF-N  缺陷清单（§三）—— 事实陈述，回答"现在到底是什么样"
├── WO-N   整改路线（§四）—— 行动清单，回答"按什么顺序改"
└── 配套 PRD（只读专项）
    └── AC-N  验收标准 —— 回答"改到什么程度算完成"
```

PRD 不复述本文的结论与数据，**只引用编号**。本文不定义验收细节，只给出整改方向。

### 0.2 编号体系（重要）

| 前缀 | 含义 | 所在 | 备注 |
|---|---|---|---|
| `DEF-N` | 缺陷项 | 本文 §三 | 严重度用 **S0 / S1 / S2** 标注 |
| `WO-N` | 整改工作项 | 本文 §四 | 节奏用 **Now / Next / Later** 标注 |
| `AC-N` | 验收标准 | PRD §四 | 必须可自动化测试 |

> **刻意不用 P0/P1/P2 作为条目 ID。** P0/P1/P2 在不同作者笔下时而是"缺陷严重度"、
> 时而是"整改优先级"，同一 token 两个含义会让评审时无法对齐。
> 本文口径：严重度只说 **S0/S1/S2**，节奏只说 **Now/Next/Later**。
> 对外汇报需要优先级时，按 `WO` 的节奏字段折算，不说"P0 有几项"。

### 0.3 严重度与节奏定义

| 标签 | 定义 |
|---|---|
| **S0** | 可直接导致未授权的数据访问或篡改。修复前不应部署到任何共享环境 |
| **S1** | 结构性缺陷。本身未必直接越权，但会放大 S0 影响面，或在特定条件下转为越权 |
| **S2** | 工程规范与可观测性问题。不直接造成越权，但削弱长期可控性 |

| 标签 | 定义 |
|---|---|
| **Now** | 本期必做。**四项 Now 全部完成前，"只读"不成立** |
| **Next** | 只读能力成立之后立即启动的下一迭代 |
| **Later** | 能力增强期，依赖前置项稳定 |

## 一、设计意图（蓝图层）

### 1.1 数据模型：五表 RBAC

| 表 | 作用 | 关键字段 |
|---|---|---|
| `soc_users` | 用户 | `role_id`(FK)、`department_id`(FK)、`is_superuser`、`status`(active/locked/disabled) |
| `soc_roles` | 角色 | `code`(唯一)、`is_system`、`is_active` |
| `soc_menus` | 菜单 | `parent_id`(自关联)、`path`、`permissions`(JSONB 按钮定义) |
| `soc_role_menus` | 角色↔菜单 | 复合主键 + `permissions`(JSONB 已授予按钮) |
| `soc_departments` | 部门 | `parent_id`(自关联树) |

模型定义在 `app/models/{user,role,menu,role_menu,department}.py`。

**关键约束：User → Role 是多对一，即单角色模型。** 一个用户只能有一个 `role_id`，
不存在用户-角色多对多表。这决定了后续无法做"一个人既是运维又是审计员"的复合授权——
若将来需要复合角色，这是第一个要动的结构约束。

### 1.2 角色清单：代码设计 vs 数据库实读

`RoleCode` 枚举声明了 6 个角色，但**数据库里实际存在 7 张角色卡片**，且描述已与注释背离。
以下右三列取自运行实例实读（`GET /api/v1/roles`），非枚举推测：

| id | code | 名称 | 枚举设计意图 | **数据库实际描述** | 用户数 | 菜单授权数（迁移头实读） |
|---|---|---|---|---|---|---|
| 1 | `admin` | 管理员 | 全部权限 | 拥有所有权限 | 1（admin） | 41 |
| 2 | `user` | 普通用户 | 历史遗留，等同 viewer | **普通用户，可使用业务功能** ← 与注释矛盾 | 1（test2） | 1（overview） |
| 3 | `readonly` | 只读用户 | 历史遗留，等同 viewer | 只读用户，仅可查看数据 | **0** | 1（overview） |
| 4 | `test_role` | 测试角色 | **枚举中不存在** | 用于测试的角色 | **0** | 1（overview） |
| 25 | `operator` | 运维 | 资产读写 + 对账/报告/AI/EOL 覆盖，不可改系统配置 | 一致 | 1（t_op） | 18 |
| 26 | `viewer` | 观察者 | 只读：资产/告警/报告/知识 | 一致 | 1（t_view） | 16 |
| 27 | `auditor` | 审计人员 | 等同 viewer + 审计日志菜单 | 一致 | 1（t_aud） | 21 |

三点结论：

1. **具备"只读"语义的角色有 3 个**（`viewer` / `readonly` / `user`），职责重叠 → `DEF-6`。
2. 枚举注释声称 `user` 与 `readonly` "等同 viewer"，但库中 `user` 的描述是"可使用业务功能"——
   **代码注释与数据库事实已经不一致**，继续引用枚举会得出错误推论。
3. `readonly` 从未被任何业务代码引用且只有概览菜单，`test_role` 连枚举里都没有。**枚举不是事实源，数据库才是。**

### 1.3 权限校验原语（`app/core/permissions.py`）

| 原语 | 语义 | admin 放行 |
|---|---|---|
| `require_admin()` | 角色码必须为 `admin` | — |
| `require_role(*codes)` | 角色码 ∈ 白名单 | 是 |
| `require_menu_permission(path)` | 菜单可见性 | **否** → `DEF-8` |
| `require_button_permission(path, mark)` | 按钮级操作码 | 是 |

服务间认证另有 `require_api_key`（采集器 X-API-Key）、`require_scanner_api_key`（扫描器独立 Key）、
Webhook 的 IP 白名单 + 共享 Key——这三条属于机器身份认证，不在用户 RBAC 讨论范围内。

### 1.4 认证设计

JWT access（默认 2h）+ refresh（7d），携带 `iss/aud/iat/exp/jti` 标准声明，
`jti` 黑名单支持撤销，登录有图形验证码 + 失败锁定（次数达阈值自动置 `LOCKED`）。
每次请求回查数据库 User，**角色变更对旧 token 立即生效**——这是好设计，避免了
"改了权限要等用户退出重登"的常见坑。

### 1.5 WebSocket 鉴权

`/ws/notifications` 无法使用 `Depends()` 标准形式，实现为从 **query string** 取
`?token=<JWT>`，复用 `core.auth.verify_token`（含 `iss/aud/exp/jti` 黑名单校验）。
**有鉴权，但传参方式不安全** → `DEF-12`。

## 二、现状盘点（代码层 + 运行实例）

### 2.1 权限原语实际调用分布

对 `app/api/` 全目录统计 `Depends(...)` 形式调用：

| 原语 | 调用次数 | 说明 |
|---|---|---|
| `get_current_user` | 97 | 仅校验"已登录"，**不含任何角色/权限约束** |
| `require_admin` | 32 | 集中在 roles/departments/menus/notifications |
| `require_role` | 26 | 集中在 asset_lifecycle/behavior_profile/scan_tasks/audit_logs |
| `require_button_permission` | 7 | 仅 4 个模块 |
| `require_menu_permission` | 2 | 仅 users.py 的列表/详情 |
| `require_active_user` | 1 | 几乎未使用 |
| `require_api_key` | 2 | 采集器通道 |
| `require_scanner_api_key` | 4 | 扫描器通道 |

**97 处"只验登录" vs 65 处"真正验权限"，且后者高度集中在后期新建模块。**
分布本身就是证据：早期模块普遍没有鉴权意识，后期模块开始补，但没有回头补齐前面欠的账。

### 2.2 完全无鉴权的路由模块：10 个

以下模块文件内**没有任何** `Depends(...鉴权依赖)`，注册时也未挂 router 级
`dependencies`（对照 `app/api/__init__.py`）：

| # | 模块 | 前缀 | 无鉴权端点 | 写操作 |
|---|---|---|---|---|
| 1 | `alerts.py` | `/alerts` | `GET /`、`/statistics`、`/trend`、`/top-assets`、`/{id}`、`POST /{id}/create-incident` | **有**（建事件） |
| 2 | `alert_digests.py` | `/alerts` | `GET /groups` 等 9 个、`POST /snapshot/generate`、`POST /digest/generate`、`POST /groups/{fp}/triage`、`POST /groups/{fp}/create-incident` | **有**（治理动作） |
| 3 | `incidents.py` | `/incidents` | `GET /`、`GET /{id}`、`POST /`、`PUT /{id}`、`POST /{id}/timeline` | **有**（增删改） |
| 4 | `assets.py` | `/assets` | `POST /sync/from-wazuh`、`GET /` 系列、`POST /`、`PUT /{id}`、`DELETE /{id}` | **有**（资产增删改） |
| 5 | `asset_ports.py` | `/assets` | 6 个含 `POST/PUT/DELETE` | **有** |
| 6 | `asset_tags.py` | `/assets` | 7 个含 `POST/PUT/DELETE` | **有** |
| 7 | `asset_incidents.py` | `/assets` | `POST /{aid}/incidents/{iid}`、`DELETE /{aid}/incidents/{iid}` | **有** |
| 8 | `ai.py` | `/ai` | `POST /analyze-alert`、`/explain`、`/analyze-alert/batch`、`GET /analysis/{id}` | 有（消耗 LLM 额度） |
| 9 | `sync.py` | `/sync` | `POST /tasks/manual` 等 3 个 | **有**（触发同步） |
| 10 | `dashboard.py` | `/dashboard` | `GET /trend`（`GET /summary` 已鉴权） | 无，但泄露告警簇趋势 |

**计数口径说明（v1.1 修订）：**

- **`ws.py` 不计入**——它有鉴权，只是不走 `Depends()`。见 §1.5 与 `DEF-12`。
- `public.py`（显式设计为公开）、`metrics.py`（Prometheus 抓取）属**预期无鉴权**，不计入缺陷。
- `sca.py` 定义了 router 但**未在 `app/api/__init__.py` 注册**，是死代码 → `DEF-17`。
- `auth.login/captcha/refresh`、Webhook IP/签名、采集器/扫描器 API Key、内部 Service Token 属于显式公开或机器身份通道，不按 JWT 用户路由统计。

有 router 级保护的只有 3 个：`knowledge`、`vulnerabilities`、`task_observability`，
且均为 `dependencies=[Depends(get_current_user)]`——**只到登录态，无角色区分**，
这正是 `DEF-2` 的成因。

### 2.3 实测证据 A：匿名维度

运行实例未携带任何 `Authorization` 头的请求结果：

| 请求 | 响应 `body.code` | 结论 |
|---|---|---|
| `GET /api/v1/incidents/` | **200**，返回真实事件（含 `[漏洞] CVE-2026-64320 @ pve-ubuntu04-k3s-work1`） | 数据泄露 |
| `GET /api/v1/alerts/?limit=1` | **200**，返回真实 Wazuh 告警明细 | 数据泄露 |
| `GET /api/v1/assets/?limit=1` | **200**，返回资产名/内网 IP/网段 | 数据泄露 |
| `GET /api/v1/alerts/groups` | **200**，返回 41 个告警组 | 数据泄露 |
| `GET /api/v1/users` | 401 Not authenticated | 正常 |
| `GET /api/v1/dicts` | 401 Not authenticated | 正常 |
| `GET /api/v1/menus/tree` | 401 Not authenticated | 正常 |
| `GET /api/v1/system-configs/` | 401 Not authenticated | 正常 |

**对照组是关键**：同样一台服务、同一套原语，挂了鉴权的模块精确返回 401。
这说明**鉴权机制本身是好的，缺的是覆盖面**。

> ⚠️ 排查提示：本服务 HTTP 状态码恒为 200，鉴权失败体现在 **body.code=401/403**。
> 用 curl 或监控判断鉴权是否生效时，必须看 body，不能看状态码。

### 2.4 实测证据 B：角色维度

以临时账号（建后即删）验证同一端点的角色差异。**判别方法**：使用能在业务逻辑层
失败、而非 Pydantic 层失败的载荷——用非法载荷触发 422 **无法证明**"未被权限拦截"，
因为 Pydantic 校验先于鉴权依赖执行。

| 操作 | viewer（只读） | operator（运维） | 匿名 | 只读期望 |
|---|---|---|---|---|
| `GET /assets/` | 200 | 200 | 200 | 200 ✅ |
| `GET /incidents/` | 200 | 200 | 200 | 200 ✅ |
| `POST /assets/` **合法载荷** | **200 创建成功** | 200 | **200 创建成功** | 403 ❌ |
| `POST /alerts/{id}/create-incident` | **200 真实落库** | — | — | 403 ❌ |
| `POST /sync/tasks/manual` | **200 真实触发** | — | — | 403 ❌ |
| `DELETE /assets/{不存在}` | 404 抵业务逻辑 | 404 | — | 403 ❌ |
| `PUT /incidents/{不存在}` | 404 抵业务逻辑 | 404 | — | 403 ❌ |
| `GET /audit-logs` | **403 拦截** | **403 拦截** | 401 | 403 ✅ |

**最后一行是全文最关键的反证**：`GET /audit-logs` 挂了 `require_role("admin","auditor")`，
实测结果 viewer 403、operator 403、auditor 200——**角色区分精确生效**。

由此得到本文的核心判断：

> **权限模型没有写错，错在覆盖面。**
> 当前是正向授权（allow-list）模型：你声明了 `require_*` 我才拦，漏配即放行。
> 安全产品的正确默认值应当相反。

## 四、整改路线图

按"**先机制后补全**"排序。先建立不会漏的机制，再逐个补声明——
反过来做的话，补到第 N 个端点时第 1 个已经漏了。

## 五、结论

**模型设计 75 分，落地执行 30 分。**

分层是清晰的（五表 RBAC + 四种校验原语 + 规范 JWT），执行是断层的（10 个模块零鉴权、
97 处只验登录，且测试门禁不阻塞）。问题不在于设计错了，而在于系统允许“忘记写鉴权”——
`GET /audit-logs` 的实测反证说明，只要写了就精确生效；真正致命的是那些没写的。

因此根治路径只有一条：**把鉴权从开发者的自觉动作，变成框架的默认行为**
（`WO-1` 读侧默认鉴权 + `WO-2` 写侧默认拒绝 + CI 门禁）。在这个翻转完成之前，
`viewer` / `readonly` 这类角色只是标签，不是约束。
