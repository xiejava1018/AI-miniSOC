## 1. 背景与问题清单（已验证基线）

### 1.1 业务口径

依据 GB/T 22240-2020《网络安全等级保护定级指南》：**定级对象是"信息系统"（业务系统），
不是单台资产**。定级对象须同时具有唯一安全责任主体、相对独立业务、相互关联的多个资源。
单台服务器只是定级对象的组成部分。因此：

- `soc_business_systems.protection_level` 是**权威源**（模型注释已声明）
- `soc_assets.protection_level` 应为**派生只读展示**（继承结果）
- 一级系统自主保护无需备案；二级及以上才向公安备案（§3 D5）

## 3. 核心设计决策（D1–D9）

> 实施时若发现现实与决策前提冲突，停下来在 tracker 登记冲突，不要静默改道。

**D1 · 权威与派生**：`protection_level` 权威源 = 业务系统。资产侧是缓存性质的派生值，
唯一合法写入路径 = 传播引擎（source=inherited 时）或人工显式设定（source=manual 时）。
API 不阻止人工写资产等级（合法覆盖场景存在，如跨系统共用堡垒机单独定级），但写即标记 manual。

**D2 · 只传播 protection_level 一个维度**。理由（第一性）：
- protection_level 是合规锚点，语义上属于定级对象，必须跟随系统；
- data_sensitivity 进 F1.1 风险评分——后端传播会静默触发全量资产评分漂移；
- business_impact 驱动 SLA，但资产级 BIA 常有独立判断（一台机器可同时服务核心与一般系统）。
前端 `pickStrictest` 的三维度表单便利**保留不动**（它只影响本次提交的初值，不持续传播）。

**D3 · 就高规则（max-rank）**：资产挂多个系统时取 `max(等级)`。与实务惯例一致
（同时服务两个定级对象时按较高者的防护要求）。档位序：`level_5 > level_4 > level_3 > level_2 > level_1`。

**D4 · source 标记与切换语义**：

| 场景 | source 变化 |
|---|---|
| 新建资产（POST /assets） | `manual`（表单值即人工提交，含 pickStrictest 预填） |
| 人工 PUT 资产且 payload 含 `protection_level` | → `manual`（单向锁定，直到显式切回） |
| 人工 PUT 资产但 payload 不含该字段 | 不变 |
| link 挂接系统（`PATCH .../systems` 等） | 若原值 source=`manual` **且用户未在请求中显式要求继承** → 不传播不改动；否则传播并置 `inherited` |
| unlink 后资产无任何系统 | 值**保留**，source → `manual`（诚实降级：继承来源已消失，留给人工复核，不静默降回 level_2） |
| 系统等级变更 | 仅重算 source=`inherited` 的成员资产 |

「link 时如何让 inherited 生效」的落地：link 请求体加可选 `inherit: bool = None`；
`None` = 仅当资产当前已是 `inherited` 才重算；`true` = 传播并置 inherited（新建资产表单默认传 true，
与前端 pickStrictest 行为对齐）；`false` = 永不传播。存量 73 资产迁移后全部 `manual`（§9 backfill），
**绝不自动改动存量数据**。

**D5 · 等保档位与备案义务提示**：建议引擎输出 `level_1` 时，message/basis 中明确标注
「等保一级：自主保护，无需备案」；`level_2` 起标注「需向公安机关备案」。
默认值 `level_2` 的语义在 UI 文案中说明「默认值≠已定级」（配合 rating_status）。

**D6 · 建议与确认分离**（S4 红线的技术形态）：

```
rating_status 状态机（单向主线，可回退到 suggested）：
  unrated ──(引擎运行)──> suggested ──(人工在确认 UI 或 PUT protection_level)──> confirmed
     └──────────(人工直接定级，未走建议)──────────────> confirmed
```

- 引擎只写 `suggested_protection_level` + `suggestion_basis`，**永不写 `protection_level`**
- 确认动作 = PUT 端点显式带 `protection_level`（或未来确认工作台按钮），写
  `rating_status='confirmed'` + `rating_confirmed_by/at` + **触发 D1 传播**

**D7 · 建议引擎形态：确定性二维矩阵（GB/T 22240 简化版）**：

受侵害客体 × 侵害程度矩阵（法定原表）：

| 客体 \ 程度 | 一般损害 | 严重损害 | 特别严重损害 |
|---|---|---|---|
| 公民、法人和其他组织的合法权益 | 1 级 | 2 级 | 2 级 |
| 社会秩序、公共利益 | 2 级 | **3 级** | 4 级 |
| 国家安全 | 3 级 | 4 级 | 5 级 |

输入代理映射（**必须**写进 suggestion_basis，诚实标注是近似）：

| 现有字段 | 代理维度 | 映射 |
|---|---|---|
| `data_sensitivity` | 受侵害客体（代理） | negligible/low → 公民法人；medium/high → 社会秩序；extreme → 国家安全 |
| `business_impact` | 侵害程度（代理） | ignorable/auxiliary → 一般；normal/important → 严重；core → 特别严重 |

佐证材料（进 basis.evidence）：成员资产数、role 分布、`exposure_level=public` 的资产数。
输出结构见 §6.2。

**D8 · role 枚举走 soc_dicts 字典**（沿用 `protection_level` 的 dict_type 先例）：
`dict_type='asset_business_role'`，值 `web/app/db/mq/cache/gateway/lb/other`。
存量 NULL 保留（语义=未指定），不强制回填。schema 层校验：传了就必须在枚举内。

**D9 · 删除防护**：`asset_count > 0` 的系统，DELETE 必须带 `?force=true` 才执行；
不带则 400（envelope code=400）返回成员数提示。删除流程 = 解绑全部 → 逐资产重算（D4 unlink 规则）→ 删系统。
force 删除在审计 metadata 中记录 force=true 与成员数。

## 5. 继承传播服务设计（T4 核心）

### 5.1 新文件 `src/backend/app/services/protection_level_propagation.py`

```python

纯函数 + 显式 DB 会话操作。调用方（API 端点）传入自己的 db session，
传播与业务动作同事务提交——绝不开独立事务，避免"link 成功但传播失败"的分裂态。

档位序（D3）：level_5 > level_4 > level_3 > level_2 > level_1
"""
PL_RANK = {"level_1": 1, "level_2": 2, "level_3": 3, "level_4": 4, "level_5": 5}

def strictest(levels: list[str]) -> str: ...

def compute_inherited_level(db, asset_id) -> str | None:
    """返回该资产所有关联系统中最高等级；无关联返回 None。"""

def recompute_asset(db, asset_id, *, allow_manual: bool) -> dict:
    """按 D4 语义重算单个资产。返回 {asset_id, changed, old, new, source}。
    - allow_manual=True（link 显式 inherit=true）：无条件传播并置 source='inherited'
    - allow_manual=False：仅 source='inherited' 的资产重算
    - 无关联系统：值保留，source 置 'manual'（D4 unlink 规则）

def propagate_system_level_change(db, system_id) -> dict:
    """系统等级变更后，批量重算其所有 source='inherited' 成员资产（就高，可能被
    另一个更高等级系统顶住而不变）。返回 {affected, changed, details}。
    循环内逐资产 recompute（资产数 ≤ 数十，无性能问题；不写 bulk UPDATE 保审计粒度）。
    """
```

### 5.2 触发点接线（全部在现有端点内，不新增传播专用端点）

| 端点 | 位置 | 接线 |
|---|---|---|
| `POST /business-systems/assets/{asset_id}/systems` | `api/business_systems.py:277` | commit 前调 `recompute_asset(db, asset_id, allow_manual=data.inherit is True)` |
| `DELETE .../systems/{system_id}`（unlink） | 同文件 `:316` | commit 前调 `recompute_asset(db, asset_id, allow_manual=False)` |
| `PUT /business-systems/{system_id}` | 同文件 `:183` | payload 含 `protection_level` 且值有变 → `propagate_system_level_change` + 置 `rating_status='confirmed'` + `rating_confirmed_by=当前用户`（D6） |
| `DELETE /business-systems/{system_id}` | 同文件 `:211` | D9：force 检查 → 解绑前收集成员 asset_id 列表 → 解绑后逐个 `recompute_asset(allow_manual=False)` → 删系统 |

**事务边界**：传播调用与业务写同一个 `db.commit()`。传播抛异常 → 整体回滚（宁可 link 失败也不分裂）。

**审计**：现有 `@log_audit` 记录主动作；传播的资产级变更作为一条汇总审计
（`action='UPDATE'`, `resource_type='asset_protection_propagation'`,
metadata={system_id, affected, changed, details}）在端点内显式落链——不让批量变更游离在 hash 链外。

**线程模型**：以上全在 API 请求上下文（FastAPI 线程池），无 event-loop 阻塞问题，
不涉及 CLAUDE.md §4.5 的 to_thread 模式。图谱 builder 不需要改（它读资产现值，传播后自然生效）。

  > ```python
  > if "protection_level" in update_data and update_data["protection_level"] != asset.protection_level:
  >     asset.protection_level_source = "manual"
  > ```
  > 在 `update_data` 应用 setattr 之前比较（用 DB 现值），跟现有 criticality 垫片逻辑并列。
  > 前端**不需要**改成增量提交——后端比较比前端 diff 可靠（前端还可能有其它调用方）。

  同样的「值有变才触发」原则已用于 §5.2 的系统 PUT 接线（payload 含 protection_level 且值有变），
  两处语义对称。
- `POST /assets`（create）：新资产默认 `manual`（列 server_default 已保证，无需改 create 逻辑，
  但 schema 不得意外把 source 写成 inherited）
- `schemas/asset.py`：`AssetUpdate` **不加** source 字段（source 只能由传播引擎或上述端点逻辑写，
  不开放给前端直接写——防绕过）。响应 schema（AssetResponse / list 返回）**加**
  `protection_level_source` 字段供前端展示来源徽标。

## 13. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 传播误改存量资产等级 | D4 存量全 manual + 传播只碰 inherited；迁移 backfill 不触碰资产表数据 |
| link 请求 body 新增字段破坏旧前端 | `inherit: bool = None` 可选，旧调用（不传）语义=仅 inherited 资产重算=现状无操作，向后兼容 |
| rating_status 回填误判（人工定过 level_2 的系统被标 unrated） | 诚实方向的误差（提示复核而非假装已确认）；UI 提供「标记已确认」快捷动作 |
| 建议被当法定结论 | basis 强制 approximation_note + UI 展示近似声明 + 引擎永不写 protection_level 三重防线 |
| 迁移在生产失败 | 先备份 102 本机 PG（当前无备份机制，CLAUDE.md §7 已知项）；迁移全幂等可重跑；downgrade 对称 |
| 图谱/画像消费新字段报错 | 响应只增不改；builders 读现值不受影响；回归测试覆盖 |
| 传播端点性能（大系统成员多） | 逐资产循环 + 单事务；资产数级 <100 无风险；>500 时再优化（登记 TODO，不过早优化） |
