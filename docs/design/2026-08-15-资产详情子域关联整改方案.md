## 0. 一句话结论

资产详情页"应用清单 / 漏洞 / 端口 / 基线 / 告警 关联不上"的**根因不是架构缺陷**，而是：

1. **三个 Tab 在脆弱性 / SCA 后端落地后从未接线** —— 前端仍是 `<ElEmpty>` 占位（注释写着"待 Phase X 接入"），但后端数据早已存在；
2. **安全摘要卡把 Wazuh 指标硬编码成 0 / null** —— `asset_summary.py` 第 101–114 行把 `vuln_critical / applications / sca_pass_rate` 写成占位常量，导致"高危 CVE / 应用数 / SCA 合规率"永远显示 0 / 待接入（摘要卡在"说谎"）；
3. **应用清单模块从头缺失** —— 无表、无模型、无 API、无同步、无前端（只有 `asset_summary.py` 里一处 `soc_wazuh_packages` 的注释占位）；
4. **端口 ↔ 漏洞关联是自由文本弱关联** —— `soc_asset_ports.vulnerability` 是手工填的字符串，从未被真实 CVE 回填。

**统一关联键 `soc_assets.wazuh_agent_id` 早已存在且贯通了告警**，所以架构是健康的，只需要"接线 + 补缺失模块 + 强化联动"。

> **⚠️ 2026-08-15 评审补充（数据事实修正）**：
> 1. **主关联键本身有数据质量问题**——实测发现 `wazuh_agent_id=002` 同时挂在两个资产上（`wazuh-agent-test-002` 和 `fnos-vm-ubuntu01`），会导致漏洞/告警/应用数据互相串；另有 40+ 条同 IP 重复资产（manual + tplink 双记录）。详见新增 §1.5，需在 M0 前修复。
> 2. **应用清单数据源已存在**——OpenSearch 已有 Wazuh 实时同步的 `wazuh-states-inventory-*` 索引（据评审实测 packages / ports / services / processes 各数千至万条，**具体条数待真实环境复核**），M3 无需新建表+同步服务，改为直查。详见 §3 M3 修订。

## 2. 关联键模型（已具备，复用即可）

```
                 soc_assets.wazuh_agent_id  ← 主关联键（master key）
                          │
        ┌─────────┬───────┼──────────┬──────────┐
        │         │       │          │          │
      告警       漏洞      SCA基线    端口        应用清单
   (AlertQuery) (asset_  (Vulner-   (AssetPort) (本期新建
                vulnerabilities) ability   按 agent
                按 asset_id)  type=sca 按 asset_id) 解析 asset_id)
```

- **告警**：`AlertQueryService.get_alert_statistics(agent_id=asset.wazuh_agent_id)` ✅
- **漏洞 / SCA**：`opensearch_scap_sync` / `wazuh_sca_sync` 同步时以 `Asset.wazuh_agent_id == agent_id` 解析出 `asset_id`，再写 `soc_asset_vulnerabilities` ✅
- **应用清单**：本期新建同步，同范式按 `wazuh_agent_id → asset_id` 解析 ✅

> 结论：所有子域都围绕 `wazuh_agent_id` 这一把钥匙与资产关联，方案无需新增关联字段，只需把"钥匙→各房间"的门打开（接线）或"建新房"（应用清单）。

> **⚠️ 评审修正**：上述"钥匙贯通"的前提是钥匙本身干净。§1.5 实测发现 agent_id 双挂/重复资产问题，需先修再接线，否则 M1-M3 的数据会串资产。

### 1.5 数据质量问题（评审补充，M0 前置）

实测数据库（2026-08-15，85 个资产）发现：

| 问题 | 实例 | 影响 | 修复 |
|---|---|---|---|
| **agent_id 双挂** | `wazuh_agent_id=002` 同时挂在 `wazuh-agent-test-002`(192.168.0.101) 和 `fnos-vm-ubuntu01`(192.168.0.30) | 漏洞/告警/应用数据互相串，资产详情页展示错误数据 | 保留正确的挂载（与 Wazuh agent 注册信息 IP 匹配者），清除另一处；给 `soc_assets.wazuh_agent_id` 加唯一部分索引（WHERE wazuh_agent_id IS NOT NULL） |
| **同 IP 重复资产** | 40+ 条 manual + tplink 双记录（如 `192.168.0.40` 两条、`192.168.0.20` 两条） | 资产列表膨胀、详情页入口分裂 | 制定合并策略（保留 wazuh 来源 > tplink > manual 优先级，合并标签/端口后去重） |
| **无 Agent 资产的空态** | ~40 个 tplink/manual 资产无 `wazuh_agent_id` | 漏洞/基线/应用 Tab 永远为空，用户误以为故障 | 前端统一空态文案："该资产无 Wazuh Agent，此类数据不适用"（不是空表格），见 M1/T3 |

修复工单：**T0a**（agent_id 去重+唯一索引）、**T0b**（重复资产合并，可延后但不阻塞 M0-M2）。

## 3. 整改目标与里程碑

按 **"先接通已有数据（低投入高回报）→ 补齐真正缺失模块（应用清单）→ 强化跨域联动"** 的顺序推进，避免一上来就造大模块。

### M0 · 摘要卡去伪（后端小改，高优先级）
- 改 `asset_summary.py`：真实统计
  - `vuln_critical / vuln_high / vuln_total`：查 `soc_asset_vulnerabilities` JOIN `Vulnerability(type='scap')`，按 `asset_id` + `status='open'` 计数。
  - `applications`：查 `soc_asset_applications`（M3 建表后）计数。
  - `sca_failed`：查 `AssetVulnerability` JOIN `Vulnerability(type='sca')` 且 `status='open'` 计数；`sca_pass_rate` 维持 `None`（合规率本期不算，见 §5）。
- 前端 `MetricCard` "SCA 合规率" 改判：当 `sca_pass_rate === null` 时改显 **"不合规 N 项"**（`sca_failed`），sub-label `待接入合规率(P5)`；"应用数"卡在 M3 前保持 0，M3 后自动填充。

### M1 · 漏洞 Tab 接通（前端为主，需少量后端补 risk_score）
- 复用已有端点 `GET /api/v1/vulnerabilities/asset-vulnerabilities?asset_id={id}`。前端工具函数 `getAssetVulnerabilities` 已存在（`src/frontend/src/api/vulnerabilities.ts`），但**当前仅被漏洞 LIST 页的"受影响资产"弹窗使用，资产详情页漏洞 Tab 仍为 ElEmpty，需接入此 Tab**。
- 表格列：`cve_id / title / severity(中文化) / cvss_score / risk_score(评审补充) / status / sla_status / detected_at`。
  - **评审补充·需补后端**：新增 **AI 风险评分列**（`risk_score`）。注意：主 `list_*` 端点（`list_vulnerabilities` L430-461）已返回 `risk_score`（用 `VulnerabilityAIService.calculate_risk_score` 计算），但本资产端点 `list_asset_vulnerabilities`（L513-581）**当前不返回该字段**，需在 M1 后端补算（复用同范式），并非"已提供同款字段"。前端 `AssetVulnerability` 接口亦需补 `risk_score`。
- 行操作：**"生成事件"** 按钮复用 `createIncidentFromVulnerability`（漏洞→事件闭环在详情页即可发起）。
- 可选后端增强：给 `list_asset_vulnerabilities` 增加按 `Vulnerability.type` 过滤的能力（见 T4），便于 M2 复用同一端点。
- **评审补充·空态处理**：`wazuh_agent_id` 为空的资产，Tab 显示"该资产无 Wazuh Agent，漏洞数据不适用"提示块（ElEmpty + 说明文案），不发无效请求。

### M2 · 基线 Tab 接通（前端为主）
- 同一端点加 `type=sca` 过滤（后端 1 行），展示**不合规配置项**：`policy_id / title / description / remediation / status`。
- 这是"基线核查"的正确语义：当前数据 = 未通过的安全配置项（SCA failed）。

### M3 · 应用清单模块（评审修订：OpenSearch 直查，不做落库同步）

> **评审修订说明**：原方案为"新建表 + Alembic 迁移 + Wazuh API 同步服务"（4 工单/约 2 天）。实测发现 **OpenSearch 已有 Wazuh 实时推送的 states 清单索引，无需落库**，改为直查方案（1 个查询服务 + 1 个 API，约 0.5 天）。

**已验证的数据源**（2026-08-15 实测）：

```
wazuh-states-inventory-packages-*   17887 条（单 agent，含 pypi/deb 多类型）
wazuh-states-inventory-ports-*        911 条（M4 复用）
wazuh-states-inventory-services-*    1713 条
wazuh-states-inventory-processes-*   3569 条
```

文档结构：`{agent: {id}, package: {name, version, size, type, path}, wazuh: {...}}`，`agent.id` 可直接解析资产。

**修订后实施内容**：
- **查询服务** `WazuhInventoryService`：直查通配索引 `wazuh-states-inventory-packages-*`，按 `{"term":{"agent.id": agent_id}}` 过滤（与 `opensearch_scap_sync.py` 查 `wazuh-states-vulnerabilities-*` 同范式）；支持 search（包名模糊）/ 分页；复用既有的内联 `httpx.Client` OpenSearch 客户端范式（`alert_query.py` / `opensearch_scap_sync.py`，**项目中无独立 `opensearch_client.py` 模块**）。
- **API**：`GET /api/v1/assets/{asset_id}/applications`（参数 search/skip/limit；内部 `asset → wazuh_agent_id → agent.id` 解析）。
- **前端**：`asset.ts` 加 `getAssetApplications`；详情页"应用清单"Tab 接真实数据（表格：软件名 / 版本 / 类型 / 大小 / 安装路径）。
- **摘要卡 applications 计数**：走 OpenSearch `_count` API，加 5 分钟内存缓存（避免每次详情页都打远端）。
- **无 Agent / agent 未开包清点**：返回空列表 + 前端友好空态（"该资产无 Wazuh Agent" / "Agent 未开启软件包清点"）。

**与原方案对比**：砍掉 T6（模型+迁移）、T7（同步服务+wazuh_client 扩展）；数据实时性反而更好（states 索引即 Wazuh 推送的最新状态）；代价是依赖 OpenSearch 可用性——告警 Tab 本就如此，无新增架构耦合。

> 若后续需要离线分析/历史趋势（包变更审计），再考虑落库方案，届时可复用同步处理器的 upsert 范式。

### M4 · 端口 ↔ 漏洞 双向关联（增强）
- **漏洞 Tab 每行展示"关联端口"**：按 `Vulnerability.affected_packages` / `title` 与该资产 `AssetPort.service` 做 best-effort 匹配（如 service=MySQL ↔ 包 mysql / CVE 描述含 mysql）。
- **端口 Tab 的"漏洞"列**：把自由文本 `row.vulnerability` 换成"本资产真实漏洞中与该端口 service 匹配的项"（来自 M1 同一份资产漏洞数据），点击可跳转漏洞 Tab 对应行。
- **评审补充·端口双源合并**：`wazuh-states-inventory-ports-*`（911 条，带监听地址/进程/协议详情）与本地 `soc_asset_ports`（手动/nmap）合并展示，加"来源"列（Wazuh / 本地）；Wazuh 端口数据走 M3 同一个 `WazuhInventoryService`。
- 备注：精确"端口↔CVE"映射依赖 Wazuh 基于包的漏洞检测，列为 **P5 增强**；本期采用服务名匹配的近似关联，已能体现"关联"。

### M5 · 跨域闭环入口（可选增强）
- 告警 Tab 行内增加"查看关联漏洞"入口（同 agent + 同时间窗）。
- 漏洞 / SCA 行"生成事件"已备（M1）。
- **评审补充·告警 Tab 自身增强**（原文档标"正常"跳过，实际体验不足）：
  - 时间范围切换（24h / 7d / 30d）
  - 等级筛选（L1-L16 分档）
  - 分页（当前固定 20 条无翻页）
  - 行点击跳转告警管理页并携带过滤参数（与告警管理页共享查询语义）

## 5. 风险与待确认决策

1. **SCA 合规率本期不算**：当前只存 failed 检查项（无 passed），真实合规率需同时落库 passed 计数 → 列入 **P5**。本期改显"不合规 N 项"，避免误导。
2. ~~**应用清单依赖 Wazuh syscollector 包扫描**~~ **（评审修订）**：改用 OpenSearch states 索引后，此风险变为"依赖 OpenSearch 可用性"——与告警 Tab 同架构，无新增耦合；agent 未开包清点时 states 索引同样无数据，前端空态文案不变。
3. **端口↔漏洞为 best-effort 匹配**：服务名字符串匹配可能漏/误，仅作关联示意，精确映射 P5。
4. **`sca_failed` 字段**：后端 `asset_summary.py` 已在返回结构中含 `sca_failed`（当前恒0），前端 `AssetSummary` 类型需确认已含该字段（若缺失则补，属对齐而非全新字段）；M0 接通真实计数后前后端自然对齐，并保留 `sca_pass_rate: null` 兼容。
5. **路由注册**：应用清单 API 挂在 `assets.py`（已有 `/{asset_id}/ports`、`/tags` 范式），无需新菜单；详情页是既有路由，无需改 `asyncRoutes`。
