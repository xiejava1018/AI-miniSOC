## 一、问题定义（Why）

**业务诉求**：一个只看不改的账号角色。运营汇报、客户旁听、外部审计、合规留痕等场景下，
交付出去的账号必须保证"能看不能动"。

**当前事实**：AI-miniSOC 有"只读"这个概念，但**不具备只读的能力**。
只读账号当前可以创建资产、创建安全事件、触发资产同步——见诊断基线 §2.4 实测证据 B。

**PM 判断**：这不是"缺个角色"的问题，是"**鉴权默认放行**"的问题。
补角色解决不了（`readonly` 角色早已存在且 0 人使用），收默认策略才能解决。

**决策依据**：`GET /audit-logs` 挂了 `require_role` 后，viewer/operator 精确 403、auditor 200。
原语能力已验证可用，缺的是覆盖面与默认值 → 本 PRD 的范围是**收敛默认值**，而非重造模型。

## 二、用户故事与场景

> 作为 **安全运营负责人**，我希望 **给外部审计/观摩人员开一个只读账号**，
> 以便 **他们能查看告警、资产、事件的全部数据，但无法创建、修改或删除任何东西**。

| 场景 | 角色 | 需要 | 当前是否成立 |
|---|---|---|---|
| 客户到机房观摩，需现场登录看大屏与明细 | 客户方人员 | 全量查看，零写入 | ❌ 可写 |
| 外部合规审计需自查留痕 | 审计方 | 查看 + 审计日志 | 部分（审计菜单本身有权限，但业务Endpoint 仍可写） |
| 内部向上级汇报，临时开号 | 管理层 | 查看 | ❌ 可写 |
| 值班交接只读备查 | 运营 | 查看 | ❌ 可写 |

## 四、验收标准（Definition of Done）

全部必须**可自动化测试**，不接受人工抽查作为通过条件。

| ID | 标准 | 验证方式 | 覆盖 DEF |
|---|---|---|---|
| **AC-1** | `viewer` 对所有**用户态业务** `POST/PUT/PATCH/DELETE` 请求返回业务码 403；`POST /auth/logout` 是唯一允许的写例外，机器通道不参与用户态测试 | 路由级授权扫描 + 代表性合法载荷集成测试；断言 HTTP 200 且 `body.code==403` | DEF-2 |
| **AC-2** | 未认证或携带无效凭证请求非白名单端点被拒绝：人类路由 `body.code==401/403`，机器路由按其 Key/Token 契约返回 401/403 | 从 OpenAPI 枚举路由；白名单精确到 method+path | DEF-1 |
| **AC-3** | 新增 API 未登记路由分类、写操作未带显式授权标记、或新增未登记例外时，CI 直接失败 | 独立阻塞步骤运行 `tests/security/test_route_authorization.py`；不受现有 advisory pytest 影响 | DEF-1, DEF-2, DEF-18 |
| **AC-4** | `viewer` 可见菜单严格等于版本化 `role_menu_baseline` 中 viewer 的期望集合 | 用测试库执行种子脚本后比对 `/menus/tree` 与基线，不少于不超出 | DEF-5 |
| **AC-5** | `viewer` 的所有被拒写尝试产生 `soc_audit_logs` 记录，字段含用户、路由、方法、IP、失败原因；完整成功写审计仍归 `WO-7` | 授权拒绝审计测试覆盖默认拒绝与显式 `require_*` 拒绝 | DEF-2, DEF-13（部分） |
| **AC-6** | 存量角色行为符合预期：`viewer` 只读，`operator/user` 可执行业务写但不可改系统配置，`auditor` 只读业务与审计日志，`admin` 全量 | 五角色对照测试（admin/operator/user/viewer/auditor） | DEF-2, DEF-5 |
| **AC-7** | 受管角色权限矩阵可由幂等脚本重建：测试库清空受管角色 `soc_role_menus` 后执行脚本两次，结果均与版本库基线一致；自定义角色不被修改 | 种子脚本 dry-run/drift/apply 三模式测试 | DEF-5 |

> 二者分别约束"当前状态"与"未来不倒退"，缺其一都只是暂时的。

## 五、方案范围

本期实现诊断基线的**全部 Now 项**，即 `WO-1` ~ `WO-4`。四项之间依赖关系如下：

```
WO-1 读侧默认鉴权 ──┐
WO-2 写侧默认拒绝 ──┼──► 只读能力成立 ──► 四项 Now 全绿方可结项
WO-3 is_admin 收口 ─┤
WO-4 角色矩阵落地 ──┘
```

| WO | 本 PRD 内的交付要求 |
|---|---|
| **WO-1** | 人类业务 router 级统一挂 `get_current_user`；公开、Webhook、API Key、Service Token、扫描器通道进入 method+path 分类表；CI 比对 OpenAPI 路由与分类声明 |
| **WO-2** | **核心**：方法感知默认写保护；`viewer/readonly` 先被硬拒绝，未标记授权的写路由也被拒绝；每个业务写路由补显式 `require_admin/require_role`，例外精确登记；拒绝动作落审计；CI 门禁独立阻塞 |
| **WO-3** | `is_admin` 单一定义；`users.py` 五处手写 if 全部替换为声明式依赖 |
| **WO-4** | 收敛只读角色的同时，从当前迁移头导出全量角色×菜单基线并按终态归一：`user=operator` 的业务授权、`viewer/auditor` 去写按钮、`readonly/test_role` 停用；脚本按 `role.code` 和父子菜单定位符解析，不硬编码 ID；支持 `--dry-run/--check/--apply`，不自动修改用户角色 |

> **`WO-4` 的完整矩阵（含非只读角色）属于本 PRD 范围**，不可裁剪——
> 只补只读角色会把矩阵做成半张表，`viewer` 与 `operator` 的边界依然靠猜。

## 六、Non-goals（本期明确不做）

| 不做 | 原因 | 归属 |
|---|---|---|
| 对象级 ACL（"某个人能改某个具体资产"） | 另一套体系，本期只做功能级权限 | 独立立项 |
| 字段级脱敏（只读账号看不到管理员手机号等） | 属数据权限范畴 | `WO-8` |
| 数据范围（全量/本部门/本人） | 依赖 `data_scope` 设计与查询层改造 | `WO-8` |
| 全量修正 `soc_menus.path` 相对名语义（跨父越权） | 改动面大，与本期默认值翻转叠加会放大回归风险。V1 先用“viewer/readonly 业务写硬拒绝”切断该缺陷对只读红线的影响 | `WO-5`，下期 |
| WebSocket 鉴权改造 / 会话管理 / 令牌黑名单持久化 | 不阻断只读能力成立 | `WO-6`，下期 |
| MCP 工具层 RBAC | 依赖 `WO-2` 稳定后再接同一套原语 | `WO-9` |
| 前端 `v-auth` 指令在业务页全面落地 | 前端 hide ≠ 后端 deny，本期先保证后端不可绕过 | `WO-9` |

**边界原则**：本期只保证"只读账号**打不进写操作**"。
按钮灰不灰是体验问题，接口拦不拦是安全问题——**先锁接口，再谈界面**。

## 七、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| `WO-2` 翻转默认值误伤在用接口 | 部分功能对 403 | 上线前跑全路由扫描，产出待放行白名单清单，**逐条由负责人确认**后方可入库 |
| 新增权限测试仍被 CI 放行 | 安全缺陷继续合入 | 权限门禁作为独立 CI 步骤，不设置 `continue-on-error`；失败输出未分类/未授权路由清单 |
| 菜单 `path` 重名导致按钮授权误判 | viewer 可能从同名菜单继承写按钮 | V1 默认写保护先按角色硬拒绝 viewer/readonly；`WO-5` 再修正菜单定位 |
| 前端未适配 403，用户看到空白页 | 体验投诉 | 前端统一 403 提示文案，与后端**同步上线**，不得分两次发布 |
| `user` 角色授权从仅概览扩到业务写 | `test2` 可见菜单和可写范围扩大 | 不修改用户角色；上线前向账号 owner 确认该语义，并在审计中保留首次授权变更记录 |
| `soc_role_menus` 按基线收敛覆盖手工改动 | 运维手工授权丢失 | `--apply` 前强制快照；基线成为受管角色事实源，脚本以 upsert/delete 精确收敛并在 drift 报告列出将被删除项 |
| 幂等种子脚本与 Alembic 迁移职责重叠 | 双源维护，再次漂移 | 明确：**迁移管结构，脚本管数据**。二者不得互相包含 |

### DR-1 · 只读角色收敛到 `viewer`（2026-09-09 已决策）

**决策**：`WO-4` 中以 `viewer`（id=26）为唯一只读角色；`readonly`（id=3）、`user`（id=2）
不再承担只读语义。

| 角色 | 处置 | 理由 | 对存量用户的处理 |
|---|---|---|---|
| `viewer` | **保留，作为唯一只读角色** | 已有真实用户 `t_view`，且迁移头已有 16 个菜单授权，迁移成本最低 | 无需迁移 |
| `readonly` | 标记 `is_active=false`，不再参与授权 | 0 用户、仅 1 个 `overview` 菜单、0 代码引用，不能承担完整只读职责 | 无存量用户，无影响 |
| `user` | 语义重定义为“普通业务用户”，退出只读范畴 | 数据库描述是“可使用业务功能”，与只读注释本就矛盾；V1 与 `operator` 同属业务写角色，但不授予系统配置权限 | `test2` 无需迁移；消除 user/operator 重名另立后续治理 |

**连带要求（纳入 `WO-4` 交付物）**：

1. 种子脚本必须显式写出受管角色终态，禁止依赖数据库 ID 和运行时当前值。
2. 脚本不得修改任何 `soc_users.role_id`；用户角色调整必须走独立审批和显式操作。
3. `readonly`、`test_role` 停用而非删除：保留 id 稳定性，避免历史审计记录外键悬空。

**已决策**：V1 不新增介于 operator 与 viewer 之间的中间角色，见 `Q2`。

## 九、结论

**角色不缺，默认值缺。**

当前的权限逻辑是"你声明了我才拦"，需要改成"你不声明我就拦"。
在这个翻转完成之前，任何只读角色都只是**标签**，不是**约束**——
`readonly` 角色已经在库里躺了很久，它拦不住任何一次写请求。

## 十、V1.0 实施规格（Agent 执行版）

### 10.0 角色与路由常量

| 常量 | 值 | 说明 |
|---|---|---|
| `READ_ONLY_ROLES` | `viewer`, `readonly` | `readonly` 虽停用，但旧 token 存量期内仍必须硬拒绝写 |
| `BUSINESS_WRITE_ROLES` | `admin`, `operator`, `user` | 业务写统一口径；admin 由 `is_admin` bypass |
| `SYSTEM_ADMIN_ROLES` | `admin` | 用户、角色、菜单、字典、系统配置、扫描器管理等系统管理 |
| `READ_METHODS` | `GET`, `HEAD` | 人类业务读接口只要求有效 access token |
| `WRITE_METHODS` | `POST`, `PUT`, `PATCH`, `DELETE` | 默认拒绝；显式授权例外 |
| `PUBLIC_API_ALLOWLIST` | `POST /api/v1/auth/login`、`GET /api/v1/auth/captcha`、`POST /api/v1/auth/refresh`、`GET /api/v1/public/system-info`、`GET /health`、`GET /`、docs/OpenAPI、`GET /metrics` | 精确到 method+path；新增必须改代码和评审 |
| `MACHINE_API_ALLOWLIST` | Webhook、`/data` collector API Key、scanner API Key、internal service token | 按机器身份认证，不套 JWT 依赖 |

### 10.1 Feature: 路由默认鉴权与写侧默认拒绝

- **User Story**: As a 安全运营负责人, I want 所有人类业务 API 默认必须认证、写操作默认拒绝, so that 漏写权限声明不会变成越权漏洞。
- **Acceptance**:
  - Given 未带 token, When 请求任何非 allowlist 人类业务路由, Then HTTP 为 200、`body.code=401`、`data=null`。
  - Given `viewer` 或旧 `readonly` token, When 请求 `POST/PUT/PATCH/DELETE` 业务路由, Then HTTP 为 200、`body.code=403`，并写入拒绝审计。
  - Given `viewer` token, When 调用 `POST /api/v1/auth/logout`, Then 允许登出并撤销 token。
  - Given `operator/user` token, When 请求业务写路由, Then 按该路由显式 `require_role("admin","operator","user")` 授权。
  - Given 新增写路由但未挂显式授权依赖, When CI 安全门禁执行, Then CI 失败并列出 method+path。
- **API contract**: 本特性不新增 path；改变现有错误契约：

```json
{ "code": 401, "msg": "Not authenticated", "data": null }
{ "code": 403, "msg": "Permission denied", "data": null }
```

  成功响应保持现有 schema 不变。机器通道分别维持 X-API-Key、Webhook 签名、Service Token 的既有 401/403 语义。
- **Data**: 不新增业务表。内部 `AuthSpec` 标记包含 `kind`、`roles`、`allows_session_write`；拒绝审计写入现有 `soc_audit_logs`。
- **Edge Cases**:
  - Pydantic 422 不能替代授权测试；门禁必须扫描路由依赖，行为测试必须用合法载荷。
  - 尾部斜杠路由视为同一个安全分类。
  - `HEAD` 按读处理；`OPTIONS` 如自动生成不进入业务写扫描。
  - 菜单按钮 path 重名不得影响 V1 只读红线：viewer/readonly 在默认写保护层先被拒绝。
  - 审计写入失败不得放宽授权决定，但必须记录应用错误日志。

### 10.2 Feature: 管理员语义与角色边界收口

- **User Story**: As a 系统管理员, I want admin/superuser 只有单一判定口径, so that 登录态、API 授权和前端资料不会出现不同结果。
- **Acceptance**:
  - Given `is_superuser=true` 且角色不是 admin, When 登录、刷新 token、调用 `require_admin`, Then 均判定为管理员。
  - Given `viewer/operator/user`, When 调用用户、角色、菜单、字典、部门、系统配置、扫描器管理写接口, Then `body.code=403`。
  - Given `operator/user`, When 调用资产、事件、告警治理、AI、同步等业务写接口, Then 既有成功契约不变。
  - Given `auditor`, When 读取业务数据和审计日志, Then 成功；调用业务写接口返回 403。
- **API**: 不改变成功响应；系统管理写接口统一业务码 403。
- **Data**: `soc_users.is_superuser` 语义为超级管理员；`soc_roles.code` 为功能角色；二者任一命中 admin 均可管理系统。

### 10.3 Feature: 角色菜单矩阵基线与幂等种子

- **User Story**: As a 运维负责人, I want 角色菜单授权可以导出、评审、重复执行, so that 权限矩阵不再随多次迁移漂移。
- **Acceptance**:
  - Given 迁移头测试库, When 执行导出脚本, Then 生成受管角色的 JSON 草稿，并自动归一 `user=operator` 业务授权、移除 `viewer/auditor` 写按钮、停用 `readonly/test_role`，人工评审后入库。
  - Given 基线文件, When `--apply` 执行两次, Then 受管角色授权结果不变，自定义角色不变。
  - Given 实际库与基线不一致, When `--check` 执行, Then exit code 2 并输出 role/menu/grant 差异。
  - Given 定位符命中多个菜单或找不到菜单, When 任意模式执行, Then 失败并列出定位符，不允许猜测。
- **API**: 脚本 CLI 契约为 `--export FILE`、`--dry-run`、`--check`、`--apply`；默认无参数等价 dry-run。
- **Data**: 基线包含 `version`、`managed_roles`、`disabled_roles`、菜单定位符、每角色 `permissions`；菜单定位符使用父定位符 + `path` + `name`，禁止数据库 ID；`user` 与 `operator` 的业务菜单/按钮必须一致，系统管理按钮仍仅 admin；`readonly/test_role` 只更新 `is_active=false`。
- **Edge Cases**: 脚本不修改 `soc_users.role_id`；手工修改受管角色会被 `--check` 报 drift；菜单 path 重名时必须因定位符歧义失败。

### 10.4 Feature: 阻断式安全门禁

- **User Story**: As a 研发负责人, I want 权限配置错误在 CI 阶段失败, so that 未授权 API 无法合入。
- **Acceptance**:
  - Given OpenAPI 中的任意 method+path, When 执行路由扫描, Then 必须命中 public/machine/human 三类之一。
  - Given 人类写路由, When 扫描依赖树, Then 必须找到带 `AuthSpec` 的显式授权依赖，或命中唯一 session exception。
  - Given 任意受管角色菜单, When 种子后读取菜单树, Then 与 JSON 基线一致。
  - Given 安全门禁失败, When GitHub Actions 执行, Then job 失败；不得依赖现有 advisory pytest。
- **API**: 无运行时 API。
- **Data**: 测试使用现有 test DB fixture，不触碰生产库。
- **Edge Cases**: 私有 FastAPI `_IncludedRouter` 结构不得直接暴露到业务代码；扫描器优先通过统一 `include_human_router` 元数据和 OpenAPI path 获取结果，避免绑定框架内部实现。
