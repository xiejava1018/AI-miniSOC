## 1. 背景与目标

### 1.1 要解决的问题

| 问题 | 现状【事实】 | 影响 |
|---|---|---|
| P1 改配置要停服 | Wazuh/OpenSearch/Loki/AI 模型参数在 `.env`，改动需重启 uvicorn；MCP(8100) 同进程重启导致令牌全部失效 | 改配置 = 停监控，需重连 MCP 并重设凭据 |
| P2 配置无校验 | 系统配置页是通用 KV 编辑器，值类型手选，填错静默回落默认值 | 故障难排查 |
| P3 配错了不知道 | 全仓无连接测试能力 | 数据断流才发现 |
| P4 假配置误导 | 23 个幽灵配置已于 2026-09-11 清理（SMTP/钉钉/微信等） | 已解决 |
| P5 无变更审计 | `SystemConfig` 只有 `updated_by`，无版本历史 | 改坏无法追溯回滚 |

### 1.2 目标

| 目标 | 衡量方式 |
|---|---|
| G1 数据源对接参数可界面配置、热生效 | Wazuh/Loki/OpenSearch 改地址后 60s 内生效，无需重启 |
| G2 配置可校验、可测试 | 每个数据源支持"测试连接"，返回结构化结果 |
| G3 配置可追溯 | 所有变更入审计日志，敏感值脱敏 |
| G4 迁移期零中断 | DB 无配置时自动回落 `.env`，老部署不受影响 |

### 1.3 北极星指标

**配置变更平均生效耗时**：15 分钟 → **< 1 分钟**。
驱动指标：需重启才能完成的配置变更占比 90% → < 20%。

## 2. 范围

### 2.1 本期（v1.0）范围

| 编号 | 功能域 | 说明 |
|---|---|---|
| A | **数据源管理**（多实例） | Wazuh / OpenSearch / Loki 的增删改查、启停、设默认、测试连接 |
| B | **配置 Schema 注册表** | 声明式描述每个配置项的元信息，驱动表单渲染与校验 |
| C | **配置变更审计** | 记录谁在何时把什么从 A 改成 B |
| D | **解析器与回落** | 业务代码统一经解析器取配置，DB 优先、settings 兜底 |
| E | **AI 服务配置** | Provider 注册表（GLM / Claude CLI），模型与密钥可配 |

### 2.2 Non-goals（**明确不做，防止过度实现**）

| 不做什么 | 原因 |
|---|---|
| `SECRET_KEY` / `ENCRYPTION_KEY` / `DB_*` 界面化 | 改动导致全量 token 失效或必须重启，界面化无收益只造事故 |
| CORS 配置界面化 | 配错直接锁死前端 |
| 采集器远程配置下发 | 决策 D3 未定，留在 v2 |
| 通知渠道（邮件/钉钉/企微）实现 | 决策 D2 已定 P1 阶段再做，本期仅清理 |
| 数据保留策略执行 | 依赖清理任务，留 v2 |
| 配置文件热重载（如改 MCP 端口） | 属环境级，本期只标注"需重启" |
| 多 worker 下的缓存同步 | 当前单 worker 部署，多 worker 时改用 Redis 发布订阅 |

### 3.1 角色与场景

| 角色 | 典型场景 | 权限 |

| **系统管理员 admin** | 首次部署时配置 Wazuh 对接；换 IP 后改地址并测试 | 全部读写 |

### 3.4 核心业务流程

#### 3.4.1 配置数据源

```
[数据源列表] → 新增 → [填写表单] → 测试连接 →
   ├─ 成功 → 保存（可选"设为默认"） → 写审计 → 60s 内生效
   └─ 失败 → 展示错误详情 → 允许"仍然保存"（二次确认，仅 admin）
```

> **产品要求【规格】**：测试连接失败时**允许仍然保存**（因为部署期数据源可能尚未就绪），但必须二次确认，且列表页该行显示红色"未通过"标记。

#### 3.4.2 配置解析（读取路径）

```
业务代码请求数据源(type=wazuh)
   → DataSourceResolver.resolve("wazuh")
        ├─ 缓存命中(60s) → 返回
        └─ 查 DB: type=wazuh AND enabled=true AND is_default=true
              ├─ 命中 → 解密 auth_secret → 构造配置 → 缓存 → 返回{config, origin:"db:xxx"}
              ├─ 未命中默认 → 查 type=wazuh AND enabled=true 任意一条 → 返回并 WARN"未设默认实例"
              └─ 无 → 回落 settings.WAZUH_API_URL 等 → 返回{config, origin:"env"}
```

#### 3.4.3 变更生效

| 变更类型 | 生效方式 | 界面标识 |
|---|---|---|
| 数据源连接参数 | 保存后 `invalidate()` 清缓存，下次读取即生效（≤60s） | 🟢 立即生效 |
| 采集范围 / 同步间隔 | 下一个调度周期 | 🟡 下个周期生效 |
| 服务端口 / MCP 配置 | 需重启 | 🔴 需重启服务 |

> v1.1 依据"实测 `alembic heads` = 单 head `c1d2e3f4g5h6`"推翻了 v1.0。复核确认**该前提有误**：
>
> | 断言 | 复核结果 |
> |---|---|
> | 迁移文件 48 个 | ✅ 正确 |
> | `c1d2e3f4g5h6` 是 head | ✅ 正确 |
> | **单 head、线性无分叉** | ❌ **实为 2 个 head**（另有一个 `f2a3b4c5d6e7`） |
>
> 文件级证据（`alembic/versions/` 全部 48 个文件的 `revision` / `down_revision`）：
>
> ```
> HEAD 1: c1d2e3f4g5h6  (rename_browsing_menu_and_reorder)  down_revision = b1c2d3e4f5g6
> HEAD 2: f2a3b4c5d6e7  (security_reports)                  down_revision = e4f5a6b7c8d9
> ROOT  : c5962ab1f662  （1 个，两链同源后分叉）
> ```
>
> **v1.1 误信的来源**：CLAUDE.md 第 466 行原文是「Alembic 迁移**历史不完整** ~~（✅ 已修复 commit 9238f78）」，
> 讲的是"**缺迁移文件/手工建表已补齐**"，与"**多 head 分叉**"是两个不同问题，不能互证。
> 佐证：`f2a3b4c5d6e7`（2026-08-21，早于 9238f78）内部仍在用 `'Document'` 这种 Material 风格 icon，
> 而该 icon 被另一条分支上的 `m1n2o3p4q5r6` 明确判定为"iconify 找不到、完全渲染不出"——
> 说明这个分支从未被 9238f78 合并处理。
>
> **结论：方向保留（走 Alembic），但必须补一步 merge。** create_all 的三个代价依然成立，
> 且项目确有 20+ 个"迁移里种菜单"的先例：
> 1. **`create_all` 不改已有表**——`soc_source_health.source_id` 这类加列必须手工 DDL，脱离版本管理，新环境重建必漏；
> 2. **无 downgrade**——上线出问题无法回退，与 `deploy.sh` 的自动回滚能力不匹配；
> 3. **菜单/权限种子无处安放**——§6.5 的 SQL 只能人工执行，与既有先例不一致。

**执行步骤**：

0. **先 merge 两个 head**（否则后续 `upgrade head` 报 `Multiple head revisions`）：
   ```bash
   cd src/backend
   ../../venv/bin/python -m alembic -c alembic.ini heads          # 确认仍为 2 个
   ../../venv/bin/python -m alembic -c alembic.ini merge -m "merge c1d2e3f4g5h6 and f2a3b4c5d6e7" \
       c1d2e3f4g5h6 f2a3b4c5d6e7
   ../../venv/bin/python -m alembic -c alembic.ini heads          # 期望只剩 1 个
   ```
   > **merge 的风险与缓解**：`merge` 本身不执行任何 DDL，但之后 `upgrade head` 会连带执行此前**从未跑过**的
   > `f2a3b4c5d6e7`（建 `soc_security_reports` 表 + 2 索引 + 2 菜单）。已确认该迁移全用
   > `CREATE TABLE / INDEX IF NOT EXISTS`，**幂等**；而 `soc_security_reports` 表早已由 `create_all`
   > 存在于生产库（`app/models/security_report.py`），所以不会冲突。
   > **仍建议**：merge 与本期迁移分两个 commit，先在临时空库完整跑一遍 `upgrade head` 再上生产。
1. 新建 `app/models/data_source.py`、`app/models/config_schema.py`、`app/models/config_change_log.py`
2. 在 `app/models/__init__.py` 中导入三个类（否则不进 `Base.metadata`，`alembic check` 会误报要 DROP）
3. 新建迁移，`down_revision` = **步骤 0 merge 后那个唯一 head**（执行前 `alembic heads` 现场确认，勿照抄本文档写死的 revision）：
   - `op.create_table()` 建三张新表
   - `ALTER TABLE soc_source_health ADD COLUMN IF NOT EXISTS source_id BIGINT`（幂等写法，生产表已存在）
   - 种入 §6.5 的菜单与角色授权（**全 SQL 子查询写法**，见下）
   - `downgrade()` 对称删除三表、删列、删菜单与授权
4. 本地空库验证：`DB_NAME=<临时库> ../../venv/bin/python -m alembic -c alembic.ini upgrade head`，
   再 `downgrade -1` → `upgrade head` 确认幂等
5. **生产由人工审阅后执行**（CI/CD 永不自动跑 alembic，见 CLAUDE.md）

> **迁移编写红线**（均为本项目已踩过的坑）：
> - 不要在迁移里用 Python 状态变量 + INSERT 后回读 SELECT——`--sql` dry-run 不执行 INSERT，回读必炸
> - 不要硬编码菜单/角色 id，一律 `INSERT ... SELECT ... WHERE NOT EXISTS` 子查询
> - `op.execute(text, params)` 双位置参数不兼容，改 `bind = op.get_bind(); bind.execute(...)`
> - JSONB 参数用 `CAST(:perms AS jsonb)`，**不要**写 `:perms::jsonb`（`::` 被当绑定参数）

```python
"""数据源模型（多实例）"""
from sqlalchemy import Column, String, Text, Boolean, Integer, DateTime, BigInteger, ForeignKey, UniqueConstraint, Index
from sqlalchemy.dialects.postgresql import JSONB
from sqlalchemy.sql import func, text
from app.models.base import Base


class DataSource(Base):
    """数据源连接配置表（支持同类型多实例）"""
    __tablename__ = "soc_data_sources"

    id = Column(BigInteger, primary_key=True, autoincrement=True)
    source_code = Column(String(64), nullable=False, unique=True)
    source_type = Column(String(32), nullable=False)
    name = Column(String(200), nullable=False)
    endpoint = Column(String(512), nullable=False)
    auth_type = Column(String(32), nullable=False, default="none")
    auth_username = Column(String(200), nullable=True)
    auth_secret = Column(Text, nullable=True)          # Fernet 加密
    verify_ssl = Column(Boolean, nullable=False, default=False)
    timeout_seconds = Column(Integer, nullable=False, default=30)
    retry_times = Column(Integer, nullable=False, default=3)
    retry_backoff_seconds = Column(Integer, nullable=False, default=2)
    enabled = Column(Boolean, nullable=False, default=True)
    is_default = Column(Boolean, nullable=False, default=False)
    config_json = Column(JSONB, nullable=False, server_default=text("'{}'::jsonb"))
    last_test_at = Column(DateTime(timezone=True), nullable=True)
    last_test_ok = Column(Boolean, nullable=True)
    last_test_message = Column(Text, nullable=True)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
    updated_at = Column(DateTime(timezone=True), server_default=func.now(), onupdate=func.now())
    updated_by = Column(BigInteger, ForeignKey("soc_users.id"), nullable=True)

    __table_args__ = (
        Index("ix_data_source_type_enabled", "source_type", "enabled"),
    )
```

### 5.8 测试连接实现规格【规格】

统一约定：
- 超时取 `min(timeout_seconds, 15)`，硬上限 15s
- 结果写回 `last_test_at` / `last_test_ok` / `last_test_message`（截断 1000 字符）
- `verify_ssl=False` 时 `httpx.Client(verify=False)`（与现有 `wazuh_client.py:36` 一致）
- 任何异常都要捕获并转为 `ok=false` + 可读 message，**不得抛 500**

| source_type | 探测步骤 | 成功判据 |
|---|---|---|
| `wazuh` | ① `POST {endpoint}/security/user/authenticate`（basic auth）→ 取 `data.token`；② `GET {endpoint}/` 带 Bearer → 取 `data.api_version`；③ `GET {endpoint}/agents?limit=1` → 取 `affected_items`；④ `GET {endpoint}/vulnerability?limit=1` → **探测**，404 记 `ok=false` 但**不影响总判定** | ①②③ 全通过 |
| `opensearch` | ① `GET {endpoint}/` → `version.number`、`cluster_name`；② `GET {endpoint}/_cluster/health` → `status` | ① 通过；② 中 `status` 为 `red` 时 `ok=true` 但 message 告警 |
| `loki` | ① `GET {endpoint}/ready`；② `GET {endpoint}/loki/api/v1/labels` | ① 通过；② 失败仅告警 |
| `tplink` | 仅做 TCP 连通性探测（`socket.create_connection`，3s）。**不做真实登录**，避免触发路由器风控 | 端口可连 |
| `scanner` | `GET {endpoint}/health` | HTTP 200 |

> **已知环境事实**（`wazuh_client.py:8-10` 注释）：本环境 Wazuh API **无 `/vulnerability` 路由**（全 404），CVE 真实数据源是 OpenSearch `wazuh-states-vulnerabilities-*`。测试连接第 ④ 步须把这一事实明确告知用户，这是本功能的高价值点。

### 6.5 菜单注册 SQL【规格】

> **⚠️ v1.0 的 SQL 有 6 处会导致菜单不可用，已重写**。本节 SQL 应放进 §4.7 的 Alembic 迁移，不要手工执行。

**先理解本项目的菜单约定**（`soc_menus` 实测数据）：

| 字段 | 顶级菜单 | 子菜单 | 反例（v1.0 写法） |
|---|---|---|---|
| `path` | 带前导斜杠 `/system` | **相对名** `user`、`dict` | ❌ `/system/data-sources`（会拼成 `/system/system/data-sources`） |
| `component` | `/index/index`（Layout） | **带前导斜杠的实际路径** `/system/user`、`/system/dict/index` | ❌ `system/dataSource/index.vue`（ComponentLoader 解析不到，404） |
| `icon` | iconify `ri:*` | 同左 | ❌ `Database` / `Setting` / `Document`（Material 风格，**静默不渲染**） |
| `permissions` | 容器为 `[]` | **`[{title,authMark}]` 必填** | ❌ 缺失 → 前端 `hasAuth('add')` 恒 false，按钮全不显示 |

> `component` 由 ComponentLoader 先试 `<path>.vue` 再试 `<path>/index.vue`，所以 `/system/data-source` 会命中 `views/system/data-source/index.vue`。
> 按钮权限必须种在**子菜单自己**的 `permissions` 上，种在父容器上无效（迁移 `p1q2r3s4t5u6` 的教训）。

```sql
-- 1) 建菜单：全部子查询取 parent_id，不硬编码（/system 实际 id=5，但不要写死）
INSERT INTO soc_menus (parent_id, name, title, path, icon, component, sort_order, is_visible, permissions)
SELECT p.id, v.name, v.title, v.path, v.icon, v.component, v.sort_order, true, CAST(v.perms AS jsonb)
FROM (SELECT id FROM soc_menus WHERE path = '/system' AND parent_id IS NULL) p
CROSS JOIN (VALUES
  ('dataSource',   '数据源管理', 'data-source',   'ri:database-2-line',  '/system/data-source',   10,
   '[{"title":"查看","authMark":"view"},{"title":"新增","authMark":"add"},{"title":"编辑","authMark":"edit"},{"title":"删除","authMark":"delete"},{"title":"连接测试","authMark":"test"}]'),
  ('configCenter', '配置中心',   'config-center', 'ri:equalizer-line',   '/system/config-center', 11,
   '[{"title":"查看","authMark":"view"},{"title":"编辑","authMark":"edit"}]'),
  ('configLogs',   '配置审计',   'config-logs',   'ri:history-line',     '/system/config-logs',   12,
   '[{"title":"查看","authMark":"view"}]')
) AS v(name, title, path, icon, component, sort_order, perms)
WHERE NOT EXISTS (
  SELECT 1 FROM soc_menus m WHERE m.name = v.name AND m.parent_id = p.id
);

-- 2) 授权 admin（role_id 用子查询按 code 取；soc_role_menus 只有三列，不要带 created_at）
INSERT INTO soc_role_menus (role_id, menu_id, permissions)
SELECT r.id, m.id,
       CAST((SELECT jsonb_agg(e->>'authMark') FROM jsonb_array_elements(m.permissions) e) AS jsonb)
FROM soc_roles r
CROSS JOIN soc_menus m
WHERE r.code = 'admin'
  AND m.name IN ('dataSource', 'configCenter', 'configLogs')
  AND NOT EXISTS (
    SELECT 1 FROM soc_role_menus rm WHERE rm.role_id = r.id AND rm.menu_id = m.id
  );
```

**执行后必须回读确认**——`INSERT ... SELECT` 在父菜单/角色解析不到时会**静默插 0 行且不报错**：

```sql
SELECT m.name, m.path, m.component, m.icon, m.permissions,
       (SELECT count(*) FROM soc_role_menus rm WHERE rm.menu_id = m.id) AS granted_roles
FROM soc_menus m WHERE m.name IN ('dataSource','configCenter','configLogs');
-- 期望 3 行，且 granted_roles 均 >= 1
```

> **其他角色授权**：本期三个页面均为 admin 专属（写端点挂 `require_admin()`）。
> 若后续要放开 `auditor` 只读查看配置审计，需**单独**授 `configLogs` 的 `['view']`——
> 注意菜单树按子菜单粒度过滤，授父容器不会连带放行子菜单（X1 已修复的行为）。

> 菜单为后端驱动；新增后前端需刷新或重新登录才能看到（约束 C8）。

### 7.1 安全约束【规格】

| # | 约束 | 实现方式 |
|---|---|---|
| S1 | **密钥只写不读** | 出参 Schema 不含 `auth_secret`；列表/详情/审计一律脱敏 |
| S2 | 密钥加密存储 | `encryption_service.encrypt()` 写入，读取时 `decrypt_if_needed()` |
| S3 | 写操作 admin-only | 端点 `dependencies=[Depends(require_admin())]` |
| S4 | 审计不落明文 | `ConfigAuditService` 对敏感键替换为 `***` |
| S5 | 不记录完整 URL 中的凭据 | 日志中 endpoint 只记 host，不记 userinfo |
| S6 | 测试连接不产生副作用 | Wazuh 仅只读 GET；tplink 只做 TCP 探测，不做真实登录 |
| S7 | 超时硬上限 | `min(timeout_seconds, 15)`，防止界面卡死 |

### 7.2 兼容性约束【规格】

| # | 约束 |
|---|---|
| B1 | DB 无配置时必须回落 `settings`，**现有部署行为不得改变** |
| B2 | resolver 异常一律吞掉并回落，不得中断业务 |
| B3 | `config_json` 未知键保留，不做强校验 |
| B4 | 新增字段全部可空或有默认值，不影响既有行 |

### 7.3 性能约束【规格】

| # | 约束 |
|---|---|
| P1 | resolver 缓存 60s，与既有配置模块一致 |
| P2 | 测试连接并发上限：单次请求一个数据源，批量测试串行执行，前端禁用重复点击 |

## 10. 风险与回滚

| 风险 | 影响 | 对策 | 回滚方式 |
|---|---|---|---|
| resolver 改动破坏现有同步 | 数据断流 | 严格 B1/B2 回落；W11 单独 commit | `git revert` W11 commit |
| 部分唯一索引在旧 PG 版本不支持 | 建表失败 | 降级为 Service 层事务实现 | 删索引，改代码 |
| 测试连接触发 Wazuh 限流 | 数据源被临时封禁 | 只做只读 GET；批量测试串行 | 停用批量测试 |
| 加密密钥变更导致 `auth_secret` 无法解密 | 数据源全部失效 | 解密失败时记 error 并提示"密钥已变更，请重新录入密码"，**不要**静默回落 | 重新录入 |
| 菜单插错 parent_id / 静默插 0 行 | 菜单不显示或位置异常 | 子查询取 parent_id，**执行后回读确认 3 行**（§6.5） | 迁移 downgrade |
| 菜单 component/icon/permissions 格式错 | 页面 404 / 无图标 / 按钮全隐藏（均无报错） | 严格按 §6.5 表格约定；上线后人工点一遍 UI | 修数据 |

### 11.3 常见错误（**执行前必读**）

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 直接用 `api_router.include_router` | CI 路由授权检查失败 | 用 `include_human_router` |
| 写端点忘加 `require_admin()` | CI 失败 / 越权 | 显式加 dependencies |
| 新模型忘记在 `models/__init__.py` 导入 | 表不创建 | 必加 |
| 靠 `create_all` 建表、跳过 Alembic | 加列不生效、无法回退、新环境重建必漏 | 走 Alembic 迁移（D5 v1.1）|
| 菜单 `component` 写成 `xxx/index.vue` | ComponentLoader 解析不到，页面 404 | 写 `/system/data-source` |
| 菜单 `icon` 用 `Database`/`Setting` | iconify 静默失败，无图标无报错 | 用真实存在的 `ri:*` |
| 子菜单 `permissions` 留空 | 前端 `hasAuth()` 恒 false，按钮全隐藏 | 子菜单自身必填 JSONB |
| 菜单 SQL 硬编码 `parent_id` / `role_id` | 插错位置或静默插 0 行 | 一律子查询 + 事后回读确认 |
| 出参 Schema 声明了 `auth_secret` | 密钥泄露 | 不声明该字段 |
| 把 `soc_asset_sources` 当数据源表用 | 语义冲突 | 用 `soc_data_sources` |
| resolver 未 try/except | 配置异常导致业务中断 | 一律回落 settings |
