## 0. 一句话结论

**这个模块在"功能完成度"上打了满分，在"产品价值"上不及格。**

设计文档规划的 4 个页面做成了 6 个，16 个 API 端点全部实现，AI 研判、威胁情报同步、规则试运行等"二期能力"也已落地。但上线运行 32 天后，它累计产出了 **2353 条告警，其中 0 条被处置、0 条升级为安全事件、0 条触发通知** —— 因为其中约 83% 是 WebRTC/P2P 的正常流量被误判，剩下的又全部卡在 medium 等级，永远够不到升级阈值。

它不是缺少功能，是**缺少可信度**。用户打开列表看到满屏 `stun.miwifi.com`、`stun.chat.bilibili.com`、`stun.hitv.com`，判断一次"这模块没用"，之后就再没打开过。

## 1. 模块全景：设计 / 实现 / 运行 三层对照

### 1.1 定位与数据流 **[设计]**

模块解决的核心问题是：**TP-Link TL-R479GP-AC 路由器的上网行为日志已经进了 Loki（约 20 万条/天），但只采集不分析**，恶意域名访问、数据外泄、C2 通信等异常无法被发现。

数据流：Loki（路由器 syslog）→ 后端 5 分钟轮询 → 字段解析 + 秒级去重 → 6 类规则加权打分 → 超阈值落 `soc_browsing_events` → 高风险升级 `soc_incidents` + 站内通知。

### 1.2 实现覆盖度 **[代码]**

| 层次 | 内容 | 规模 |
|------|------|------|
| 数据模型 | `soc_browsing_events` / `soc_browsing_baseline` / `soc_browsing_blacklist` | 3 张表，含唯一约束与 FK |
| 检测服务 | `browsing_detection/` 8 个模块 | loki_client / log_parser / rule_engine / baseline_service / event_service / scheduler / config / threat_intel |
| API | `/api/v1/browsing/*` | **16 个端点**（设计文档规划 11 个） |
| 前端 | `views/browsing/` 6 个页面 | 1235 行（event 412 / statistics 273 / logs 193 / config 146 / blacklist 140 / baseline 71） |
| 菜单 | `soc_menus` id=22 父菜单 + 6 子项 | 异常事件 / 行为统计 / 行为日志 / 黑名单 / 规则配置 / baseline |

**超出设计文档的部分**（实现领先于设计）：

- `/logs` 原始日志查询页、`/statistics` 行为统计页（设计只规划了 4 页）
- `/events/{id}/analyze` AI 研判（设计列为 M5/二期，已落地，复用 `AIAnalysisService`）
- `/threat-intel/sync` 威胁情报同步（设计列为 M6/二期，已落地，已导入 1000 条）
- `/events/{id}/logs` 事件关联原始日志回溯
- 前端详情抽屉已具备完整处置动作：确认威胁 / 标记误报 / 忽略 / 加白名单 / AI 研判 / 查看原始日志

**[产品判断]** 工程交付质量是扎实的，M1–M6 里程碑基本都完成了。**问题不在"做没做出来"，而在"做出来的东西能不能用"。**

|------|--------|---------|------|
| 累计事件 | **2353 条** | < 100 条/天 | 日均 73.5 条，量级符合预期 |

### 2.2 分值分布 —— "50 分魔咒" **[实测]**

| 分值 | 条数 | 占比 |
|------|------|------|
| **50** | **2280** | **96.9%** |
| 55 | 63 | 2.7% |
| 60 | 6 | 0.3% |
| 70 | 4 | 0.2% |

**[产品判断]** 96.9% 的事件分值**恰好等于阈值 50**，这不是巧合，是规则权重设计的结构性缺陷（详见 §3.2）。它意味着**严重度等级事实上是二元的**：要么不告警，要么 50 分 medium。设计文档规划的 critical(≥100)/high(≥80)/medium(≥50)/low 四层分级，在真实运行中退化为一层。

### 2.3 规则命中频次 —— 只有一条组合在干活 **[实测]**

| 规则 | 名称 | 权重 | 命中次数 | 占事件比 |
|------|------|------|---------|---------|
| **R5** | 凌晨活跃 | 15 | **2293** | 97.4% |
| **R4** | 隧道/穿透工具 | 35 | **1955** | 83.0% |
| R3 | 基线偏离 | 20 | 447 | 19.0% |
| R6 | 可疑域名特征 | 15 | 383 | 16.3% |
| R2 | 突发高频访问 | 40 | **15** | 0.6% |
| **R1** | 恶意域名命中 | **100** | **0** | **0%** |

**[产品判断]** 三个致命信号：

1. **R4 + R5 = 50 分**，正好压线。这一条组合贡献了绝大多数告警，其余规则全是陪跑。
2. **R2（突发高频，设计文档定义的核心风险"数据外泄/C2 心跳"）32 天只命中 15 次**，形同虚设。
3. **R1（恶意域名，唯一权重达 100、唯一能单独触发 critical 的规则）零命中**。

## 3. 六项核心缺陷（按严重度排序）

### P0-1 · R4 规则把正常 P2P 流量判为隧道工具 —— 误报的主要来源

**[代码]** `soc_system_config` 中 `tunnel_keywords` 实际生效值为：

```
easytier|stun|frp|fatedier|zerotier|tailscale|n2n|wireguard|tinc|nebula
```

**[实测]** R4 命中 1955 次（占事件 83%），其中绝大多数是 `stun.*` 域名。

**[设计溯源]** 该关键词列表出自设计文档 §4.3 原文，属于**设计阶段就埋下的缺陷**，不是实现偏差：

```
easytier|stun|frp|fatedier|zerotier|tailscale|n2n|wireguard|tinc|nebula|innernet
```

**[产品判断]** STUN（Session Traversal Utilities for NAT）是 IETF 标准的 NAT 穿透协议，被 WebRTC、VoIP、视频会议、直播 CDN、P2P 分发、IoT 设备远程连接广泛使用。将它等同于 frp / zerotier / tailscale 这类**主动型内网穿透工具**，是一个语义错误。二者的区别在于：STUN 是"应用为了建立 P2P 连接而做的标准协商"，frp 是"人为把内网服务暴露到公网"。

- **影响**：83% 的告警量、32% 的明确误报、用户对整个模块的信任崩塌。
- **根因分类**：设计缺陷（关键词语义误判）+ 缺少默认白名单兜底。

### P0-2 · 闭环断裂：0 处置、0 升级、0 通知

**[代码]** `event_service.py` 中升级与通知的触发条件为 `severity in ("high", "critical")`；`severity_for()` 映射为 ≥80 分 high、≥100 分 critical。

**[实测]** 2353 条事件 100% 是 medium（50–79 分区间），因此：
- 升级 `soc_incidents`：0 条
- 站内通知 + WebSocket 推送：0 次
- 人工处置（确认/误报/忽略/加白名单）：0 次

**[产品判断]** 设计文档 §1.2 列的 5 条目标中，第 2 条"事件化落地"、第 3 条"实时通知"在真实运行中**从未触发过一次**。这不是 bug，是 P0-1 与 P0-3 的连带后果：误报淹没了模块 → 用户不看 → 不处置；而告警等级又永远够不到升级线 → 系统也不推。两个方向同时断，闭环就死了。

值得强调的是：**前端处置功能本身是完整的**（详情抽屉有确认威胁/标记误报/忽略/加白名单/AI 研判/原始日志 6 个动作）。**功能齐全而无人使用，比功能缺失更值得警惕** —— 它说明问题出在"输入质量"而非"交互设计"。

### P0-3 · 基线只增不减 + 基线自污染，R3 检测力单调衰减

**[代码·缺陷 A]** `BaselineService.cleanup_old()` **定义了但从未被调用**。全仓库检索 `cleanup_old` 仅出现在 3 处：定义处（baseline_service.py:95）、配置项、配置默认值。scheduler 中无调用点，无任何定时任务挂载。

**[实测]** 基线表最老记录为 2026-08-03，至今 32 天，23486 行且持续增长。设计文档 §5.3 明确要求"仅保留近 7 天有访问的记录（每日清理）"。

**[代码·缺陷 B]** `scheduler.py` 第 150 行在**规则评估之后**立即执行 `baseline.upsert_many()`，把本窗口访问过的域名写入基线。这意味着下一轮（5 分钟后）同一域名就变成"已知"，R3 不再命中。

```python
# scheduler.py:142-150
findings = engine.evaluate(records, known_map, start, end)   # 第 4 步：用旧基线评估
baseline.upsert_many([r for r in records if r.action == "url"])  # 第 5 步：立刻把本窗口数据写进基线
```

**[代码·缺陷 C]** `upsert_many` 冲突时执行 `total_count = BrowsingBaseline.total_count + 1`，但传入的 `items` 是 dict（同 `(ip, domain)` 只保留一条 ts，即已去重）。因此 `total_count` 累加的是"**检测轮次数**"而非设计文档 §5.3 定义的"累计访问次数"。基线页展示的访问次数严重虚低，且无法用于任何频次类判断。

**[产品判断]** 三个缺陷叠加的后果是灾难性的：

1. **基线无限膨胀** → 34 个 IP 积累了 13944 个域名，平均每个 IP 690 个"已知域名"→ R3 检出率随时间持续下降，模块越用越钝。
2. **慢速攻击完全逃逸** —— 这是最严重的安全后果。攻击者每天访问一次新域名：首轮命中 R3(20 分)，低于 50 阈值不告警；5 分钟后该域名进入基线，此后**永远不再告警**。而"低频、慢速、域名轮换"恰恰是 C2 心跳和数据外泄的典型特征，也是这个模块立项时要解决的核心风险之一。
3. 设计文档宣称的"7 天基线"在实际语义上是"**5 分钟前**"。

**[根因分类]** 实现缺陷（清理任务漏挂）+ 设计缺陷（基线更新与检测同轮，缺少延迟窗口）。

### P1-1 · R1 黑名单零命中，威胁情报与实际流量完全脱节

**[实测]** 黑名单 1001 条（1000 条来自 threat_intel 同步 + 1 条手动），32 天内 **R1 命中 0 次**。基线中实际访问过的域名有 13944 个，二者交集为 0。

**[产品判断]** 这有两种可能，都需要立即核查（**当前证据不足以判定是哪一种，标注为待核实**）：

- **可能 A**：情报源质量问题 —— 导入的 1000 条域名可能是通用恶意域名库，与一个内网办公环境的实际访问面重合度天然极低。
- **可能 B**：导入格式/匹配逻辑问题 —— 例如情报域名带了协议头、端口或路径，与解析器提取的裸域名无法匹配。

无论哪种，R1 都是权重 100、唯一能单独触发 critical 的规则。**它空转，就等于这个模块的"高价值告警通道"从未打开过。** 顺带一提，`blacklist_domains` 配置项（手动黑名单）至今为空字符串 —— 意味着上线以来没有任何人工维护。

**[根因分类]** 待核实，需排查情报源与匹配逻辑。

### P1-2 · 12.7% 任务失败率静默无感知

**[实测]** `soc_source_health` 记录 `loki:browsing_detection` 成功 8284 次、失败 1208 次（12.7%），`last_failure_message` 为 NULL。另 `loki:browsing` 数据源最后成功时间为 8/22，已停摆 13 天。

**[产品判断]** 模块已经接入了 `SourceHealthRecorder` 和 `track_task` 可观测框架（这是 P4 阶段的成果，做得对），但**观测到了却没有消费这些数据**：

- 前端 6 个页面没有一个展示数据源健康状态
- 连续失败没有触发任何告警
- 日志文件中的 `browsing` 相关记录为空，失败原因无从追溯（`last_failure_message` 为 NULL）

**"采集中断无感知"是项目已知问题（见项目记忆 P4 缺口⑤），本模块正是该问题的具体受害现场。** 8/10–8/13、8/24–8/27 两段事件空白，无法区分"真的没异常"还是"日志断了"。

**[根因分类]** 可观测性数据未消费（有采集、无告警、无展示）。

### P1-3 · 打分体系退化：单规则全低于阈值，组合恰好压线

**[代码]** 规则权重 R1=100 / R2=40 / R4=35 / R3=20 / R5=15 / R6=15，阈值 `score_threshold=50`。

**[产品判断]** 这个权重表的结构决定了：

- 除 R1(100) 外，**没有任何单条规则能独立触发告警**（最高 R2=40 < 50）
- 可行的双规则组合仅 4 种：R2+R3=60、R2+R6=55、R4+R3=55、**R4+R5=50**、R4+R6=50
- 而 R5（凌晨活跃，IP 级加成）一旦命中就会**加到该 IP 本窗口的所有域名上**，导致凌晨时段 R4+R5 的组合批量产生恰好 50 分的事件

这解释了 §2.2 的"50 分魔咒"（96.9% 的事件分值 = 50）和 §2.3 的 R5 命中率 97.4%。**R5 作为 IP 级加成施加到每条 (ip, domain) 上，是设计上的一个放大器缺陷** —— 它让"这个 IP 凌晨活跃"这个单一事实，变成了几十条独立告警。

**[次要缺陷]** 另有两处实现细节值得记录：
- `_domain_main_part()` 对多级子域执行 `"".join(parts[:-2])`，会把 `a.b.c.example.com` 拼接成 `abc` 求熵，**长子域的熵被平均化，高熵特征被稀释** → R6 对 CDN 动态子域的漏报风险。
- 聚合键对 apptype 类记录使用 `[app]{apptype}`，但 R1/R2/R3/R4/R6 均要求 `domain` 非空，导致**占数据量约 22% 的"使用应用"类日志实际不参与任何检测**（最高仅 R5 的 15 分，永不触发）。

## 6. 指标体系建议

当前模块**没有任何产品指标**——§4 的 Gap #13「误报统计」未实现，也没有 MTTD/MTTR 之类的运营指标。建议建立三层：

### 6.1 北极星指标

> **每周有效处置的异常上网行为数**（状态被人工确认为 `confirmed` 且非误报的事件数）

- **当前基线：0**（32 天 0 处置）
- **目标**：改进后 3 个月内达到 ≥ 2 条/周

选它的理由：这个指标同时衡量了"检测能力"和"可信度"——只有告警准、界面可用、流程顺，用户才会真正处置。单纯追求"告警数"会让团队继续堆噪音。

### 6.2 驱动指标

| 指标 | 定义 | 当前基线 | 目标 |
|------|------|---------|------|
| **告警准确率** | 1 − (标记误报数 / 已处置总数) | 无数据（0 处置） | ≥ 50% |
| **日均告警量** | 每日新增事件数 | 73.5 | ≤ 15 |
| **有效告警占比** | 非 STUN/白名单类事件占比 | 约 12% | ≥ 50% |
| **升级率** | 升级为 soc_incidents 的事件占比 | 0% | 5–10% |
| **MTTD** | 异常发生到事件入库的平均时长 | ≤ 5 分钟（轮询周期） | 维持 |
| **MTTR** | 事件创建到处置完成的平均时长 | 无数据 | ≤ 24 小时 |

### 6.3 健康指标

| 指标 | 定义 | 当前基线 | 目标 |
|------|------|---------|------|
| **任务成功率** | 1 − (失败轮次 / 总轮次) | 87.3% | ≥ 99% |
| **数据源新鲜度** | 当前时间 − 最后成功采集时间 | 正常 | ≤ 10 分钟告警 |
| **基线新鲜度** | 基线中 last_seen 在 7 天内的记录占比 | 待清理后测量 | ≥ 95% |
| **基线规模** | 基线表总行数 | 23486（32 天累积） | 稳定在 7 天量级 |
| **R1 情报命中率** | R1 命中次数 / 总事件数 | 0% | 需先排查，再定 |

## 7. 验收标准建议

改进完成后，建议按以下标准验收（可纳入 P2 阶段回归测试）：

1. **误报率验收**：连续 7 天运行，日均告警 ≤ 15 条，且 `stun.miwifi.com` / `stun.chat.bilibili.com` / `stun.hitv.com` / `*.easytier.cn` 出现次数为 0。
2. **闭环验收**：随机抽取 20 条事件，走完「查看详情 → 确认威胁/标记误报 → 状态变更」流程，全部成功且状态正确持久化。
3. **升级验收**：构造一条 score ≥ 80 的测试事件，验证自动生成 `soc_incidents` + 站内通知 + WebSocket 推送。
4. **基线验收**：运行 7 天后，基线表中 `last_seen < now() - 7d` 的记录数为 0；且同一域名首次出现后，至少在 N 轮内保持 R3 可命中。
5. **可观测验收**：人为停止 Loki 或断网 30 分钟，验证系统在 10 分钟内产生数据源中断告警。
6. **慢速攻击验收**：构造"每 10 分钟访问一个新域名"的测试流量，验证能被检出（当前实现下此项会失败）。

## 8. 总结

**这个模块需要的是"调优"，不是"重做"。**

工程实现是扎实的——6 个页面、16 个 API、AI 研判和威胁情报这些二期能力都已落地，代码结构清晰、幂等与可观测性考虑周全。真正的问题在于：**一个设计上把 STUN 当隧道、把 50 分当阈值的规则集，配上一条从不清理还在自我污染的基线，稳定运行了一个月，产出了 2353 条没人看的告警。**

三个 P0 缺陷的因果链很清晰：

```
R4 关键词误伤 STUN (P0-1)
    → 83% 告警是正常流量，全部卡在 50 分 medium
    → 够不到 high/critical，升级与通知通道从未打开 (P0-2)
    → 用户打开列表看到满屏 bilibili/小米，判定模块无用，0 处置
    → 闭环死亡

基线清理未挂接 + 检测后即写入 (P0-3)
    → 基线从 7 天语义退化为 5 分钟语义，且无限膨胀
    → R3 基线偏离对慢速攻击完全失效（这正是立项要防的核心风险）
```

**建议立即执行 Now 组的 N1–N3（三个配置项修改，预计 1 小时内完成），先把日均告警从 73 条压到 10 条以内、把有效告警率从 12% 提到 50% 以上，重建用户对模块的基本信任。然后再做 Next 组的基线修复与打分体系重构。**

在告警准确率达标之前，不建议投入任何新功能开发——**给一个没人信的告警列表加更多功能，只会产生更多没人看的东西。**
