# AI-miniSOC 资产管理 AI 能力建设方案

> **核心主线**：从"台账思维"跃迁到"本体治理"——把资产从一行行台账记录，升级为可对齐、可推理、可审计的资产本体图谱，让 AI 在图上完成融合、稽核、研判、优先级与整改闭环。
> **范围**：技术落地方案。**不涉及**数字员工 MSS 备案（合规）、资产数据治理委员会（组织机制）等组织/合规议题。
> **对接规划**：`AI-SOC产品规划知识库/04-规划库/04-4-规划产出/2027专项规划/2027年资产管理AI能力建设规划.md`（v1.3，2026-09-19，本体驱动 O-ASG）。
> **决策依据**：[`docs/sessions/2026-09-30-资产管理规划差距分析.md`](../sessions/2026-09-30-资产管理规划差距分析.md)（2026-09-30 与规划逐项对比，明确本方案承接之范围）。
> **配套文档**：[`docs/design/2026-09-30-资产管理AI能力建设-实施方案.md`](2026-09-30-资产管理AI能力建设-实施方案.md)（任务清单 + 工作量 + 优先级）。
> **本体骨架**：[`configs/asset_ontology_v1.yaml`](../../configs/asset_ontology_v1.yaml)（v1 类/属性/关系定义草案，OH-1.1 起点）。

### 2.1 现状与缺口

| 维度 | 现状 | 缺口 |

| 类定义 | 隐式散落在 SQLAlchemy 模型 | 缺统一本体文件 |
| 属性 | 字段级，部分缺关键属性 | 缺关联语义 |

### 2.2 设计原则

- **不自创轮子**：复用 STIX 2.1 SCO/SDO + 扩展自有层
- **可机读**：YAML 主形态 + OWL 派生形态
- **Git 可回滚**：本体演进走 PR + 校验 CI
- **强约束**：公理必须可代码化测试
- **向 AI 倾斜**：本体类定义直接驱动 LLM 抽取 Agent

### 2.3 本体主干（v1）

```

├── 标准锚定层（复用 STIX 2.1，不自造）

│   └── CVE → CWE → CAPEC
└── 自有扩展层（AI-miniSOC 云网语境）

    │   ├── LogicalAsset    逻辑资产（IP/域名/证书/端口）

    │   └── BusinessAsset   业务资产（业务系统/服务）

    │   ├── ExposureSurface 暴露面（公网 IP/端口/域名 + maps_to 内外网映射）
```

### 3.2 八维画像数据模型（设计）

```python
# app/services/asset_profile.py（设计伪代码，非现代码）

@dataclass
class AssetProfile:
    # ① 身份维
    identity: AssetIdentity
    # ② 归属维
    ownership: AssetOwnership
    # ③ 技术维
    technology: AssetTechnology
    # ④ 暴露维
    exposure: AssetExposure
    # ⑤ 脆弱维
    vulnerability: AssetVulnerability
    # ⑥ 威胁维
    threat: AssetThreat
    # ⑦ 合规维
    compliance: AssetCompliance
    # ⑧ 行为维
    behavior: AssetBehavior

    # AHS 健康分
    ahs_score: int          # 0-100
    ahs_evidence: List[EvidenceItem]

    # 画像可信度
    profile_confidence: float  # 0-1
    missing_dimensions: int
```

### 3.3 AHS 算法

```
AHS = 100 − (暴露风险 × w1 + 脆弱 × w2 + 威胁 × w3 + 合规缺口 × w4 + 行为异常 × w5)
       × 资产关键性系数

资产关键性系数 = f(业务影响, 数据敏感度, 等保等级)
                = 三维加权（BIA 5 档 × CIA 5 档 × 等保 5 级）
                范围 0.8 ~ 1.5
```

> 与本地 `app/core/criticality.py`（commit q9r05u5v，2026-09-14 三维度重要性重构）同构——本次直接把其纳入画像输入。

## 十一、与本地现实的对齐（关键要点）

1. **CLAUDE.md 已记载 F3.1 降级版**——S11 变更预测恰要靠拓扑；本次实施需在 H2 先补图谱拓扑覆盖，再上 S11。

3. **SQL 图非 Neo4j**——本方案不调整图存储；扩容触发看板先解决性能观测，分布式图库作储备。
4. **采集器 CI/CD 覆盖**——本次新增的 **TP-Link NAT 扩展**，**必须在 `deploy_collectors.sh` 同步加健康门禁**（CLAUDE.md 2026-08-23 续八教训）；Wazuh 已在门禁内，无需额外接入。
5. **本地三库严格分离**——本体迁移、AHS 计算、图谱重建都需考虑测试库隔离（CLAUDE.md §1.7）。
6. **X1 权限矩阵**——新加的 S2/S4/S5/S11/S12 端点必须接权限（admin/auditor/viewer 三档）。
7. **`sync_client` 不看 `body.code`**——CLAUDE.md 2026-08-23 顺带发现新发现的 bug，本次采集器新增必须遵守 envelope 口径。
8. **新增 MCP 工具必须走 schema 验证**——CLAUDE.md "service 测过了路由未必通"，MCP tools 同样需路由级端到端实测。
