## 0. 结论摘要

| 项 | 结论 |
|---|---|
| **能否集成** | 能。定位为「ARL-Next 单向供给攻击面情报，AI-miniSOC 保持资产主数据权威」，不做双向主数据同步 |
| **最优落点** | 复用现成模型三件套：`soc_asset_sources`（多源溯源，`source='arl-next'`）+ `soc_asset_ports`（端口 JSONB 多源）+ **`soc_scan_findings`（PoC/弱口令发现的旁路，评审修正新增）**；影子资产走现成 `discovery`→F1.3→确认工作台链路，**不新建影子资产管理** |
| **融合方式** | 接现成四层融合机制：`identity_fusion`（已落地 OH-4.1，47 例测试）+ 端口 JSONB 多源并存 + 漏洞三键/置信度分层 + discovery→确认工作台——**不新建融合引擎**；冲突裁决权威表见 §5.8 |
| **通道顺序** | 一期 REST pull + 只读画像实时查 → 二期新增 MCP Client → 三期受控扫描调度。ARL 侧**无资产事件 Webhook**（源码实证），只能 pull |
| **最大结构缺口** | 两侧**都是 MCP Server**（SOC :8100 / ARL :5173 `/mcp/sse`），AI-miniSOC 侧**零 MCP Client 实现**（grep 实证）——"注册为外部 MCP 源"不是配置动作而是新增开发 |
| **最大数据缺口** | ARL 无稳定资产 UUID（MongoDB ObjectId / `target` / `scope_id`），SOC 用 UUID 主键；ARL `task_id`(24 位 ObjectId) 与 SOC `scan_task_id`(UUID FK) 类型不兼容 |
| **合规红线** | ARL 是主动测绘工具；集成只消费已授权 `scope_id` 范围的数据，写工具（`create_scan_task`）强制 human-in-the-loop |

## 3. 集成定位与边界

| 维度 | 【设计】定位 |
|---|---|
| 主数据权威 | **AI-miniSOC `soc_assets` 是唯一资产主数据**。ARL 只是「观测来源」，不得反向覆盖 SOC 的业务属性（owner、business_impact、data_sensitivity、protection_level） |
| 数据方向 | 主方向 **ARL → SOC**（资产、端口、漏洞/发现、画像）；反向仅「受控扫描任务下发」一条，且需人工审批 |
| 能力互补 | ARL：主动测绘 / 互联网暴露面 / ICP 企业生态 / Nuclei PoC / Web 指纹（8894 条库）；SOC：被动告警 / 事件闭环 / 资产业务属性 / AI 研判 / 治理闭环（稽核·确认·审计） |
| 不做什么 | ① 不做双向资产主数据同步；② 不把 ARL 的 MongoDB 直接暴露给 SOC；③ 不让 SOC 自动触发 ARL 全量扫描；④ 不用 `task_id`（临时态）作为资产身份锚点；⑤ **不绕过 discovery 通道直接写台账**（切断 F1.3 shadow 判定的坑，`DiscoverySyncHandler` 文件头注释明令） |

**合规边界**：ARL 属主动攻击面测绘工具，集成范围必须与客户书面授权范围（IP 段 / 域名 / 时间窗）一致；SOC 展示与缓存的 ARL 数据同样受该范围约束；写工具产生的扫描动作需留存授权凭证与任务日志对应关系。

```
            （IP 匹配在 SOC 侧 arl_site handler 内完成；未命中项由 handler 内部转入 discovery 暂存）
            MCP Client Gateway（新增）                              ← 二期
   ▼
[ SOC 现成处理链（评审修正：不再新建映射层）]
   新发现 IP ──→ SYNC_HANDLERS["discovery"]（DiscoverySyncHandler 暂存）
                  → F1.3 对账稽核（shadow 判定）
                  → 确认工作台 attribution.py（人工确认，只建议不裁决）
                  → 确认后入 soc_assets（data_source='arl-next'）
   端口/指纹 ──→ arl_site handler → soc_asset_ports（sources JSONB 追加 arl-next）+ 画像摘要
   发现/漏洞 ──→ arl_vuln handler → 有 CVE → soc_vulnerabilities + soc_asset_vulnerabilities(scanner='arl-next')
                                  → 无 CVE → soc_scan_findings（旁路，§5.6 冲突 1 修正）
   ▼
[ SOC 持久层 ]  soc_assets ｜ soc_asset_sources(source='arl-next')
                soc_asset_ports(sources 含 arl-next) ｜ soc_asset_vulnerabilities(scanner='arl-next')
                soc_scan_findings(discovery_source='arl-next')
   ▼
[ 消费层 ]  AssetEnrichmentService / 告警富化与降噪 / AI 研判 / 脆弱性管理 / 暴露面交叉验证（§10.1）
```

> **拉取模型澄清**：SOC 后端对 ARL **零直接依赖**——「拉」是 arl-collector 从 ARL 拉（REST，30min 节奏 + 水位增量 + 每周全量对账），「推」是 collector 向 SOC `/data/sync` 推（出向请求，与 tplink / wazuh / scanner 采集器同构）。唯一例外是一期 B 告警富化实时查（AI 研判服务单点只读调用，缓存熔断，不落库）。ARL 停机不影响 SOC 主数据与告警链路（C7）。

> **与原稿的差异**：原稿 §4.1 设计了一个独立的「映射层：资产 ID 对齐器（规范化→匹配→新建影子资产）」。评审修正：**新建影子资产的动作一律收敛到现成 `DiscoverySyncHandler` → F1.3 → 确认工作台链路**；「对齐器」收敛为 SOC 侧 `arl_site` handler 内的匹配逻辑（复用 `exposure.py` `_assets_by_ip` 单次 in 查询范式：命中→写来源溯源，未命中→内部转入 discovery 暂存），不复刻影子资产管理、确认队列、老化策略。

### 4.2 通道选型对比

| 通道 | 实现成本 | 实时性 | 复用现成能力 | 适用 | 结论 |
|---|---|---|---|---|---|
| **A. REST pull**（`/api/asset_*`） | 低 | 分钟~小时（定时） | `BaseCollector` + `MiniSOCClient` + `discovery` handler + `soc_asset_sources` + `asset_enrichment` | 资产基线 / 端口 / 漏洞落库 | ✅ **一期主通道** |
| **B. 只读画像直调**（`/api/mcp/asset_profile`） | 最低 | 实时 | AI 研判链路直接 HTTP 调用，不落库 | 告警富化（单点上下文） | ✅ **一期并行** |
| **C. MCP Client → ARL SSE** | 中（**需新建 Client 层**） | 实时 | 无，需新建 | Agent 自然语言查 ARL 资产 | ⏳ **二期** |
| **D. 受控写调度**（`create_scan_task`） | 中 | 实时 | `central_scan_scheduler._create_scan_task` 可复用 | SOAR 触发补扫 | ⏳ **三期 + 人工审批**（另评估 §10.2 scanner agent 注册路线） |

> 【实证】选 A 而不选 push 的原因：ARL 侧没有资产事件 Webhook（§2.1 末行），只能主动拉。

## 5. 资产 ID 对齐模型（本方案核心）

### 5.1 问题的本质

| | ARL-Next | AI-miniSOC |
|---|---|---|
| 资产主键 | 无统一资产 UUID；MongoDB `_id`（24 位 ObjectId）、`task_id`、`scope_id`、`target`（IP/域名/URL） | `soc_assets.id`（UUID） |
| 稳定边界 | `scope_id`（资产组归档态） | `asset_id`（UUID），`public_ip` 唯一部分索引 |
| 时间语义 | 任务态随生命周期失效，归档态持久 | 持久主数据 + `last_seen_at` 证据时间戳 |

因此对齐不是「ID 直连」，而是**多键匹配 + 来源溯源 + 影子确认**。

### 5.2 对齐键优先级【设计，评审修正】

| 优先级 | 键 | 匹配规则 | 置信度 | 落点 |
|---|---|---|---|---|
| 1 | `public_ip` / `asset_ip` 精确匹配 | ARL `ip` 字段规范化后与 `soc_assets.public_ip`（有唯一索引）比对 | 高 | 写 `soc_asset_sources(source='arl-next')` |
| 2 | 域名 / 站点 URL → 解析 IP | 复用 ARL `mcp_asset.py:41-70` 的 `urlparse` 规范化逻辑（去协议、去端口、去路径），再走优先级 1 | 中 | 同上 |
| 3 | MAC / 主机名 | 【实证】ARL 画像无 MAC 字段，`soc_assets` 侧无稳定对应键 | 不可用 | — |
| 4 | 无匹配 | **走现成 discovery 通道**：collector 推 `data_type=discovery` → `DiscoverySyncHandler` 暂存 → F1.3 对账判 shadow → **确认工作台人工确认** → 确认后 `data_source='arl-next'` 入台账 | 待确认 | **不直接新建 soc_assets**（评审修正，原稿此处为重新发明） |

> 匹配逻辑放在 **SOC 侧 `arl_site` handler 内**（handler 持有 DB 会话；复用 `exposure.py` `_assets_by_ip` 单次 in 查询范式），collector 只做拉取 / 规范化 / 授权过滤——IP 匹配与来源写入是通用语义，ARL 特有的指纹/画像仅进 `source_metadata`，避免把 ARL 特有语义写进 `SYNC_HANDLERS`。未命中项由 handler 内部转发 `DiscoverySyncHandler` 暂存（§5.7）。

### 5.3 `soc_asset_sources` 落点映射【设计】

> 【实证】该表已存在且带 `UniqueConstraint(asset_id, source)`，**不需要新增资产表**；只需把 `source` 枚举值扩展为 `arl-next`。

| 字段 | 取值 | 说明 |
|---|---|---|
| `asset_id` | SOC UUID | §5.2 对齐后的主键 |
| `source` | `arl-next` | 新增枚举值（不改表结构） |
| `source_id` | **优先 ARL `scope_id`**，其次 `_id` | 稳定锚点，见 §5.4 命名空间决策 |
| `source_status` | ARL 站点 status / 任务 status | 来源视角状态 |
| `last_seen_at` | ARL 扫描时间 | 证据新鲜度，驱动影子资产老化策略 |
| `source_metadata` | JSONB：`{arl_version, scope_id, task_id, target, ports_count, vulns_count, profile_digest}` | **只放摘要**，不放全量画像（避免 Token 与存储膨胀） |

### 5.4 命名空间决策：用 `scope_id`，不用 `task_id`

| 依据 | 说明 |
|---|---|
| 【实证】`API_GUIDE.md:131-140` | ARL 明确区分「任务临时成果（按 `task_id`）」与「资产组归档资产（按 `scope_id`）」两套独立 MongoDB 集合与索引 |
| 【实证 + 本地实测】`mcp_asset.py`；`/api/asset_*` 全端点 200 | 归档态端点全部存在且可用（§2.4），是长期稳定视图 |
| 【设计】结论 | 采集器一律走 `/api/asset_*?scope_id=...`；`task_id` 仅作为 `source_metadata` 内的溯源信息，不作为资产身份 |

### 5.5 字段映射表（ARL → SOC）【设计】

| ARL 字段 | SOC 目标 | 映射规则 | 约束 / 冲突 |
|---|---|---|---|
| `target` / `ip` / `site` | `soc_assets.asset_ip` / `public_ip` | IPv4/IPv6 规范化、去协议/端口/路径 | `public_ip` 有唯一部分索引；内网 IP 不写 `public_ip` |
| 新发现 IP（无匹配） | `data_type=discovery` | **经 `DiscoverySyncHandler` 暂存 → F1.3 → 确认工作台** | 不得直写 `soc_assets`（§4.1 修正） |
| `ports[] {port, service, version, state}` | `soc_asset_ports` | 按 `(asset_ip, port, protocol)` upsert | 唯一键已存在；`sources` JSONB 追加 `arl-next`，`last_seen_by_source` 记录观测时间 |
| Web 指纹（`site.finger[]`，8894 条指纹库） | `source_metadata.web_fingerprint`（一期） | 站点→URL/标题/指纹摘要；资产详情页消费 | 不进 `soc_assets` 业务列；二期评估 AssetComponent（SBOM 方向） |
| `vulns[]` / `nuclei_result[]` **有 CVE 编号** | `soc_vulnerabilities` + `soc_asset_vulnerabilities(scanner='arl-next')` | 结构化落库；`detected_at` 用 ARL 验证时间 | ⚠️ 冲突 2：`scan_task_id` 是 UUID FK——**在 SOC `soc_scan_tasks` 建一条「ARL 同步批次」轻量记录换取 UUID**（顺带进任务中心可观测） |
| `vulns[]` / `nuclei_result[]` / 弱口令 **无 CVE** | **`soc_scan_findings`（评审修正新增旁路）** | `discovery_source='arl-next'`；每轮同步生成批次 `scan_task_uuid`（软关联，不强制 FK）；ARL `task_id`/插件名/URL 存 `raw_data` JSONB | ⚠️ 冲突 1 修正：原稿"只落 source_metadata 摘要"信息损失过大——Swagger 泄露类高价值发现应完整保留并进发现清单 UI |
| `web` / `cert` / `geo` / `asn` / `os` | `soc_assets.os_name` / `source_metadata` | 富化字段，不覆盖业务属性 | 不得覆盖 owner / 重要性三维 / 等保等级 |
| `scope_id` | `soc_asset_sources.source_id` | 稳定锚点 | — |
| 企业生态画像（`get_enterprise_profile`） | 资产组 / 业务系统映射 | 一期不接入，二期评估 | ⚠️ 冲突 3：ARL 企业画像维度（ICP/APP/小程序/投资关系）在 SOC 无对应模型，需先定义 |

### 5.6 三个硬冲突的处置【设计，评审修正】

| 冲突 | 一期处置（修正版） | 后续 |
|---|---|---|
| **冲突 1**：`soc_vulnerabilities.cve_id` UNIQUE NOT NULL，ARL 大量 PoC/弱口令结果无 CVE | **双落点分流**：有 CVE → 漏洞模型（走 `scanner='arl-next'`，SLA 机制现成）；无 CVE → **`soc_scan_findings` 旁路**（`discovery_source='arl-next'` + 批次 UUID，完整保留插件名/URL/raw_data），复用发现清单 UI 与一键纳管入口 | 若后续需要把 PoC 发现升级为正式漏洞记录，经确认工作台人工确认后补建 `soc_vulnerabilities` 行（仍只建议不裁决） |
| **冲突 2**：ARL `task_id`(24 位 ObjectId) 与 SOC `scan_task_id`(UUID FK) 类型不兼容 | 漏洞路径：SOC 侧为每轮同步建一条 `soc_scan_tasks`「ARL 同步批次」轻量记录（mode=arl_sync，status=done）换 UUID——顺带获得任务中心可观测性与审计；发现路径：`soc_scan_findings.scan_task_uuid` 为**软关联**（实证：跨表不强制 FK），直接用批次 UUID | ARL 原 `task_id` 一律存 `raw_data`/`source_metadata` 溯源 |
| **冲突 3**：企业生态维度无落点 | 不接入 | 与资产拓扑方案（`soc_graph_*`）一并评估 |

### 5.7 多源融合接入设计（v1.1 补充：接现成融合引擎，不新建）

【实证】S1 多因子融合引擎已于 2026-10-05 落地（OH-4.1 done，`services/identity_fusion.py`，Session #18；融合/信任共 47 例测试全绿）：`AssetSyncHandler` 写入路径已接入融合判定——IP 命中直接对齐；IP 未命中查身份候选（MAC / agent_id / hostname 强信号一致自动合并，含 IP 漂移 `allow_ip_update`）；无候选新建。配套 `entity_resolver.py` / `port_fusion.py` / `data_source_resolver.py` 同期落地。**ARL 接入 = 向既有融合体系喂一个新来源，不写新融合引擎。**

三类 ARL 数据的融合路径：

| ARL 数据形态 | 融合路径 | 落点 |
|---|---|---|
| IP 在台账已有 | IP 精确命中（`public_ip` 唯一部分索引 / `asset_ip`）→ 写来源溯源 | `soc_asset_sources(source='arl-next')` |
| IP 未命中、仅主机名等弱信号 | 【设计】**不自动合并**——ARL 无 MAC / agent 强信号，主机名候选合并留待实测评估误合率，主体走 IP 精确匹配（保守起步） | 同上（保守起步） |
| 全新 IP | **不入台账**：handler 内部转 `DiscoverySyncHandler` 暂存 → F1.3 判 shadow → 确认工作台人工确认 → 确认后 `data_source='arl-next'` 入账；此后其它来源数据自动走融合判定（IP 锚点已建立） | 发现暂存 → 确认后入台账 |
| 端口 / 指纹 | 端口级多源**并存不覆盖**：`sources` JSONB 追加 `arl-next`、`last_seen_by_source` 各记观测时间；Web 指纹进 `source_metadata`（ARL 独有维度，不挤占业务列） | `soc_asset_ports` |
| 漏洞 / 发现 | 有 CVE → 漏洞模型（`scanner='arl-next'`，与 wazuh / scap 并存不冲突）；无 CVE → `soc_scan_findings` 旁路 | §5.6 冲突 1/2 |

**漏洞置信度分层**（喂给 S5 VPT+ 修复优先级排序）：

| 来源 | 性质 | 置信度 |
|---|---|---|
| ARL PoC（nuclei 实测） | **已验证存在** | 高——修复排序靠前 |
| CISA KEV | 已知在野利用 | 中高 |
| SCA / SCAP | 披露库 | 中 |

### 5.8 冲突裁决权威表（v1.1 补充）【设计】

| 字段 / 判定 | 权威顺序 | 说明 |
|---|---|---|
| owner / 重要性三维 / 等保 / 标签 | **人工与业务系统** | ARL 永不覆盖（C1 / §3 边界） |
| OS | Wazuh agent（主机直证）＞ ARL（远程探测推断）＞ nmap | ARL `os_info` 仅作 `source_metadata` 富化 |
| 端口开放状态 | 多源并存展示 | ARL「看见」≠ 其它来源「错」；对外暴露面结论以 NAT 映射（`soc_maps_to`）+ scanner 实测为准 |
| 失联（offline）判定 | **以管理通道为准**（Wazuh agent / 路由器） | ARL 观测仅作参考证据展示，**不阻止失联判定**——外部探测可达 ≠ 管理通道在线 |
| 域名 → IP | 仅作匹配辅助证据 | 域名不做资产身份锚（ARL 无稳定域名 UUID） |

**时间语义**：`last_seen_at` 各源**各自记录**——「ARL 说活着」与「Wazuh 说活着」是两个独立证据；`effective_status` 统一口径（失联一致为离线）继续以管理通道为判定依据。

## 10. 与 AI-miniSOC 既有体系的衔接与增强（评审修正新增）

### 10.1 S2 暴露面交叉验证（二期候选，双方集成的独特价值）

AI-miniSOC 已有**内→外视角**：`soc_maps_to`（NAT 映射，tplink-collector 5min 同步）+ `/exposure/lookup|rules` API；ARL 提供**外→内视角**（公网 IP 资产 + 站点 + 端口实测）。两侧对齐后可做**双向对账**：

- ARL 从外部看到的公网开放端口 应与 `soc_maps_to` NAT 映射一致 → **不一致 = 配置漂移 / 未登记映射**的强信号，自动入稽核；
- ARL 观测到的 `ip_type=PUBLIC` + `is_cdn` 可反哺 `soc_assets.public_ip` / `exposure_level` 富化（只富化不裁决）。

这是单独任一系统都做不了的检测，列为二期能力（**OH-ARL.10**，与 MCP Client Gateway 同期）。

### 10.2 三期路线评估：scanner agent 注册 vs MCP 受控写

SOC 扫描控制面已有成熟的**扫描器注册体系**：`soc_scanner_agents`（scanner_id UUID + API Key）+ 心跳/拉任务 + watchdog 离线监测 + 按任务 mode 路由（nmap 任务→nmap collector）。三期可评估把 ARL 注册为一种 scanner agent（mode=web_poc / web_fingerprint 路由到 ARL REST 任务创建 API），**复用整个控制面**；MCP `create_scan_task` 仅作为不走控制面的兜底。决策待三期 POC 后拍板。

### 10.3 复用清单对照（新端点/新组件立项前必查）

本方案全部落点均为复用或最小新增：`soc_asset_sources`（复用）｜`soc_asset_ports` JSONB（复用）｜`soc_scan_findings`（复用旁路）｜`discovery` handler（复用）｜确认工作台（复用）｜同步批次任务（复用 `soc_scan_tasks`）｜source_health/死信（复用）｜`mcp_key` 作用域（复用）｜`identity_fusion` 融合引擎（复用，§5.7）｜**新增仅**：arl-collector、2 个 handler（含 handler 内 IP 匹配）、MCP Client Gateway（二期）、前端健康卡通用化重构（OH-ARL.8，替代既有特例）。符合「实施方案 §九」复用规约——无同义重造。
