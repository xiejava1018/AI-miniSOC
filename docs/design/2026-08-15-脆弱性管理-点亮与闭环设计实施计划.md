## 0. 范围声明（最重要）

**本计划不是"从零开发脆弱性管理"，而是把一套已经写好的代码"点亮"并补齐闭环。**

经代码实测，脆弱性管理后端骨架（模型 + AI 评分 + Wazuh 同步 + 一整套 REST API）和前端页面（概览/列表两个 Vue）**已经存在**。真正的问题不是"没写"，而是：

- 后端路由**没注册**进应用 → 所有接口不可达；
- 前端页面**没挂菜单/路由** → 界面上无入口；
- 两个关键能力是**桩/TODO**（扫描任务执行、`has_exploit` 威胁情报）；
- 一处**数据契约硬伤**会让 AI 建议接口直接崩溃（`exposure_level` 列缺失）。

因此本计划以"低风险先点亮、再逐步闭环"为主线，**拒绝重写**，最大化复用现有代码。

## 2. 目标与成功标准

**总目标**：让已有脆弱性管理能力在系统中"可用、可信、可闭环"。

**成功标准（可验收）**：
1. 后端 `/api/v1/vulnerabilities/...` 全部接口可达且冒烟通过；
2. 前端"脆弱性管理"菜单出现，概览/列表页可渲染、数据正确；
3. `GET /vulnerabilities/stats/ai-suggestions` 不崩溃，且评分真实反映 CVSS + 资产关键度 + 暴露面；
4. 高危/严重漏洞可**手动一键**生成事件（复用 Phase 3 链路；"自动生成"无触发规则设计，移 P5，见 §14.5-5）；
5. 修复状态可回写，且有修复时限（SLA）跟踪雏形。

---

## 3. 设计原则

1. **不重写**：全部复用现有模型/服务/API/页面，只做"接线"和"补缺"。
2. **低风险优先**：先点亮（注册路由 + mock 验证），再补质量，最后做闭环。每阶段可独立验证、可回滚。
3. **对齐 v1.0 设计**：导航结构（脆弱性管理 → 概览/列表）、双维度视图（漏洞维度 + 资产维度）、AI 多因子评分均沿用已有定义。
4. **复用闭环范式**：漏洞→事件直接复用 `alert_incident_service.build_incident_from_*` 与 `POST /alerts/.../create-incident` 的成熟模式。

## 4. 详细设计（分 5 阶段）

### Phase 1 — 点亮后端（最小风险，先证明代码是活的）

**目标**：把 `vulnerabilities.router` 注册进应用，用 mock 数据跑通全链路。

**改动**：
- `src/backend/app/api/__init__.py` 增加：
  ```python
  from app.api import vulnerabilities
  api_router.include_router(vulnerabilities.router, prefix="/vulnerabilities", tags=["脆弱性管理"])
  ```
  > 前缀 `/vulnerabilities` 与前端 `vulnerabilities.ts` 的 URL **路径**一致，但**前端封装缺 `/api/v1` 前缀且方法/参数与后端不匹配**（评审 §14.1-P2/§14.3，T13 修复，属 M3 范围）。**注意**：`/vulnerabilities/vulnerabilities` 这种"双写"是已有路由定义决定的，前端封装已按此调用，保持一致即可。
  > **评审修订**：注册时加鉴权——`api_router.include_router(vulnerabilities.router, prefix="/vulnerabilities", tags=["脆弱性管理"], dependencies=[Depends(get_current_user)])`（原端点零鉴权，且含写操作，见 §14.4）。
- **前置 T0（评审新增，§14.1-P1）**：先给 `wazuh_client` 补 `use_mock_data` 开关并接线 `mock_scap_data.py`——否则 sync 端点首行访问该属性即 `AttributeError`，mock 冒烟无从谈起。
- 启动后端，执行冒烟（T1 加鉴权后需带 JWT）：
  - `POST /api/v1/vulnerabilities/sync/wazuh?use_mock=true` → 灌入 mock 数据（依赖 T0）
  - `GET /api/v1/vulnerabilities/stats/overview`
  - `GET /api/v1/vulnerabilities/stats/ai-suggestions`
  - `GET /api/v1/vulnerabilities/vulnerabilities`

**预期**：除 `ai-suggestions` 会因 §5 的 `exposure_level` 缺失而 500 外，其余应正常。这恰好验证 Phase 3 必须先修数据契约。

**验收**：T0 完成后 4 个接口中 3 个 200；`ai-suggestions` 明确 500 且根因定位到 `exposure_level`（ORM 模型缺属性，DB 列已在）。

### Phase 3 — 修数据契约 + 补数据质量（**阻塞项，必须先做**）

> 这是"先想清楚"最关键的一环：不修，AI 评分既崩溃又失真。

**3.1 补 `exposure_level` 列（修崩溃）**
- 在 `app/models/asset.py` 增加 `exposure_level = Column(String(20), default="internal")`（取值 `public/internal/isolated`，与 `vulnerability_ai.EXPOSURE_SCORES` 对齐）。
- ~~新建 Alembic 迁移~~（POC-3 已证 DB 列存在，**仅需模型补一行属性，无需任何迁移**；且评审发现 alembic 迁移图已损坏——两个迁移文件共用 revision `a1b2c3d4e5f6`，**本期一律禁用 alembic**，见 §14.4）。
- 对存量资产按 `network_zone`/`data_classification` 做一次性回填（internal 为默认，公网 IP 段标 public）。

**3.2 对齐 `criticality` 枚举**
- 盘点 `Asset.criticality` 真实取值集合（当前默认 `normal`）。两种修法：
  - (a) 统一为 AI 评分期望的 `critical/high/medium/low`；
  - (b) 在 `vulnerability_ai.CRITICALITY_SCORES` 增加 `normal` 映射并定义语义。
  - **推荐 (a)**：与 `数据库模型设计.md` 的 SQL 视图口径一致，避免双套枚举。需同步排查资产录入/同步处对 criticality 的赋值。

**3.3 取真实 CVSS（修失真）**
- `wazuh_scap_sync._create_vulnerability_from_wazuh`：用 Wazuh 返回的 `cvss3_score`/`cvss2_score`/`cvss_vector` 填充 `cvss_score`/`cvss_vector`，弃用 severity→CVSS 硬映射。

**3.4 （可选，P5 轻量前置）`has_exploit` 接 CISA KEV**
- 新增本地 KEV 表或定时拉取 CISA KEV CSV，`_check_exploit(cve_id)` 改为查表。点亮 AI 评分"在野利用 15%"权重。**此步为可选项**，不阻塞主链路；若本期不做，需在 UI 上明确"在野利用"暂未启用。

**验收**：`ai-suggestions` 返回 200，评分随资产关键度/暴露面明显分化；抽查一条漏洞的 CVSS 为真实值。

### Phase 4 — 漏洞→事件闭环 + 修复 SLA（P1 核心价值）

**目标**：把高危/严重漏洞接入 Phase 3 已成熟的"事件"体系，形成处置闭环。

**4.1 漏洞→事件**
- 新增 `app/services/alert_incident_service.py` 的 `build_incident_from_vulnerability(asset_vuln)`（复用 `build_incident_from_alert` 的字段范式：标题=CVE+资产，描述=风险原因，severity 由漏洞 severity 映射）。**关联机制（评审明确，§14.5-4）**：复用 `_persist_incident` 现成 `asset_ids` 参数走 `AssetIncident` 关联 + 描述内嵌 CVE/av_id，**零 schema 变更**（`Incident` 表无 `asset_vulnerability_id` 字段，勿加列）。
- 新增 `POST /api/v1/vulnerabilities/asset-vulnerabilities/{av_id}/create-incident`（参照 `POST /alerts/groups/{fp}/create-incident`）。
- 前端漏洞详情/列表增加「生成事件」按钮，调用该接口。

**4.2 修复时限（SLA）跟踪（雏形）**
- `AssetVulnerability` 增加 `due_date`（严重 X 天/高危 Y 天，可配）与 `sla_status`（normal/warning/overdue）。
- 在概览页/列表增加 SLA 逾期标记与统计。
- 本期为"雏形"：仅计算与展示，不强制工单流转（v1.0 明确"不做修复工单"，保持范围）。

**验收**：高危漏洞可一键生成事件（UUID），事件详情可回溯到资产+漏洞；逾期漏洞在列表高亮。

### Phase 5 — 扫描任务执行 或 明确替代（收尾决策）

**决策点**（二选一，建议 b）：

## 10. 脆弱性治理的 AI 应用场景、设计与体现（AI-miniSOC 定位）

### 10.1 定位

AI-miniSOC 的脆弱性 AI **不是"又一个扫描器"**，而是**在已有漏洞数据之上做"决策增强"**——把"先治噪声 → 闭环"的战略原则落到漏洞域。价值不在发现漏洞（那是 Wazuh 的活），而在：**哪一个最该先修、为什么、怎么修、是否要 escalation 成事件**。

### 10.2 应用场景清单（分两级）

**Level 1 — 确定性（实时、可解释、不依赖 LLM，做"脊柱"）**
1. **智能风险评分与优先级排序**：CVSS×0.4 + 资产关键度×0.25 + 暴露面×0.2 + 在野利用×0.15。
2. **资产上下文暴露面推断**：用 `network_zone`/`data_classification`/是否公网推断 `exposure_level`（顺带补上缺失列）。
3. **噪声抑制 / 误报收敛**：呼应"先治噪声"——对"包存在但不可达、已有缓解、CVSS 低且内网隔离且无关键业务"的低信号漏洞降权/隐藏。

**Level 2 — LLM 增强（GLM/智谱，走三级降级，做"解释与富化层"）**
4. **漏洞自然语言解读**：对单条 CVE+资产组合，用大白话解释"对我业务意味着什么、该不该修、怎么修"。
5. **漏洞→事件自动研判与富化**：生成事件时，AI 把关键度/暴露面/在野利用/影响资产上下文编成 enriched 描述。
6. **告警-漏洞跨域关联**：同资产"漏洞 + 告警 + KEV 在野利用"叠加 → 高置信入侵信号，提升事件等级。
7. **趋势与薄弱点画像**（P5）：周报/知识库叙事，定位哪类资产/业务风险累积最快。
8. **修复编排建议**（P5/SOAR）：自动生成修复 playbook 草稿。

### 10.3 两级 AI 架构设计（核心设计原则）

```
┌─ 脊柱：确定性多因子评分 (VulnerabilityAIService.calculate_risk_score) ─ 实时、可解释、零 LLM 依赖
│       → 驱动概览榜 / ai-suggestions / score-breakdown
│
└─ 增强层：LLM 解读 / 富化 / 关联 (GLM/智谱)
        → 复用告警研判的「三级降级」：缓存 → Pi Agent → GLM → 启发式兜底
        → 保证离线 / 密钥失效时降级不崩（与告警治理完全一致）
        → 缓存范式：仿 soc_alert_group_analyses 增加 soc_vuln_analyses 缓存表
```

设计要点：
- **确定性评分是" spine "**，LLM 是" explanation & enrichment "——评分永远可用；LLM 仅增强可读性与决策上下文。
- **严格复用现有 AI 基础设施**（GLM 客户端、三级降级、`build_incident_from_*` 富化范式），不另起炉灶。

### 10.5 与告警 AI 研判的复用与区别

- **复用**：GLM 客户端与三级降级、`soc_*_analyses` 缓存范式、`build_incident_from_*` 事件富化范式、前端「AI 研判详情」面板范式。
- **区别**：告警研判多为 LLM 直接生成结论；漏洞评分是**确定性多因子**（可审计、可解释），LLM 只做"解释与富化"，不参与评分本身——这保证即使 LLM 全部失效，优先级排序依然成立。

- **决策**：不做独立扫描引擎；明确 Wazuh（SCAP+SCA）已是**持续扫描源**，`scan-tasks` 仅作为"手动触发一次 Wazuh/OpenSearch 重新评估 + 落库"的轻封装。
- **设计**：
  1. `POST /scan-tasks`（当前仅建记录、`add_task` 被注释）：创建任务记录后，后台（复用 `BackgroundTasks` 或调度）调用 `WazuhSCASyncService.sync_all_sca_checks` + M2 实现的 `OpenSearchSCAPSyncService.sync_all`，执行完回写 `status=completed`、`progress=100`、`result_summary`。

  3. **UI/文档明确**："数据来源 = Wazuh 持续扫描（自动），本按钮 = 按需立即刷新一次"。
  4. 不实现 OpenVAS 深度扫描（与"先治噪声、不重复建设"原则一致）。
- **验收**：① 点"立即扫描"后后端真实拉取 Wazuh/OpenSearch 并落库，进度/结果回写；② 前端明确展示"持续扫描源：Wazuh"；③ 不产生与持续扫描冲突的重复引擎。
