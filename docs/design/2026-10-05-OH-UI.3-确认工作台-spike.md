## 1. 问题回顾

`_try_identity_fusion`（`app/services/sync_handlers/asset_sync_handler.py:316`）：

- `auto_merge` → 已合并（updated）
- `needs_review` → **仅 `logger.warning` + 返回 skipped，不持久化**
- `distinct` / 无候选 → 正常新建

后果：冲突观测每次同步重复判定、人工无入口、「防重复资产」只防了一半。

## 2. 表结构：`soc_attribution_reviews`

### 2.1 字段

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | gen_random_uuid |
| `status` | String(20) NOT NULL, default `pending` | 见 §3 状态机：`pending` / `merged` / `created` / `dismissed` |
| `review_kind` | String(20) NOT NULL | v0.1 固定 `identity_conflict`（为未来「非融合类归属问题」预留枚举，不做抽象表） |
| `observation` | JSONB NOT NULL | 触发复核的原始观测（进入 sync 的 item，**剔除过大字段**，见 2.4） |
| `observation_fingerprint` | String(64) NOT NULL | 观测指纹，sha256，用于去重（算法 2.3） |
| `source` | String(50) NOT NULL | 观测来源（sync handler 的 source） |
| `sync_task_id` | UUID FK → soc_sync_tasks(id) ON DELETE SET NULL NULL | 首次触发时的同步任务（可追溯） |
| `asset_id` | UUID FK → soc_assets(id) ON DELETE SET NULL NULL | **最终裁决关联的资产**（merged：候选资产；created：新资产；pending 阶段为 NULL） |
| `candidate_asset_id` | UUID FK → soc_assets(id) ON DELETE SET NULL NULL | 评分最高的候选资产（pending 阶段即可展示） |
| `best_score` | JSONB NOT NULL | 最佳候选的 `FusionResult.to_dict()`（confidence / factors / conflict_factors 等，支撑工作台详情） |
| `candidate_count` | Integer NOT NULL default 1 | 候选数量（供列表展示） |
| `occurrence_count` | Integer NOT NULL default 1 | 同一指纹重复触发次数（见 2.3） |
| `last_occurred_at` | DateTime(tz) NOT NULL | 最近一次触发时间（每次重复时更新） |
| `resolved_by` | String(255) NULL | 裁决人用户名快照 |
| `resolved_at` | DateTime(tz) NULL | 裁决时间 |
| `resolve_note` | Text NULL | 裁决备注 |
| `created_at` | DateTime(tz) NOT NULL server_default now | |
| `updated_at` | DateTime(tz) NOT NULL server_default now onupdate now | |

### 2.2 索引

| 索引 | 用途 |
|---|---|
| unique partial：`(observation_fingerprint) WHERE status='pending'` | **同指纹只允许一条 pending**——pending 队列去重的硬保证，裁决后指纹释放，允许再次进入 |
| `(status, created_at DESC)` | 工作台列表主查询 |
| `(candidate_asset_id)` | 「这台资产关联过哪些待复核」 |
| `(asset_id)` | 裁决后追溯 |

### 2.3 去重 / 指纹算法

在 `needs_review` 分支落表前计算指纹：

```
fingerprint = sha256(json.dumps({
    "asset_ip": observation.asset_ip,
    "mac_address": observation.mac_address,
    "wazuh_agent_id": observation.wazuh_agent_id,
    "name": observation.name,
}, sort_keys=True, default=str))
```

- 命中 pending（靠唯一索引，`INSERT ... ON CONFLICT` 或先查后插）→ **不新增行**，`occurrence_count += 1`、`last_occurred_at = now()`、`best_score` 更新为最新评分
- 无命中 → INSERT，`occurrence_count = 1`

说明：指纹以「身份信号四元组」为键，不含 source/timestamp/端口等易变字段。候选集变化（如候选资产被删除）不产生新行，评分刷新即可。

### 2.4 observation JSONB 白名单

为避免无界字段入库，observation 只存：`asset_ip / mac_address / name / os_name / os_version / wazuh_agent_id / network_segment / network_zone / hardware_info / asset_type` 及若干身份相关键；端口列表、长描述等易变大字段不存（端口在资产侧另有融合）。白名单常量放 service。

## 3. 状态机

```
                 POST /resolve  decision=merge
        pending ───────────────────────────────► merged
          │
          │  POST /resolve decision=create
          ├──────────────────────────────────────► created
          │
          │  POST /resolve decision=dismiss
          └──────────────────────────────────────► dismissed
```

- `pending` 是唯一可处理入口；三个终态**互斥、不可逆**（参照 `soc_asset_reconciliations` 的既有约定）。
- 终态行不可再被重复触发逻辑更新；同指纹再次冲突 → 产生一条新的 pending（唯一 partial index 已释放）。

### 3.1 裁决动作语义

| decision | 服务端动作 | asset_id 写入 |
|---|---|---|
| `merge`（body 可选 `target_asset_id`，默认 candidate） | 复用 sync handler 的合并路径执行合并（含 IP 漂移更新 + AssetSource upsert + change log），不是新写一套合并逻辑 | 目标资产 id |
| `create` | 以 observation 走 `_create_new` 等价路径新建资产 | 新资产 id |
| `dismiss`（note 必填？建议可选） | 不动作，仅终态 | NULL |

- `merge.target_asset_id` 若不在原候选集内 → 422（防止越过评分依据乱合并；候选快照可从 best_score/candidates 校验，候选 id 存入 best_score 不够，见下）。
- **补充**：为支持「候选资产不只是最高分那个」，v0.1 在 `best_score` 之外再加 `candidates` JSONB 列？→ **决策点 D-OH3-1**（见 §7）。建议加 `candidates JSONB NOT NULL`：全部候选 `[{asset_id, asset_ip, name, score: FusionResult.to_dict()}]`，列表/详情一次取齐，裁决时服务端校验 target ∈ candidates。

## 4. API 设计

路由：`app/api/attribution.py`，`include_human_router(api_router, attribution.router, prefix="/assets", ...)`，最终路径 `/api/v1/assets/attribution/**`。
**必须在 `assets.router`（含 `/{asset_id}` catch-all）之前注册**（与 reconciliation 相同的教训）。

### 4.1 端点

| 方法 / 路径 | 说明 | 权限 |
|---|---|---|
| `GET /assets/attribution/reviews` | 分页列表：`status`（默认 pending）、`review_kind`、`candidate_asset_id`、`page/page_size`；返回 items + total + pending 计数 | 登录可见（viewer+），按钮位 `attribution:view` |
| `GET /assets/attribution/reviews/{id}` | 详情：observation + candidates 全量评分 + 冲突因子 + occurrence 历史概要 | viewer+，`attribution:view` |
| `POST /assets/attribution/reviews/{id}/resolve` | 裁决，body `{decision: merge\|create\|dismiss, target_asset_id?, note?}` | operator/admin，按钮位 `attribution:resolve`；`@log_audit` |

- 统一 envelope（`code/msg/data`，HTTP 恒 200）。
- 并发裁决：两个操作员同时 resolve 同一行 → 用状态条件 UPDATE（`WHERE status='pending'`），失败方返回 code=409 语义（envelope code 409）。
- 列表查询用 `useTable` 约定：`page/page_size` → 返回 `total/items`。

### 4.2 分层

- `app/models/attribution_review.py`：模型 + 状态常量
- `app/services/attribution_service.py`：`create_or_bump_review(...)`（sync handler 调用）、`list/get/resolve`；resolve 内复用 handler 的合并/新建能力
- `app/api/attribution.py`：薄路由

复用方式：把 sync handler 的 `_update_existing / _create_new / _upsert_source_record / _log_change` 中 resolve 需要的部分，抽到可复用函数或让 service 调 handler 方法（handler 当前是实例方法，可直接实例化 `AssetSyncHandler()` 复用；须确认其无外部状态依赖）。**这是实现时的第一个小核查点**，不新写合并逻辑（实施方案 §九 复用纪律）。

### 4.3 sync handler 改动（小）

`needs_review` 分支：

```python
AttributionReviewService(db).create_or_bump_review(
    item=item, source=source, sync_task_id=sync_task_id,
    candidates_scored=[(cand, res), ...], best=(best, best_result), now=now,
)
# 仍返回 "skipped"
```

即 `_try_identity_fusion` 需要把全部候选评分传下去（目前只保留 best，小改）。

## 8. 验收标准（编码完成的 DoD）

1. 制造冲突观测走 sync：`soc_attribution_reviews` 出现 1 条 pending；同观测再 sync，仍 1 条且 `occurrence_count=2`
2. `merge`：资产合并成功（含漂移 IP 更新），review 终态 merged 且 asset_id 正确；不产生重复资产
3. `create`：新资产建成，终态 created
4. `dismiss`：终态 dismissed，资产无变化
5. 并发 resolve：一方成功一方拿到冲突错误
6. 全部写操作落审计 hash 链
7. 后端：新增 service/API 单测 + 端到端；前端：工作台页可从菜单到达，`npm run build` / vue-tsc 无新增错误
8. 迁移在测试库 up/down 均通过；CI 绿
