### 3.2 运行锁（v0.4.1 修订：单 worker 用进程内锁）

> **v0.3 P0-1 阻塞项**：`single_worker_guard.try_acquire_scheduler_lease` 是 `NotImplementedError`，v0.3 整套运行锁机制失效。
>
> **v0.4 原决策**：装饰器自带轻量 PG advisory 会话锁。
>
> **⚠️ v0.4.1 修订**：代码已证实当前部署为**单 worker**（`main.py` 的 `check_single_worker_or_warn()` + 无 `--workers` 配置）。单 worker 下防 tick 重叠只需进程内 `asyncio.Lock(task_key)` 这一**唯一正确的最小解**；PG advisory 会话锁不仅 YAGNI，且**锁随 Session 关闭自动释放、无法保护 body 执行期**（名不副实）。故 v0.4.1 将装饰器运行锁统一改为进程内 `asyncio.Lock`；PG advisory + `soc_scheduler_lease` 表锁整体**移至 §3.10 的 Phase 2 多 pod 方案**，不在 Phase 1 使用。

```python
# app/services/task_observability/lock.py  (v0.4.1：单 worker 用进程内锁)
import asyncio
from typing import Dict

# 单 worker 下：按 task_key 维护进程内互斥锁（协程安全）
_task_locks: Dict[str, asyncio.Lock] = {}

def get_task_lock(task_key: str) -> asyncio.Lock:
    """返回该 task_key 专属的进程内 asyncio.Lock（不存在则创建）。"""
    lock = _task_locks.get(task_key)
    if lock is None:
        lock = asyncio.Lock()
        _task_locks[task_key] = lock
    return lock
```

**装饰器集成（v0.4.2 POC-2 修订）**：

> 🔴 **关键修复**：v0.4.1 原伪代码 `async with lock: await asyncio.wait_for(body(), timeout)` 在 timeout 时会**立即释放锁**，但 `to_thread` 里的同步 DB 代码无法被 cancel 仍在后台跑——下一轮 tick 拿到锁就会造成两个同步线程并发查询 PG。v0.4.2 改为 `create_task + shield + 显式 await` 模式（POC 实测通过）。

```python
@track_task(task_key="browsing_detector", ...)
async def _run_detection_with_track():
    # 装饰器内部（v0.4.2 修订后的正确范式）：
    # 1. lock = get_task_lock(task_key)                  # 进程内 asyncio.Lock
    # 2. if lock.locked():
    #        → 写 run(status=skipped) → return（上一轮仍在进行，不排队）
    # 3. async with lock:                                 # 锁持有到 inner_task 真正结束
    #        write run(status=running)
    #        write registry.current_run_id
    #
    #        inner_task = asyncio.create_task(
    #            asyncio.to_thread(body_sync_impl)       # ★ 同步 body 必须包在 to_thread 里
    #        )
    #        try:
    #            async with asyncio.timeout(timeout_s):
    #                result = await asyncio.shield(inner_task)  # ★ shield 保护
    #            write run(status=success) + registry.last_status=success
    #            return result
    #        except TimeoutError:
    #            # ★ 关键：显式 await inner_task（等同步线程跑完，锁不释放）
    #            try:
    #                result = await inner_task
    #            except Exception as e:
    #                write run(status=failed, error_text=str(e))
    #                return
    #            write run(status=timeout) + registry.last_status=timeout
    #        except Exception as e:
    #            write run(status=failed, error_text=str(e))
    #        finally:
    #            registry.current_run_id = NULL
    #        # 锁由 async with 在 inner_task 真正结束后才释放
    ...
```

**新语义说明**：
- `status=timeout` 表示"业务超过 timeout_s，但代码最终跑完了"
- 锁持有到 `inner_task` 真正结束（可能是 timeout_s 之后 N 秒）
- 期间所有 tick / trigger 看到 `lock.locked()=True` → 写 `skipped` run
- **PG 同步查询绝不并发**（POC-2 实测确认）

> **注（v0.4.1）**：`if lock.locked(): return` 与 `async with lock:` 之间无 `await`，单 worker 协程不会被抢占，不存在竞态。Phase 2 升级多 pod 时，把 `get_task_lock` 替换为 §3.10 的 `soc_scheduler_lease` 分布式锁即可，装饰器 body 不变。

### 3.3 装饰器契约 v0.4（带"半取消"语义）

> **v0.3 P0-3 阻塞项**：`asyncio.wait_for` 包同步 SQLAlchemy Session 的协程场景，cancel 只到协程层、不到 SQL 层。

**v0.4 明确约束**：

```python
@track_task(
    task_key="browsing_detector",       # 必填
    task_type="scheduled",              # scheduled | async | thread | watchdog
    timeout_s=360,                      # 默认 360；启动时校验 >= 30（防 P0-4 配置错误）
    hard_timeout=True,                  # 默认 True；协程场景用 wait_for；线程场景不杀
    source_key="loki:browsing",         # 可选：成功后调 SourceHealthRecorder
    progress=False,                     # 长任务用 ctx.update_progress(...)
)
async def _run_detection():
    """body 必须是协程；body 内部 DB Session 必须用 asyncio.to_thread 调。"""
    # ✅ 正确范式（参考 browsing_detection/scheduler.py:66）
    return await asyncio.to_thread(_sync_body)

def _sync_body():
    db = SessionLocal()  # 同步 Session
    try:
        # ... 同步 DB / I/O
    finally:
        db.close()
```

**“半取消”语义（v0.4.2 POC-2 修订）**：
- v0.4.1 原设计：`asyncio.wait_for(body, timeout=timeout_s)` 在 timeout 时取消协程，同步 to_thread 无法取消——会造成 **锁提前释放 + 同步线程后台跑 + 下轮 tick 拿锁新起 to_thread**，PG 连接池被吃满（POC-2 实测复现）
- **v0.4.2 修正为**：装饰器内部用 `create_task(to_thread) + timeout(shield(task)) + 显式 await task`（详见 §3.2 伪代码）
  - timeout 只取消 shield 外层，inner_task 不受影响
  - timeout 分支 `await inner_task` 等同步线程真正跑完才释放锁
  - 期间所有 tick / trigger 看到 `lock.locked()=True` → 写 `skipped` run
- **新语义**：`status=timeout` = “业务超时，但代码最终跑完了”；不是“被强制中断”
- **PG 同步查询绝不并发**（POC-2 实测：1000 次并发 trigger 只起 1 个同步线程）
- **不强制杀 PG 连接**：Python 线程无法安全 kill，让 SQL 自然结束是唯一正确选择；`pg_cancel_backend` 仅作为 Phase 2 可选项（需 pid 跟踪）

```python
# app/services/task_observability/notification_queue.py
import asyncio
from collections import deque

class NotificationQueue:
    """v0.4.2 POC-3 修订：无锁 deque。
    
    deque.append / list / clear 都是 GIL 保护的原子操作；
    不需要 threading.Lock（在 async 函数里同步 with 会冻结 event loop）；
    也不需要 asyncio.Lock（装饰器异常路径是同步的，不能 await）。
    POC-3 实测：100 并发入队 < 0.3ms；10 producer × 100 条 + 1 consumer 不丢消息。
    """
    def __init__(self, max_size: int = 1000):
        self._queue: deque = deque(maxlen=max_size)
        self._dropped = 0
    
    def enqueue(self, alert_type: str, payload: dict) -> None:
        """同步入队，O(1)，GIL 原子。调用方不需 await。"""
        if len(self._queue) >= self._queue.maxlen:
            self._dropped += 1  # deque 满时 append 会自动弹出最老的；计数仅作观测
        self._queue.append({"alert_type": alert_type, "payload": payload})
    
    def drain_sync(self) -> list:
        """一次性取出所有，同步。
        list() 与 clear() 之间如果有新 enqueue，新项会留到下次 drain（不丢）。
        """
        items = list(self._queue)
        self._queue.clear()
        return items

notification_queue = NotificationQueue()

# 在 lifespan 内启动 drain task
async def _drain_notifications():
    while True:
        await asyncio.sleep(2)
        items = notification_queue.drain_sync()
        notification_queue._queue.clear()
        for item in items:
            await _send_with_fallback(item)

async def _send_with_fallback(item: dict):
    """WS → 站内 → 邮件 三级降级。"""
    from app.services.notification_service import NotificationService
    recipients = resolve_recipients(item["alert_type"])
    if not recipients:
        notification_dropped_total.labels(reason="no_recipients").inc()
        return
    payload = item["payload"]
    notif_type = payload.get("type", "task_alert")   # ★ NotificationService.create 的 type 必填
    title = payload.get("title", "Task alert")
    content = payload.get("content", "")
    link = payload.get("link")
    for user_id in recipients:
        db = SessionLocal()
        try:
            svc = NotificationService(db)
            await svc.create(
                user_id,
                type=notif_type,
                title=title,
                content=content,
                link=link,
                push_ws=True,
            )
        except Exception as e:
            logger.error("WS+inbox send failed for user %d: %s, fallback to email", user_id, e)
            try:
                await _send_email(user_id, payload)
            except Exception as e2:
                notification_dropped_total.labels(reason="all_failed").inc()
                logger.error("All notification channels failed for user %d", user_id)
        finally:
            db.close()
```

### 3.7 告警去重（v0.4 防风暴）

> **v0.3 P0-3 阻塞项**：一个任务持续失败 → 每次 tick 都告警 → 通知库爆炸。

```python
# app/services/task_observability/dedup.py
import hashlib
import time
from collections import defaultdict

class NotificationDeduplicator:
    """简单滑动窗口去重。"""
    def __init__(self, window_seconds: int = 300):  # 5 分钟
        self.window = window_seconds
        self._seen = defaultdict(list)  # key -> [timestamps]
    
    def _key(self, task_key: str, alert_type: str, error_text: str) -> str:
        # error fingerprint: 错误类型 + 错误信息前 100 字符
        fp = hashlib.md5((type(error).__name__ + error_text[:100]).encode()).hexdigest()[:8]
        return f"{task_key}:{alert_type}:{fp}"
    
    def should_send(self, task_key: str, alert_type: str, error_text: str) -> bool:
        key = self._key(task_key, alert_type, error_text)
        now = time.time()
        # 清理过期
        self._seen[key] = [t for t in self._seen[key] if now - t < self.window]
        if self._seen[key]:
            return False  # 窗口内已发过
        self._seen[key].append(now)
        return True

dedup = NotificationDeduplicator()

# track_task 内：
if not dedup.should_send(task_key, "task_deadman_alert", str(e)):
    notification_dropped_total.labels(reason="dedup").inc()
    return  # 5 分钟内同 fingerprint 不重发
```

```python
def find_zombie_runs() -> list[SocTaskRuns]:
    """从 runs 行（每 run 独立）取 last_progress_at。"""
    candidates = db.query(SocTaskRuns).filter(
        SocTaskRuns.status == 'running',
    ).all()
    zombies = []
    for run in candidates:
        reg = db.query(SocTaskRegistry).filter_by(task_key=run.task_key).first()
        if not reg:
            continue
        timeout_s = reg.timeout_s
        age_since_start = (now - run.started_at).total_seconds()
        
        if run.last_progress_at is None:
            # 无进度跟踪：仅 started_at 超时
            if age_since_start > timeout_s:
                zombies.append(run)
        else:
            # 有进度跟踪：started_at AND last_progress_at 都超时
            age_since_progress = (now - run.last_progress_at).total_seconds()
            if age_since_start > 2 * timeout_s and age_since_progress > timeout_s:
                zombies.append(run)
    return zombies
```

### 3.10 多 pod 分布式锁（v0.4.1 修订：Phase 2 才启用）

> **v0.3 P1-10 漏项**：`lock_owner` 写了但没设计续约 / 释放。

> **⚠️ v0.4.1 修订**：本节原属 Phase 1 装饰器锁，现统一降为 **Phase 2 多 pod 才启用**。Phase 1 单 worker 下装饰器运行锁已改为 §3.2 的进程内 `asyncio.Lock`，**不创建 `soc_scheduler_lease` 表、不调用本节函数**。仅当系统升级为多 pod 部署时，才用本节 DB 租约锁替换 `get_task_lock`，实现跨进程互斥（保持接口一致，装饰器 body 不变）。

```sql
CREATE TABLE soc_scheduler_lease (
  task_key     VARCHAR PRIMARY KEY,
  owner        VARCHAR NOT NULL,           -- host:pid
  acquired_at  TIMESTAMPTZ NOT NULL,
  expires_at   TIMESTAMPTZ NOT NULL,        -- now() + TTL
  heartbeat_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_lease_expires ON soc_scheduler_lease(expires_at);
```

**装饰器逻辑**：

```python
def acquire_lease(db, task_key, owner, ttl_s=60):
    now = utc_now()
    expires = now + timedelta(seconds=ttl_s)
    # INSERT ... ON CONFLICT (task_key) DO UPDATE ... WHERE expired OR same owner
    res = db.execute(text("""
        INSERT INTO soc_scheduler_lease (task_key, owner, acquired_at, expires_at, heartbeat_at)
        VALUES (:k, :o, :now, :exp, :now)
        ON CONFLICT (task_key) DO UPDATE
          SET owner = EXCLUDED.owner,
              acquired_at = EXCLUDED.acquired_at,
              expires_at = EXCLUDED.expires_at,
              heartbeat_at = EXCLUDED.heartbeat_at
          WHERE soc_scheduler_lease.expires_at < :now  -- 已过期可抢
             OR soc_scheduler_lease.owner = :o        -- 自己续
        RETURNING owner
    """), {"k": task_key, "o": owner, "now": now, "exp": expires}).first()
    db.commit()
    return res is not None and res[0] == owner

def heartbeat_lease(db, task_key, owner, ttl_s=60):
    """长任务每 30s 调一次，续约。"""
    db.execute(text("""
        UPDATE soc_scheduler_lease
        SET expires_at = :exp, heartbeat_at = :now
        WHERE task_key = :k AND owner = :o
    """), {"k": task_key, "o": owner, "now": utc_now(), "exp": utc_now() + timedelta(seconds=ttl_s)})
    db.commit()

def release_lease(db, task_key, owner):
    db.execute(text("DELETE FROM soc_scheduler_lease WHERE task_key=:k AND owner=:o"),
               {"k": task_key, "o": owner})
    db.commit()
```

**`track_task` 集成（仅 Phase 2 多 pod）**：每 30s 调一次 `heartbeat_lease`（在 long-running body 的 ctx 上提供 `ctx.heartbeat()` API）。Phase 1 单 worker 不启用，装饰器直接用 §3.2 的进程内锁。

### 3.13 MCP 线程节流（v0.4 修 P1-9）

> **v0.3 P1-9 漏项**：MCP 线程型"每 tick 一次 with 上下文管理器"会让 runs 表膨胀（30 天 43200 行）。

**v0.4 决策**：

| 范式 | 行为 | runs 表行数 | 适用 |
|---|---|---|---|
| **每 tick 写 run**（v0.3 方案 1） | 60s 一行 | 43200/30d | 不采纳 |
| **★ 心跳模式**（v0.4） | 失败时写 run；成功 1h 才写一行 status=success | < 100/30d | MCP 刷新器 |
| **★ 异常聚合** | 同 fingerprint 失败 N 次才写一行 | < 50/30d | 业务型 |

**心跳模式伪代码**（v0.4）：

```python
def _mcp_refresher_loop(stop_event):
    consecutive_fail = 0
    last_written_success_at = None   # 上次写 success run 的时间戳
    while not stop_event.is_set():
        try:
            refresh_token()
            # 成功：节流写入——仅在"从失败中恢复"或"距上次写 success > 1h"时写一行
            now = utc_now()
            if consecutive_fail > 0:
                write_run(task_key="mcp_token_refresher", status="success",
                         stats={"recovered": True})
                last_written_success_at = now
            elif last_written_success_at is None or \
                 (now - last_written_success_at).total_seconds() > 3600:
                write_run(task_key="mcp_token_refresher", status="success")
                last_written_success_at = now
            consecutive_fail = 0
        except Exception as e:
            # 失败：仅首次失败立即写一行（后续失败由去重器抑制，见 §3.7）
            if consecutive_fail == 0:
                write_run(task_key="mcp_token_refresher", status="failed", error_text=str(e))
            consecutive_fail += 1
        stop_event.wait(60)
```

## 13.5 POC 验证记录（v0.4.2 新增，2026-08-16）

> 在正式编码前做 3 个关键 POC，验证 v0.4 设计的技术可行性。**2 个有问题、1 个通过**。

### POC-1：`asyncio.Lock` 必要性 ✅ 通过

**验证问题**：v0.4 §3.2 引入的进程内 `asyncio.Lock` 是否真的需要？

**实测结论**：
- 5 个现有 scheduler（browsing/alert_snapshot/alert_digest/cisa_kev）全部是**单协程顺序循环**：`while True: await body(); await sleep(interval)`——**body 完成后才 sleep**，自身不可能 tick 重叠
- 但 **trigger API 是外部 HTTP 请求**，会 `asyncio.create_task(_execute_with_tracking(...))` 起新协程——**与定时 tick 真的会重叠**（实测第 0.3s 触发 manual 时，tick-0 已在跑，两者并发执行 body）
- **结论**：锁必须保留，防止 manual trigger × tick 重叠。v0.4 §3.2 设计正确。

### POC-2：`wait_for` 半取消 + lock 释放 🔴 发现严重 bug

**验证问题**：v0.4 §3.2/§3.3 的伪代码 `async with lock: await asyncio.wait_for(body(), timeout)` 在 timeout 后是否真的能防并发？

**实测数据**（timeout_s=2s, body_duration=5s）：
```
[tick-0] LOCKED at t=0.00s
  [thread] sync body start at t=0.00s
[tick-0] TIMEOUT at t=2.00s, will release lock
>>> tick-0 returned 'timeout' at t=2.00s, lock.locked()=False  ← 锁释放！
  [thread] STILL RUNNING (to_thread 同步代码未被取消)
--- 0.5s later ---
[tick-1] LOCKED at t=2.50s  ← 新 tick 拿到锁！
  [thread] sync body start at t=2.50s  ← 两个同步线程并发跑！
```

**问题根因**：
1. `asyncio.wait_for` timeout 时**会 cancel inner task**（包括 `to_thread` 创建的协程包装）
2. 但 `to_thread` 跑的同步代码**无法被 cancel**——继续在后台线程跑到自然完成
3. `async with lock` 在 `except TimeoutError: return` 时**立即释放锁**
4. 下一轮 tick 拿到锁 → 又开新 `to_thread` → **PG 同步查询并发翻倍**
5. 反复 timeout 会持续累积线程，最终吃满 PG 连接池

**🔴 v0.4 §3.2/§3.3 必须改为以下模式**（POC 实测通过）：

```python
async def tracked_run(task_key, body, timeout_s):
    lock = get_task_lock(task_key)
    if lock.locked():
        write_run(status='skipped')
        return
    async with lock:
        write_run(status='running')
        # ★ 关键 1：先 create_task 包 to_thread，拿到 task 引用
        inner_task = asyncio.create_task(asyncio.to_thread(body))
        try:
            # ★ 关键 2：shield 保护 inner_task，timeout 只 cancel 外层
            async with asyncio.timeout(timeout_s):
                result = await asyncio.shield(inner_task)
            write_run(status='success')
            return result
        except TimeoutError:
            # ★ 关键 3：timeout 后显式 await inner_task（等同步线程跑完）
            # 此时 async with lock 仍持有，下一轮 tick 会看到 lock.locked()=True → SKIPPED
            try:
                result = await inner_task
            except Exception as e:
                write_run(status='failed', error_text=str(e))
                return
            write_run(status='timeout')  # 业务语义：超时了但代码跑完了
```

**新语义**：
- status=timeout 表示"业务超过 timeout_s，但代码最终跑完了"
- 锁持有到 inner_task 真正结束（可能是 timeout_s 之后 N 秒）
- 期间所有 tick / trigger 看到 `lock.locked()=True` → 写 `skipped` run
- **PG 同步查询绝不并发**

**Tradeoff**：单个卡住的任务会让后续 N 轮 tick 全部 skipped——这是**正确行为**（既然同步代码无法取消，就应让它独占，不允许叠加）。

### POC-3：`NotificationQueue` 锁实现 🟡 建议改

**验证问题**：v0.4 §3.6 用 `threading.Lock` 在 async 函数里同步 `with`，是否会阻塞 event loop？

**实测数据**（100 并发 enqueue + 1 drain）：
| 实现 | 耗时 | 1000 条 10p+1c 丢消息 |
|---|---|---|
| v0.4 原设计 `threading.Lock` | 0.34ms | — |
| `asyncio.Lock` | 0.25ms | — |
| **✅ 无锁 `deque`** | **0.29ms** | **0 丢** |

**结论**：
- 单条入队微秒级，`threading.Lock` 实际不会致命卡死 event loop
- 但在 async 函数里用同步锁是**反模式**，没好处只有隐患
- `asyncio.Lock` 要求 enqueue 是 async——但装饰器异常路径是同步的，不能 await
- **✅ 最佳方案：用无锁 `collections.deque(maxlen=N)`**——`append/pop/clear` 都是 GIL 保护的原子操作
  - enqueue 保持同步（`q.enqueue(item)` 即可，不需要 await）
  - drain 用 `list(q._queue); q._queue.clear()` 也安全
  - 实测 10 producer × 100 条 + 1 consumer 并发，0 丢消息

**v0.4 §3.6 必须改的代码**：

```python
# 旧（有问题）
class NotificationQueue:
    def __init__(self):
        self._queue = deque(maxlen=1000)
        self._lock = threading.Lock()  # ⚠️ 删
    def enqueue(self, item):
        with self._lock:  # ⚠️ 删
            self._queue.append(item)

# 新（POC 验证）
class NotificationQueue:
    def __init__(self, max_size=1000):
        self._queue = deque(maxlen=max_size)
        self._dropped = 0
    def enqueue(self, item):
        if len(self._queue) >= self._queue.maxlen:
            self._dropped += 1  # 统计但不阻塞
        self._queue.append(item)  # GIL 原子
    def drain(self) -> list:
        items = list(self._queue)
        self._queue.clear()
        return items
```
