# AI-miniSOC 行为画像 · 两层结构改造方案

> 版本: v1.2（实施完成，验收记录见 §8）
> 日期: 2026-09-06
> 作者: 产品通（产品管理视角）
> 上游文档: `docs/design/2026-09-05-用户IP行为画像-方案设计.md`（v1.5）
> 触发: 用户实测 `http://localhost:5173/#/browsing/profile` 后发现 3 处偏差 + 1 个结构性设计问题

---

## 1. 背景：实测发现的偏差

### 1.1 三处偏差（已代码级验证）

| # | 偏差 | 严重度 | 证据 | 性质 |
|---|------|--------|------|------|
| **D1** | 详情页左栏是「全部画像主体列表」，而设计 §3.1 要求「该 IP 身份档案卡」 | 🔴 P0 | 设计 §3.1 原文："层 1 固定占据详情页**左栏身份档案卡**，不随 Tab 切换消失"；`views/browsing/profile/index.vue:5-53` 实为 `sortedSubjects` 列表 | **违反设计文档** |
| **D2** | 关系画像 Tab 无任何关系网络拓扑，只有三张表（设备共享度/入站/出站） | 🟠 P1 | `index.vue:294-353` 无图表组件 | **设计承诺未兑现**（§3.4 关系画像） |
| **D3** | 异常判定 Tab 几乎无数据 | 🟢 P2 | 见 §2 根因诊断 | **非 bug，数据积累不足** |

### 1.2 一个结构性问题

> **菜单叫「行为画像」（群体概念），点进去却是「某 IP 的画像详情」（个体概念）—— 名实不符。**

当前 `/browsing/profile` 页面实际做的是 **L2 单 IP 详情**的活，但却挂在「行为画像」这个群体语义的菜单下，且左栏塞了主体列表来做妥协。这是 D1 的根本成因。

**结论：必须拆成两层。**

## 2. D3 根因诊断：异常判定为什么没数据

### 2.1 实测数据（2026-09-06 16:20）

| 实测项 | 结果 |
|--------|------|
| 画像主体总数 | 74 |
| **快照日覆盖** | **仅 `2026-09-04` 一天**（74 主体全部） |
| 数据量 | 74 主体中 **59 个 total < 50**，中位数 = 0 |
| confidence 分布 | 0 分占 54/74；100 分占 7/74 |
| traffic_type | **74 个全部 human**（无 machine / mixed） |
| 实际异常信号 | .8 / .102 各 1 条（"低置信度"）；.100 / .17 / .25 各 0 条 |

### 2.2 根因

`services/behavior_profile/service.py:350` 的硬门槛：

```python
if len(ok_rows) >= 4:        # ← 需要 ≥4 个有效快照日
    latest, baseline = ok_rows[-1], ok_rows[:-1]
    # 访问量激增 / 节律突变 / 机器流量 / 数据截断 四条核心规则
```

当前只有 **1 天**快照 → 核心规则全部跳过，只剩两个兜底信号：
- `gap_days` 数据缺失
- `confidence < 40` 低置信度

**这不是 bug，是快照任务刚上线、数据尚未积累。** 跑满 4 天后核心规则自动点亮。

### 2.3 顺带发现的真问题（新 P1）

**`traffic_type` 判定失效**：74 个主体全为 human，但 .17 是 NAS 下载机（POC 时正确判为 machine）。

实测 .17 的 `layer_visit = {ACT: 91.1%, SYS: 8.9%}` —— SYS 层仅 8.9%，远低于 machine 阈值 60%（`aggregator.py:75`）。

**推论**：`layer_visit` 三层分类器（ACT/SYS/AD）把机器心跳误归入了主动行为层 ACT，导致 `compute_traffic_type()` 永远判不出 machine。

> **修复方向**：审计 `classifier.py` 的 SYS 层规则覆盖（STUN/NTP/DNS/CDN 心跳的域名与 UA 特征），或降低 machine 阈值 + 引入"域名集中度 + 24h 曲线平直度"作为辅助判据（设计 §9.7.1 原文就写了"分布高度集中于少数域名且无时段起伏"，但代码只实现了 SYS 占比单判据）。

## 3. 两层结构设计

### 3.1 总体结构

```
菜单「上网行为 › 行为画像」
        │
        ▼
┌─────────────────────────────────────┐
│ L1  行为画像概览（群体画像）           │  /browsing/profile
│  · 群体统计卡（人设分布/风险分布）      │
│  · 全网活跃节律 / 兴趣构成             │
│  · 画像主体列表（74 个，可筛选排序）    │
└─────────────────────────────────────┘
        │ 点击某个 IP
        ▼
┌─────────────────────────────────────┐
│ L2  单 IP 画像详情                    │  /browsing/profile/:ip
│  左栏：身份档案卡（固定，不随 Tab 切）  │
│  右栏：行为 / 风险 / 关系 / 异常 4 Tab │
└─────────────────────────────────────┘
        ▲
        │ 直接跳转（?ip= / :ip）
  资产列表 · 告警详情 · 行为基线
```

### 3.2 路由与菜单

| 层级 | 路径 | 组件 | 菜单 |
|------|------|------|------|
| L1 概览 | `/browsing/profile` | `views/browsing/profile/index.vue`（**重写**） | 「行为画像」path=`profile`（已注册，id=22 下） |
| L2 详情 | `/browsing/profile/detail/:ip` | `views/browsing/profile/detail.vue`（**新建**） | 隐藏菜单行（DB `is_visible=false`，不占侧边栏） |

> **路由注册机制（v1.1 补，重要）**：本项目是**后端驱动菜单**（`VITE_ACCESS_MODE` 未设 → backend 模式），
> 前端 `asyncRoutes.ts` 的 `isHide` **不生效**。隐藏路由的正确做法与资产详情（id=16，`detail/:id`，is_visible=false）一致：
> `soc_menus` 插一行（parent=/browsing，`path='profile/detail/:ip'`，`component='/browsing/profile/detail'`，
> **`is_visible=false`**，注意列名是 `is_visible` 不是 `is_hidden`），并在 `soc_role_menus` 授给已拥有
> 「行为画像」菜单的角色（admin + auditor）。走 alembic 迁移，禁止手工插库。
>
> 现有从资产/告警/基线跳转的 `?ip=xxx` 入口保持不变：L1 概览页 onMounted 读到 `?ip=` 时
> `router.replace` 重定向到详情路由（L2 不直接消费 query）。

## 4. L1 · 行为画像概览页设计（群体画像）

### 4.1 页面结构（自上而下）

| # | 区块 | 组件 | 内容 | 数据来源 |
|---|------|------|------|---------|
| 1 | 群体 KPI | 4 张指标卡 | 画像主体总数 / 人类主体 / 机器主体 / 数据完整度 | `GET /behavior-profile/overview` |
| 2 | **人设群体分布** | 横向条形图 + 标签云 | 夜猫子 15 · 作息极规律 7 · 早起鸟 4 · 轻度熬夜 4 · 码农 1 · 下载机 1 · 学生党 1 …（实测标签） | 同上 `tag_distribution` |
| 3 | 全网活跃节律 | 24h 曲线 + 时段饼 | 全网各时段访问量聚合 | 同上 `global_by_hour` / `global_by_block` |
| 4 | 全网兴趣构成 | 分类饼 + TOP 域名 | 14 类兴趣占比 + 全网 TOP 20 域名 | 同上 `global_cat_share` / `global_top_domains` |
| 5 | 风险分布 | 分层条形图 | **V1 按 `soc_assets.criticality`（已有、零成本）分层**；告警量/漏洞数分层为 V2（需跨源聚合，成本高，暂缓） | 同上 `risk_distribution` |
| 6 | **画像主体列表** | 表格（可筛选/排序/搜索） | IP / 主机名 / 资产名 / 访问量 / 流量类型 / 置信度 / 标签 / 操作（查看画像） | `GET /behavior-profile/list`（已存在） |

### 4.2 列表筛选与排序

| 维度 | 选项 |
|------|------|
| 流量类型 | 全部 / 人类 / 机器 / 混合（已有 `traffic_type` 参数） |
| 人设标签 | 下拉多选（夜猫子/工作狂/下载机/学生党…） |
| 置信度 | 全部 / ≥60 / <60 |
| 排序 | 访问量↓ / 置信度↓ / 深夜占比↓ / 告警数↓ |
| 搜索 | IP / 主机名 / 资产名模糊匹配 |

### 4.3 新增接口

```
GET /api/v1/behavior-profile/overview?days=7
```

**权限（v1.1 补）**：与现有画像读端点同口径 `require_role("admin", "auditor")`，
查看落审计（`_audit(current_user, "QUERY", "*", "overview days=N")`）。

**数据口径（v1.1 补）**：
- `subject_total` / `traffic_type` / `confidence_dist` / `tag_distribution`：取每主体**最近一条 ok 快照**（不限窗口）
- `global_by_hour` / `global_by_block` / `global_cat_share`：窗口内全部 ok 快照按日求和再算占比；分类占比来自 `cat_by_block`（ACT 层计数）
- `global_top_domains`：`soc_behavior_domains` 窗口内按域名聚合 TOP 20
- `risk_distribution`：V1 = join `soc_assets.criticality` 四档计数
- `data_freshness`：窗口内 distinct 快照日数 + 最新日期

响应（建议）：

```json
{
  "code": 200,
  "data": {
    "subject_total": 74,
    "traffic_type": {"human": 74, "machine": 0, "mixed": 0},
    "confidence_dist": {"high": 7, "mid": 4, "low": 63},
    "tag_distribution": [{"name": "间歇上线型", "count": 19}, ...],
    "global_by_hour": [0,0,...],
    "global_by_block": {"深夜": 12.3, ...},
    "global_cat_share": {"AI 工具": 34.2, ...},
    "global_top_domains": [{"domain": "...", "visits": 0, "category": "..."}],
    "risk_distribution": {"critical": 0, "high": 3, "medium": 12, "low": 59},
    "data_freshness": {"latest_date": "2026-09-04", "snapshot_days": 1}
  }
}
```

## 5. L2 · 单 IP 详情页改造

### 5.1 左栏：身份档案卡（替换现有主体列表）

## 6. 关系网络拓扑设计（D2 修复）

### 6.1 可视化方案

采用 **ECharts `graph` + `force` 力导向布局**（与 §9.5 的 ECharts 选型一致，前端已装 `echarts@^6.0.0`）。

### 6.2 图元约定

| 元素 | 样式 | 含义 |
|------|------|------|
| 中心节点（本机） | 大圆 + 主色描边 | 当前画像 IP |
| 出站目标节点 | 绿色 | 本机登录了谁（`relations.outbound`） |
| 入站来源节点 | 蓝色 | 谁登录了本机（`relations.inbound`） |
| 外部攻击源 | 红色 | 失败登录来源（`relations.external_attackers`） |
| 同网段邻居 | 灰色虚线 | `soc_assets` 同 `network_segment` |
| 账号节点 | 菱形 | 归一化后的账号（`accounts_on_host`） |
| 边粗细 | 按 `count` 映射 | 交互频次 |
| 边标签 | "xiejava ×556" | 账号 + 次数 |

### 6.3 交互（V1 实现范围，v1.1 修订）

| 交互 | 行为 | 版本 |
|------|------|------|
| 点击节点 | 跳转到该 IP 的画像详情（`router.push`） | V1 |
| 悬停节点/边 | 显示账号 + 次数 | V1 |
| 布局 | 力导向（节点 ≤30 时）⇄ 环形（节点 >30 时自动切） | V1（自动，不提供手动切换） |
| 边粗细映射 count | 按次数对数映射 | V1 |
| 图例筛选 | 按关系类型显隐 | **V2（降级）** |

> 原型中拓扑图为简单左右布局；V1 落地用 ECharts graph（力导向为主），交互以「可点、可悬停」为验收线，
> 图例筛选等增强顶后续需求。

### 6.4 数据

复用现有 `GET /behavior-profile/{ip}/relations`（已返回 `inbound` / `outbound` / `external_attackers` / `accounts_on_host` / `device_shared_by`）。

**建议补充字段**（可选）：
- `same_segment: [{ip, hostname, asset_name}]` —— 同网段邻居，让拓扑图更饱满
- `last_seen` —— 关系边的最近活跃时间
